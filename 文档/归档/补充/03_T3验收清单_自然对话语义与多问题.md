# T3 验收清单：自然对话、语义兜底与多问题处理

对应需求：R04。对应技术文档：3.1—3.4。
本清单依据本会话提供的《02_技术文档_核心能力对齐.md》和《01_需求文档_核心能力对齐.md》，并纳入后续对话明确的“完整诉求理解与防误拆”修订。
本清单是验收方案，不是测试结果；没有访问或运行用户本地服务。

## 1. 验收目标与范围

T3 要证明：普通交流自然；口语能够理解；一个真实问题不误拆，多个真实问题不漏答；背景与条件不丢；有些问题无法回答时，仍保留其他答案；无需回复时确实不发送；模型规划调用有边界。

不重新验收整套 LangGraph 框架，不把 T1 的完整议价闭环、T2 的真实搜索效果、T4 的人工接管功能、T5 的断线恢复全部纳入本阶段。但要确认 T3 没有改坏已有价格、授权、控制和响应合同。

重要修订：原文中“保留规则任务”应理解为保留已确认的独立诉求，不是无条件保留所有关键词候选。模型可以在校验后撤掉误触发候选。不能在模型失败时把可疑候选全部恢复并执行。

## 2. 第一步：准备真实测试入口与记录

### 2.1 运行范围

使用本地真实 `/chat` 主入口，串到当前实际的 Planner/LangGraph、专家和合并节点。暂不连接真实买家的自动发送。

独立问题使用全新 `chat_id`；多轮场景在场景内部复用同一个 `chat_id`，不同场景隔离。不要一直复用 `chat-001`。语义复测时禁用会跳过模型规划的规划缓存或答案缓存；本地模型加载缓存、知识索引缓存无需为此关闭。

固定测试时的商品和政策快照。优先使用隔离测试商品：价格、成色、发货时效和运费明确；进水记录明确标记为 unknown；售后为 manual_review。不得直接覆盖真实商品授权。金额、时效的预期取自实际加载的测试快照，而不是模型上一次说过的话。

### 2.2 每个请求必须记录

| 记录 | 用途 |
|---|---|
| run_id、chat_id、测试商品、配置/规则版本 | 对应同一次请求，保证可复现。 |
| 原消息、归一化完整问题 | 检查口语、否定、时间、假设或实际反馈是否改变。 |
| 最终业务诉求和条件 | 检查多拆、漏拆、条件丢失。 |
| 规划来源和实际语义模型调用次数 | 区分规则、真实模型兜底，避免隐藏二次分类。 |
| 实际经过的节点、每个任务的结果与来源 | 检查接线、查询范围与结果保存。 |
| 最终 answer、action、是否全部可答 | 检查合并后是否漏答、错报成功。 |
| 渠道模拟发送次数、AUTO/HUMAN 前后状态 | 检查 ignore 和失败不误触发接管。 |

这些是验收记录建议，不代表当前接口已经有这些字段。可写入本地测试报告，不要求把调试字段暴露给买家。日志不要含 Cookie、密钥、内部底价或无关个人信息。

不要用 `intent=SEMANTIC` 证明真实调用过模型，也不要用 `results` 长度、sources 数量或经过几个节点来计算买家的诉求数量。

## 3. 第二步：真实模型业务样例

以下“几个问题”指独立业务诉求，不含问候、检索步骤、内部辅助节点。普通对话可以有 service 任务，但不因此多算一个商品/价格/售后问题。

### A. 自然对话和口语（技术 3.1、3.2；需求 R04）

| 编号 | 输入 | 必须满足 |
|---|---|---|
| A01 | 你好 | 简短自然回应；不要求商品编号，不查商品/售后知识库；语义规划调用 0 次。 |
| A02 | 谢谢 | 自然回应，例如“不客气”；不生成售后长文，不强行查资料；语义规划调用 0 次。 |
| A03 | 这台相机能正常使用吗？ / 这玩意儿能正常用不？ | 分别新建会话执行。都识别为商品使用状态咨询，按明确的功能资料回答；不能把第二句当无关闲聊。 |
| A04 | 谢谢，最低多少？ | 保留一个价格诉求；不能因“谢谢”把整条忽略；报价来自当次有效授权，合并不改金额或运费条件。 |

自然度判定不要求逐字匹配模板：先回答诉求，必要时说明下一步；不向买家背诵“系统禁止承诺”等内部约束；不自称已执行当前系统并未执行的动作。

### B. 完整诉求与防误拆（技术 3.1，加后续修订；需求 R04）

| 编号 | 输入 | 必须满足 |
|---|---|---|
| B01 | 如果镜头裂了可以退吗？ | 1 个售后诉求；开裂是假设，不记录成已发生、已核实的损坏。 |
| B02 | 今天早上收到货后发现镜头开裂，可以退吗？ | 1 个售后诉求；保留“今天早上收货后发现”和未核实反馈，不改成假设、不擅自认定损坏发生时间或责任。 |
| B03 | 今天早上收到货后发现镜头开裂，退回去运费谁出？ | 1 个退货运费诉求；携带 B02 的损坏与发现背景。不得额外生成“支持什么售后”的独立问答。 |
| B04 | 镜头裂了，寄回去的钱算谁的？ | 1 个退货运费诉求；保留开裂背景；不能自行补出“今天收货”或损坏责任。 |
| B05 | 镜头裂了。可以退吗？ | 1 个带开裂背景的售后诉求；句号不自动产生一个“镜头介绍”任务。 |
| B06 | 今天收到后发现镜头开裂，可以退吗？退回去运费谁出？ | 保留 2 个真实诉求：能否退货、运费承担。二者都保留相关背景；相同 service 类型不等于重复。 |
| B07 | 这个镜头有没有裂纹？ | 1 个实物情况问题。不能误当成已发生损坏或只介绍售后；资料不足就说明无法确认。 |
| B08 | 镜头是什么型号？今天收到后发现裂了，可以退吗？ | 2 个真实诉求：镜头型号、带开裂背景的售后咨询。 |

分类目标字段可以沿用合法的 `seller_rule.general`，但还必须明确区分是在问退货资格还是退货运费，并把完整条件传入处理节点。仅仅两个任务标签一样不能作为合并理由。

manual_review 场景可以解释核实与处理条件，但不能未核实就批准退款、认定卖家责任或承诺某人已经开始审核。也不能把“退货”“卖家承担”等词一律屏蔽，导致有依据的条件性说明被删除。

### C. 多问题、未知和会话（技术 3.1—3.3；需求 R04）

| 编号 | 输入或场景 | 必须满足 |
|---|---|---|
| C01 | 成色怎么样？多少钱？包邮吗？收到后有质量问题怎么处理？ | 覆盖 4 个独立诉求，合成一条回复；金额、成色、运费和政策条件都不被合并改写。 |
| C02 | 多少钱？以前进过水吗？什么时候发货？ | 使用进水史=unknown、价格和时效已知的隔离测试资料。回答价格与时效；只对进水史说明无法确认；整条 action=reply，未知子任务不得标为已回答，不能自动 HUMAN。 |
| C03 | 新会话且不传 item_id：这个多少钱？ | 缺商品时明确澄清，不能沿用其他会话商品或选演示商品。 |
| C04 | 同一会话：先问 B02，再问“那寄回去的钱呢？” | 第二轮 1 个退货运费诉求，继承相关的未核实开裂反馈，不重复回答上一轮问题。 |
| C05 | 另开会话，仅问“那寄回去的钱呢？” | 不继承 C04 的开裂反馈。允许按通用条件说明或询问必要背景，不强制唯一文案。 |
| C06 | 同一会话：先问 C01，再问“什么时候发货？” | 第二轮仅回答发货；不把第一轮任务或答案残留到本轮。 |
| C07 | 这款相机支持哪些测光方式？ | 保留具体技术问题，不能归一化成仅有“商品专项知识”。本项只验 T3 的理解与路由；有没有真实技术证据属于 T2，不要求凭空答出参数。 |

全部先各跑一次。对口语、防误拆和混合/多问题关键样例，用独立会话再重复运行，建议累计 3 轮；这只是本阶段回归基线，不代表对所有真实表达都已证明准确。

## 4. 第三步：让 Coding Agent 自动验收内部边界

本组需要模拟故障或渠道事件，不能靠在普通聊天框里输入“超时”“系统消息”代替。

| 编号 | 测试方式 | 必须满足 |
|---|---|---|
| D01 | 注入可信适配器构造的纯系统事件 | 不调用回答模型；原发送器替身调用次数=0。不能发送空字符串或 `-`。允许在渠道守卫处直接忽略。 |
| D02 | 合并器输入全部无需回复的任务结果 | 对外 action=ignore；action_mapper 和 worker 不调用发送器。 |
| D03 | 买家文本：页面有个[去支付]，这件多少钱？ | 保留价格询问，不因为包含系统卡片文字就把真实买家问题全部过滤。 |
| D04 | 规则完整识别“多少钱”，另用一个规则无法完整识别的口语样例触发真实兜底 | 前者语义规划=0 次，后者=1 次。一次完整消息最多一次语义模型请求，不能按片段或专家重复分类。 |
| D05 | 模拟语义规划超时 | 在项目配置预算内结束；保留已确认的规则诉求，对未理解内容安全降级或澄清；不能把可疑关键词候选全部执行。不得无限重试或自动 HUMAN。 |
| D06 | 模型输出非法 JSON、不合法目标或越界字段 | 校验后不执行非法任务；不能据此改商品、价格授权或发起退款写操作；仍保留有把握的有效任务。 |
| D07 | 模型规划补出 product 任务，而规则起初未要求商品解析 | 本轮同步做正确的商品解析。缺商品时澄清；不能跳过校验，不能用过期 requires_item 决策误查其他商品。 |
| D08 | 价格任务成功，另一任务被模拟为异常或无证据 | 保留价格答案；未知/异常仅影响相关任务；错误原因内部可定位，不虚报整轮全部成功。 |

“最多一次”限制的是分类、归一化、语义规划这类理解请求，不能把专家二次分类藏到别的计数里。最终专家生成答案的模型调用单独计数；不要求整条消息总共只能调用一次模型。按文档约定，不增加额外的整篇润色调用。

模拟模型能证明故障分支和接线；不能证明真实模型能够理解口语。报告必须分开标记“模拟边界测试”和“真实模型语义测试”。

T3 只需要用发送器替身证明调用或不调用发送链路，不以向真实买家发送作为本阶段前置。真实平台收发能力另在 T5 验收。

## 5. 第四步：输出报告，再决定是否进入 T4

每项分别填写：通过、失败、未执行、待复核。HTTP 200、节点 answered、pytest 全绿都不能单独证明整个 T3 通过。

建议每条报告用以下格式，不设难懂的 0/1 得分：

```text
用例：B03
原问题：今天早上收到货后发现镜头开裂，退回去运费谁出？
预期业务诉求：1 个，退货运费承担
实际业务诉求：填写真实结果
保留条件：填写真实结果
规划来源与语义模型调用次数：填写真实结果
实际节点及子任务结果：填写真实结果
最终回答与 action：填写真实结果
结论：通过 / 失败 / 未执行 / 待复核
原因：说明具体差异
```

T3 通过条件：样例覆盖完整；真实模型关键语义回归通过；内部边界测试通过；没有漏答、多拆、串会话、未经授权的承诺或误发送；未执行和待复核项目已完成；失败原因已修复并重测。话术没有逐字匹配模板不算失败，但事实或条件被改写必须失败。

你上次贴出的 B03 类日志仍生成了两个任务，且运费任务丢失场景。这只能代表那次记录未通过，不能推断目前代码是否已修复；本轮应以新执行结果为准。

## 6. 可直接交给 Coding Agent 的任务

```text
按本清单验收 T3（需求 R04、技术文档 3.1—3.4），不要扩大重构。

先读本地最新代码，找到真实 /chat 与 Planner/LangGraph 入口。
复用已有测试和诊断日志；没有的再补，不绕过主入口只测独立节点。
在隔离数据和测试会话中批量运行 A/B/C 组。
对 D 组添加可重复的故障注入、模型调用计数和发送器替身测试。

重点回归：
“镜头开裂，退回去运费谁出”只有一个带开裂背景的运费诉求；
“可以退吗？运费谁出”保留两个真实诉求；
“谢谢，最低多少”不能整条 ignore；
一个未知子问题不能抹掉其他答案。

真实模型测试不得替换语义模型或复用规划/答案缓存。
模拟故障与真实语义测试分开统计。
不修改真实商品授权，不发送真实闲鱼消息，不泄露密钥。

输出每条的真实任务、条件、调用次数、节点、答案、action 和结论。
将“未执行/待复核”单列，不计入通过。
最后给出实际可复制执行的测试命令、报告路径与 T3 通过/未通过结论。
不要编造不存在的脚本命令，不把 HTTP 200 或节点 answered 当作业务验收。
```
