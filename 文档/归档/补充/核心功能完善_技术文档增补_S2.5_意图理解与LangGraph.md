## 1. 本次要解决什么

本章不是为了修复某一个句式，而是要把当前“按关键词拆题”的方式升级为**通用多诉求语义规划**。

真实买家可能一次性把多个问题、条件、补充说明和口语表达混在一起，例如：

> 这台修过没？最低多少？今天能发吗？如果到手发现镜头裂了能退吗？不包邮还能再少点吗？

系统不能只看见“修过、最低、发货、镜头、退、包邮”这些词，然后机械生成一堆任务；也不能只给整句话贴一个主意图标签。它必须先理解：

- 买家到底提出了几个**独立诉求**；
- 哪些只是对象、前提、条件、否定或补充说明，不应单独变成任务；
- 每个诉求属于哪个业务意图、需要哪个专家；
- 诉求之间是否存在先后依赖或成交条件；
- 哪些信息来自当前轮，哪些需要从历史上下文补全；
- 哪些只是内部核验步骤，不需要额外对买家输出一段回答。

本次同时落实两个目标：

- **理解正确**：把任意一条复杂买家消息转换为结构化 `UserNeed[]`，而不是针对若干固定句式写补丁。
- **执行清楚**：由 LangGraph 执行已经确定的任务图，只调用必要的专家；保留既有商品查询、价格计算、RAG、联网搜索和结果合并能力。

“如果镜头裂了可以退吗？”只作为一个典型回归样例，用来验证“条件不能被误拆成独立商品问题”；它不是本章的唯一目标。

意图正确，不等于业务结论已经确定。识别出一个售后诉求，不代表可以直接承诺退货；识别出一个报价诉求，也不代表报价一定可接受。专家仍依据已有业务资料和确定性规则作答。本章不恢复旧固定拒答覆盖链。

## 2. 关键架构决定

### 2.1 意图理解属于 Planner，不另设第二个总调度 Agent

建议逻辑边界：

```text
读取会话上下文
→ Planner：完整语义理解 → 独立诉求 → Task[]
→ 解析本轮需要的商品上下文
→ LangGraph：执行已确定的任务
→ ResultMerger：合并一次
→ 保存会话
→ 渠道发送
```

读取会话只是取得历史和当前商品，不等于已理解意图。最终任务规划必须由一个入口负责。不能先识别为售后，再由另一套关键词规则添加镜头参数任务。

意图理解逻辑必须先于专家分派，但不要求所有系统都必须将它放在图外。为缩小本项目的改造范围，第一版保留 Planner 在图外；以后即使包装成图的首节点，也只能运行同一套理解逻辑一次。

### 2.2 不能用一个“主意图标签”覆盖整轮所有问题

“镜头裂了能退吗”是一个售后诉求；“带什么镜头？镜头裂了能退吗”是两个诉求。模型需输出结构化诉求列表，而不是只输出一个 AFTER_SALE 标签。

每个诉求应至少保留：原文、规范化问题、意图、对象、情景条件、否定信息、上下文引用。模型不得补写未提供的商品事实。

### 2.3 一个诉求不一定等于一个内部步骤

“如果没修过，1900我就买”是一个有成交条件的诉求，系统内部可能需要商品核验和价格判断。内部核验不代表买家又额外提出了一个“维修记录介绍”问题。执行依赖完成，也不等于成交条件成立。

### 2.4 核心目标是 1～N 个诉求，而不是单意图分类

Planner 必须支持一条消息中同时存在多个独立诉求。典型组合包括但不限于：

```text
商品事实 + 价格
商品事实 + 价格 + 发货
价格 + 售后
商品事实 + 售后 + 平台规则
商品事实 + 价格 + 发货 + 售后 + 议价条件
同一专家内部的多个不同诉求
```

因此，系统输出的核心对象不是：

```text
primary_intent = AFTER_SALE
```

而是：

```text
UserNeed[]
```

其中每一个 `UserNeed` 表示一个“需要单独得到结果的诉求”。同一专家可以对应多个 `UserNeed`，不同专家之间也可以存在依赖。

### 2.5 任务数量由“独立答案数”决定，不由关键词数量决定

判断是否拆成多个任务时，应问：

> 买家是否期待系统分别给出多个可以独立判断、独立回答的结果？

例如：

- `镜头裂了能退吗？` → 1 个售后诉求；
- `带什么镜头？裂了能退吗？` → 2 个诉求；
- `修过没？最低多少？今天能发吗？` → 3 个诉求；
- `如果没修过，1900我就买。` → 1 个成交诉求，但内部存在“维修事实核验 → 价格判断”的依赖步骤。

不能用标点数、关键词数、专家数直接代替这个判断。

## 4. 语义规则的具体判定

### 4.1 本例必须只有售后任务

输入：`如果镜头裂了可以退吗？`

| 字段 | 预期理解 |
|---|---|
| 对象 | 镜头 |
| 情景 | 裂开 |
| 情景性质 | 假设，并非已确认这件商品裂开 |
| 真正诉求 | 该情景下是否支持退货 |
| 负责专家 | ServiceAgent |
| 用户可见问题数 | 1 |
| 不应新增 | 焦距、型号、配件、最低价等任务 |

允许 ServiceAgent 读取当前商品资料、已有售后知识和必要的上下文。“只调用售后专家”不等于“禁止读取商品数据”。

### 4.2 以下情况不能套用“只要出现售后就只答售后”

| 买家原话 | 应当如何处理 |
|---|---|
| 镜头是不是裂了？ | 商品状态询问，交给商品专家；不能因资料没写损坏就答没有裂 |
| 带什么镜头？如果裂了能退吗？ | 商品参数和条件售后两个独立诉求 |
| 最低多少？收到镜头裂了能退吗？ | 价格与售后分别处理 |
| 不是问镜头型号，我问裂了能不能退 | 只处理当前明确的售后诉求，不执行被否定的参数询问 |
| 如果没修过，1900我就买 | 先核验成交条件，再进行价格决策，不把 unknown 当成满足条件 |

这些示例是本项目的预期语义，不是对真实售后资格或商品状态的事实认定。

### 4.3 多诉求复杂消息必须整体理解

下面这类消息才是本章真正要覆盖的主要场景：

> 这台修过没？成色怎么样？最低多少？不包邮还能少多少？今天能发吗？如果收到以后镜头有裂痕能退吗？

预期应先形成多个独立诉求，例如：

```text
Need 1：维修记录                  → product
Need 2：成色                      → product
Need 3：最低价                    → price
Need 4：不包邮条件下的价格         → price
Need 5：发货时间                  → service
Need 6：特定损坏情景下的售后处理   → service
```

其中：

- “镜头有裂痕”属于 Need 6 的售后情景，不能额外再生成“镜头参数”任务；
- Need 3 和 Need 4 都属于 PriceAgent，但仍然是两个不同诉求，不能因为专家相同就错误合并；
- 如果某个诉求依赖另一个事实，例如“没修过才按1900成交”，必须建立显式依赖，而不是依赖回答文本猜测。

再例如无标点口语：

> 这个修过没最低多少今天能发不收到有问题咋办

也必须能够识别多个诉求，不能把“没有标点”当作只有一个问题。

### 4.4 语义理解至少要处理五类关系

对每一个买家消息，Planner 至少需要判断：

1. **独立诉求关系**：哪些内容需要分别回答；
2. **条件关系**：`如果A，那么B` 中 A 是否只是 B 的前提；
3. **否定关系**：`不是问型号` 不能继续生成型号任务；
4. **指代/省略关系**：`那不包邮呢` 需要结合上一轮价格上下文；
5. **依赖关系**：某些任务必须在另一个事实核验完成后才能安全执行。

只有识别出这些关系之后，才能生成最终 Task 列表。

### 4.5 不能遗漏数字与动作的语义

“7天无理由”中的7是天数，“50mm”是规格，“1900元包邮可以吗”才是报价场景。“能退吗”是咨询，“请直接退款”可能是操作请求，两者不能共用一个自动退款动作。本阶段不增加实际退款、改价等写操作。

### 4.6 区分理解不明确与系统出错

有历史时，“那能退吗”可以补全上下文；没有历史且指代不明时，提出具体澄清。模型超时、JSON 无法解析是系统故障，应记录独立错误，不伪装成买家没说清楚，也不得回退成按领域词拆多个任务。

## 5. 实施顺序

| 阶段 | 内容 | 完成后才进行 |
|---|---|---|
| A0 | 保存现有任务、回复与搜索调用基线 | A1 |
| **S2.5A** | 补齐语义意图理解与任务生成；先使用现有执行器验收 | S2.5B |
| **S2.5B** | 按既定流程图接入 LangGraph 专家工作流，负责专家路由、任务依赖、状态流转与结果收集 | S2.5C |
| **S2.5C** | 联调真实模型与指定闲鱼测试会话，检查多轮、搜索和来源 | 原第三部分 |

A 阶段解决“用户到底问了什么、应该生成哪些任务”；B 阶段把这些任务交给 LangGraph，由图负责专家路由、依赖、状态流转和结果收集。两阶段要分开验收，避免把语义问题和图编排问题混在一起。

本章明确把 LangGraph 作为专家工作流编排层，而不是把它描述成普通执行器替代品。意图理解属于 A 阶段；Graph 只执行 A 阶段已经生成并校验过的任务图。

以下案例的“语义诉求数”不等于网络请求数、图节点数或发送消息数。每轮最终只有一个发送候选；内部核验可以有独立任务。

| I28 | 无 | 这个修过没最低多少今天能发不收到有问题咋办 | 4 | product + price + service + service | 无标点口语仍识别维修、价格、发货、售后四个诉求。 |

| I30 | 无 | 这台摔过吗修过吗快门正常吗配件齐不齐 | 4 | product × 4 | 同一专家四个独立商品事实诉求，不能错误合并成一个“商品情况”。 |

### 6.1 怎么执行验收

先做确定性测试：将语义模型输出、工具结果或专家结果固定，验证映射、依赖、专家调用次数和结果合并。

再做真实模型测试：以上36条每条建议至少重复3次，并增加未写入提示词的口语改述；报告每条的实际任务和错误，不声称一次通过就具有普遍正确性。关键回归不只看 I01 这类单诉求，还必须重点覆盖 I27— I36 的多诉求、无标点、同专家多任务和跨轮组合场景。

最后做真实多轮测试：指定测试会话自由追问，不限制买家只能发送用例原文。普通多轮保留相同会话；测试无历史时使用新会话。记录新增失败样例，加入回归集。

本阶段的判定标准：关键用例不能出现无关参数/价格任务；真实多问题不能漏掉独立诉求；搜索行为不因B阶段迁移而增加或失效；不得靠删除失败用例或一律返回固定话术来通过。

### 6.2 报告必须区分的指标

| 指标 | 统计口径 |
|---|---|
| 诉求集合正确率 | 本轮识别出的完整诉求集合与人工标注集合一致的样本数 / 总样本数 |
| 诉求数量正确率 | 实际独立诉求数量与人工标注一致的样本数 / 总样本数 |
| 条件保留率 | 正确保留前提、否定、运费、金额、时效等关键条件的适用样本数 / 适用样本数 |
| 错误拆分率 | 一个诉求被额外拆成无关任务的样本数 / 单诉求样本数 |
| 错误合并率 | 两个或多个独立诉求被错误合并成一个任务的样本数 / 多诉求样本数 |
| 漏答诉求率 | 未规划出的独立诉求数 / 标注的独立诉求总数 |
| 无关专家调用率 | 出现至少一次不必要专家调用的请求数 / 总请求数 |
| 延迟与模型调用数 | 区分意图模型、专家模型和搜索；记录平均值、P95与失败数 |

上述指标尚无实测值，不写成已达成成绩。
