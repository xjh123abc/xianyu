## 1. 结论与边界

本次不是“修复镜头裂了能不能退”这一条特殊句式，也不是在关键词 Planner 前面再加一个单标签分类器。

目标是把 Planner 升级为**通用多诉求语义规划器**：

```text
任意一条买家消息
→ 识别 1～N 个独立诉求
→ 为每个诉求提取对象、动作、条件、否定、金额/时间单位、上下文引用
→ 识别诉求之间的依赖与内部核验步骤
→ 生成唯一的 Task DAG
→ LangGraph 执行 Task DAG
```

“如果镜头裂了可以退吗”只是一个回归案例，用来验证“前提不能被误拆成独立任务”。真正验收重点必须覆盖三到六个诉求叠在一起、同一专家多个诉求、无标点口语、跨轮省略和带条件成交等复杂输入。

LangGraph 只接管已经生成的 Task DAG 的执行，不重新解释整轮原话。

```text
ChatService / SessionManager.load
→ Planner.plan_async
    → IntentAnalyzer：UserNeed[]
    → Task映射与合同校验：就绪时输出Task[]；否则提前澄清/报告错误
→ 原有ItemContextResolver与预计算澄清结果
→ GraphTaskExecutor.execute
    → 按任务选择处理器
    → ProductAgent / PriceAgent / ServiceAgent / 现有其他Handler
→ 原ResultMerger
→ 原SessionManager.save_turn
→ 原渠道发送器
```

这是建议的新路径。当前同步 `Planner.plan()` 接口不应被突然删除；按A阶段迁移步骤逐一切换调用点。

“先理解再分派”是逻辑依赖；意图理解也可以成为图的首节点。第一版刻意保留在图外，是为了不同时搬迁规划和执行两种职责，不是LangGraph规定理解必须在图外。

## 2. 当前代码为什么会误拆

| 位置 | 已核实的行为 | 本次处理 |
|---|---|---|
| `intent_router.py::route()` | 先匹配规则；“可以退”可判为AFTER_SALE；规则命中后不会走模型后备 | 保留兼容用途，不能再独立决定新路径的最终任务 |
| `planner.py::plan()` | 调用 `route(query, allow_ai=False)`；对标点分句后调用 `build_expert_plan()`，未传入模型规划器 | 为新路径提供整轮语义分析，不能先把条件切散 |
| `query_planner.py::_rule_drafts()` | 出现“镜头”就添加商品配件任务 | 在新语义路径中不再按出现对象名直接生成任务 |
| `query_planner.py::_merge_drafts()` | 从全部规则草稿开始，模型草稿主要增补或修改同目标问题，不能取消错误规则目标 | 新路径采用一份最终语义计划，不将规则任务无条件并回 |
| `service_agent.py` | `item_fact`走确定性字段回答；`seller_rule`才准备通用证据并生成 | 售后场景咨询必须进入能解释规则的服务路径，不只返回单个配置枚举 |

因此，单独把 `allow_ai=False` 改成 `True` 不够；仅优化Prompt也不够；在最后字符串去重更不够。必须调整“谁拥有最终任务列表”。依据见C1—C4。

## 3. A阶段：语义意图理解

### A0：固定当前基线（R-LG04）

记录当前版本、Prompt版本、模型配置、任务列表、专家/工具调用与输出。至少留存单商品问题、单售后问题、多问题、需要联网、不需要联网、搜索失败、多轮追问。

用户第二部分已经可用的搜索实现只作为现有能力接入；实施者先定位实际文件，不创建一个同名但独立的新搜索系统。

### A1：定义通用多诉求语义合同（R-INT01—R-INT04、R-INT07—08）

建议在 `app/services/intent_contracts.py` 定义 `UserNeed`、`NeedDependency` 与 `UnderstandingResult`；使用项目现有的 Pydantic 或 dataclass 风格。

合同必须天然支持一轮 1～N 个诉求，而不是为单一主意图设计。以下是多诉求示意，不是当前已有字段。

输入：

```text
这台修过没？最低多少？今天能发吗？如果到手镜头裂了能退吗？
```

建议输出：

```json
{
  "status": "ready",
  "needs": [
    {
      "need_id": "n1",
      "intent": "product.repair_history",
      "original_question": "这台修过没？",
      "normalized_question": "查询当前商品是否有维修记录",
      "subject": "当前商品",
      "conditions": [],
      "reply_required": true,
      "depends_on_need_ids": []
    },
    {
      "need_id": "n2",
      "intent": "price.minimum",
      "original_question": "最低多少？",
      "normalized_question": "查询当前商品最低可成交价格",
      "subject": "当前商品",
      "conditions": [],
      "reply_required": true,
      "depends_on_need_ids": []
    },
    {
      "need_id": "n3",
      "intent": "shipping.dispatch_time",
      "original_question": "今天能发吗？",
      "normalized_question": "确认今天是否可以发货",
      "subject": "当前商品",
      "conditions": [],
      "reply_required": true,
      "depends_on_need_ids": []
    },
    {
      "need_id": "n4",
      "intent": "after_sale.consult",
      "original_question": "如果到手镜头裂了能退吗？",
      "normalized_question": "假设收货时镜头裂开，是否支持退货",
      "subject": "镜头",
      "conditions": [
        {
          "type": "scenario",
          "event": "镜头裂开",
          "timing": "收到商品时",
          "modality": "hypothetical"
        }
      ],
      "reply_required": true,
      "depends_on_need_ids": []
    }
  ],
  "clarification_question": null
}
```

这个例子同时验证：

- 一条消息可以产生多个 `UserNeed`；
- 同一句中的对象词不会自动变成独立任务；
- 不同诉求分别保留自己的原文和条件；
- 最终任务数由独立诉求决定，而不是由关键词数量决定。

字段含义：

| 字段 | 约束 |
|---|---|
| `status` | `ready`、`clarify`、`error`；系统失败和语义歧义分开 |
| `needs` | 当前轮的独立诉求列表；一个整轮主标签不能代替它 |
| `intent` | 例如售后咨询、商品属性、价格询问/出价、订单查询；意图与专家名称分开 |
| `original_question`、`source_texts` | 来自买家当前原文；跨句可记录多个原文片段；不得虚构条件 |
| `normalized_question` | 保留原意的完整问题；用于检索/生成，不把条件简化没 |
| `scenario.modality` | `hypothetical`、`reported_unverified`、`unspecified`；买家说法不自动等于已验证事实 |
| `context_references` | 必要时引用本次上下文快照的历史位置及原文；不由历史自动创造新待答任务 |
| `requested_outcome` | 买家需要的答案，例如退货资格，不是对象“镜头” |

确实发生的“我收到的镜头已经裂了”记录为买家报告；仅“镜头裂了能退吗”未明确发生与否时，不强行标成已发生。“如果镜头裂了”必须是hypothetical。

原文定位需要校验：`source_texts`应能在当前消息或明确引用的历史快照中找到；如使用字符区间，区间应基于未经改写的原文，并校验切片。结构正确不等于理解正确，最终仍需要标注用例回归。

### A2：一次联合理解，不再两套计划叠加（R-INT01、03、04、05）

新增或收敛为 `IntentAnalyzer.analyze(message, context)`，由Planner内部调用：

1. 完整保留消息；不先按“镜头/退货”等领域词切片，也不把每个标点强制当成独立问题。
2. 只有全句明确匹配的简单消息走确定性快路径，例如独立的“你好”“标价多少”。快路径必须做整句匹配，不能用包含某个词就认定简单。
3. 口语、否定、条件、多问题、跨轮省略等情形，正常路径最多调用一次语义模型，联合输出所有诉求和条件。
4. 本地检查原文来源、金额单位、枚举、任务覆盖、重复和依赖；再确定最终任务。
5. 不调用另一个“总主管模型”再次拆题；不在图中再调用Planner。

推荐Prompt核心约束：

```text
你只解析买家的本轮诉求，不回答买家、不决定交易结果。
按“需要独立回答的请求”识别需求，不按出现的商品名、部件名或领域词数量拆分。
假设、原因、否定、举例、自我纠正属于对应请求的上下文，不能单独变成属性问题。
一个用户消息允许多个诉求；每个诉求必须保留必要条件。
最近历史只用于补全省略和指代；用户未重问的旧问题不再次加入。
当前商品事实与买家报告分开；不要把假设记成事实。
仅输出约定JSON；没有足够信息分辨请求时返回具体歧义，而不是随意猜测。
```

成对示例必须同时给模型看：“如果镜头裂了能退吗”只有售后；“带什么镜头？裂了能退吗”有两个请求。不能只教模型“售后优先”。

正常路径最多一次模型调用是性能约束，不是承诺每个问题都无需模型。先量测真实延迟；此阶段不做额外的模型自评、无限修复或反思循环。JSON解析失败记录 `intent_parse_failed`，模型超时记录 `intent_model_timeout`。不能悄悄回到旧的“每个领域词一个任务”。

系统故障只在无歧义的完整句规则可用时使用该规则；否则返回技术失败，保留日志。真正缺少语义上下文才返回clarify。不得因解析失败自动将会话切为HUMAN。

### A2.1：语义分析流程必须是“先建诉求，再建任务”

建议 Planner 内部按下面的固定顺序处理：

```text
1. 读取当前原话 + 必要历史
2. 找出所有候选诉求
3. 判断哪些候选只是对象/条件/否定/补充说明
4. 合并同一诉求的改述
5. 保留真正独立的 1～N 个 UserNeed
6. 为每个 UserNeed 标注意图、对象、约束和上下文引用
7. 建立 Need 之间的依赖关系
8. 确定哪些是用户可见诉求，哪些只是内部核验
9. 再确定性映射为 Task DAG
```

关键点：

- 不能先按标点切句，再假设每段都是独立问题；
- 不能先按领域关键词建任务，再让模型做“补充解释”；
- 不能只输出一个 `primary_intent`；
- 不能按专家名去重任务；
- 不能因为两个诉求都交给 ServiceAgent，就合成一个模糊的“售后问题”；
- 不能因为没有标点，就把整段当成一个问题。

例如：

```text
这个修过没最低多少今天能发不收到有问题咋办
```

仍应能识别出：

```text
维修记录
最低价
发货时间
售后处理
```

四个独立诉求。

### A2.2：明确就绪、澄清与错误的出口

建议新增轻量的 `PlanOutcome`，包含 `tasks`、`early_response`、`understanding`。新的异步 `plan_async` 返回它；现有同步 `plan()` 不改返回类型，仍只作兼容入口。`ChatService` 对就绪结果取出Task[]进入原 `_execute_planned_turn`；对语义澄清或系统失败，走明确的提前响应出口，不调用图，不给未知意图随便造一个商品或服务任务。两种出口都使用现有会话/响应保存边界，防止重复保存。

`early_response` 中的买家澄清必须具体；技术失败不得表述成“你的问题不清楚”。可复用项目已有错误响应语义，不把新结果伪装成 `can_answer=true`。

### A2.3：整合当前Planner的其他判断

当前 `order_router`、`build_question_plan` 和 `_needs_item` 等判断发生得较早。新路径不能先让这些规则按原文关键词做出最终决策，再加一个语义模型当装饰。

已分析的 `needs` 应决定：任务类型、是否为咨询或实际操作请求、是否需要当前商品，以及规范化查询。旧模块可以保留作兼容入口或提供候选线索，但不能覆盖新路径的语义结果。

保留现有订单、普通RAG、unsupported_action等能力的输入输出。涉及旧分支的迁移，逐个用现有回归验证，不直接删除目录或将所有问题强制改为售后。

同步处理 `ChatService` 的 `_planner_state` 兼容元数据：在仍有消费者期间保留，但从最终语义结果推导，不再次按原始领域词反向生成任务。

### A3：UserNeed[] 到 Task DAG 的确定性映射（R-INT02、04、06—08、R-COMP01）

语义模型负责“理解买家有几个诉求以及诉求之间是什么关系”，但不要让模型直接自由生成任意执行代码。

Planner 应将已经校验的 `UserNeed[]` 确定性映射成 Task DAG：

```text
UserNeed
→ 选择 task_type
→ 选择 query_target / execution_mode
→ 填充 normalized_question / intent_context
→ 建立 depends_on_task_ids
→ 标记 reply_required
→ 合同校验
→ 最终 Task DAG
```

简单单诉求案例仍然可以映射到当前已有的任务目标，例如：

```json
{
  "task_id": "q1",
  "task_type": "service",
  "query": "如果镜头裂了可以退吗？",
  "query_target": "seller_rule.general",
  "execution_mode": "xianyu_expert",
  "depends_on_task_ids": [],
  "metadata": {
    "normalized_question": "假设镜头裂开，是否支持退货？",
    "knowledge_scope": "seller_rule",
    "transaction_conditions": {},
    "intent_context": {
      "need_id": "n1",
      "intent": "after_sale.consult",
      "subject": "镜头",
      "scenario": {
        "event": "裂开",
        "modality": "hypothetical",
        "timing": "unspecified",
        "cause": "unspecified"
      },
      "requested_outcome": "return_eligibility",
      "reply_required": true
    }
  }
}
```

注意：`intent="after_sale.consult"` 是新增语义标记，而 `query_target="seller_rule.general"` 是现有执行目标，两者不是同一个概念。

之所以本例不简单设为 `after_sale.return_policy + item_fact`，是因为当前该路径只读单个售后字段；在资料是 `manual_review` 时无法直接解释这个具体场景。本例采用服务专家的规则解释路径，并提供已解析的商品上下文。它仍只有一个ServiceAgent任务。

新语义路径也不能再受“带item_id就禁止seller_rule，除非原话出现店铺词”的旧规则约束；当前商品的售后咨询同样可能需要商家规则。保留真实商品和资料作用域过滤，移除的是用字面词决定证据类型的限制。

不要未经修改合同就使用 `after_sale.return_policy + seller_rule`：当前 `_target_matches_expert` 不允许这个组合。如后续要扩展该目标，须同步修改合同验证、映射、处理器与测试。

#### A3.1：多诉求映射必须按 need_id 保持一一对应

对于：

```text
这台修过没？最低多少？今天能发吗？如果到手镜头裂了能退吗？
```

建议映射为：

```text
n1 → q1 product / repair_history
n2 → q2 price / minimum
n3 → q3 service / dispatch_time
n4 → q4 service / after_sale consult
```

约束：

1. 一个 `reply_required=true` 的独立诉求至少对应一个可追踪任务；
2. 同一专家可以拥有多个 task，不能按 `task_type` 或 expert 名称去重；
3. 相同诉求的重复改述可以在语义层合并，但必须保留 `source_texts`；
4. 内部核验任务可 `reply_required=false`，不直接形成额外买家回答；
5. 任务依赖必须来自显式语义关系，不能靠任务顺序猜测；
6. 最终 ResultMerger 按用户诉求顺序组织回答，而不是按专家执行顺序组织回答。

#### A3.2：保证情景没有在中间丢失

- `Task.query`保留对应完整原文，不能变成“镜头”或“可以退”。
- `metadata.normalized_question`为完整情景问题，用于检索。
- `metadata.intent_context`承载假设、对象、否定、历史引用等；增加从Task到ExpertTask/ExpertContext的透传，不能只在日志记录后丢掉。
- 不把非价格情景塞进旧 `transaction_conditions`。旧验证主要为报价条件设计，应该分字段处理。
- ServiceAgent收到原文、规范化问题、情景及真正检索证据。多轮省略问题应同时提供规范化完整问题与其历史出处，不只提供一句孤立的“能退吗”。
- 模型看到的是当前服务任务，不是其他专家任务的整轮问题清单；历史只补足上下文，不要求重复回答。

#### A3.3：规范化不是偷偷改变资料

“如果镜头裂了”不能被改写成“运输损坏的镜头”或“到货即损坏”，除非原话真的给出了原因/时间。买家报告不能写入卖家商品事实表；模型回复更不能反过来作为维修、进水等事实来源。

商品状态问题缺字段时，不能映射成焦距/型号来凑答案。严格区分“当前实物情况”和“该型号一般知识”。

#### A3.4：金额与数字

价格诉求必须有金额语义。先提取出价语境、原文金额和单位，再由确定性代码转换为整数分。7天、48小时、50mm、F1.8、商品ID不能进入 `offer_cents`。

本次完善价格输入识别，但不改变现有底价、优惠、运费算法。不得为得到非空回答擅自把低于底价的出价改成可接受。

#### A3.5：依赖完成不等于交易条件满足

“如果没修过，1900我就买”可以产生一个内部商品核验任务与一个价格任务。内部任务标记 `reply_required=false`，只向最终成交请求提供结构化证据；不是强行给买家再回答一个无关问题。

建议在结果元数据中提供有证据支持的 `verified_facts`，在价格任务携带显式 `preconditions`。只有证据支持未维修且价格条件允许，才确认可成交。

- 商品专家回答“维修过”：任务执行成功，但成交条件不成立。
- 商品专家回答“记录不明”：条件未知，不当作未维修。
- 买家说“修过也没事”：不生成必须未维修的条件。

第一版只实现明确支持的条件类型，例如是否维修；不支持的复杂条件保持原文并说明不能确认，不在通用条件解释器上扩展过多。

### A4：A阶段验收后冻结任务合同

使用配套需求文档 I01— I36。先固定模型输出测试任务映射，再测试真实语义模型。

验收重点分两类：

```text
单诉求：
不能因为对象词、条件词、数字而多建无关任务。

多诉求：
不能漏掉独立问题，不能按专家名合并，不能因无标点而漏拆。
```

特别要求覆盖：

- 3～6 个诉求叠加；
- 同一专家连续多个诉求；
- 多领域混合；
- 无标点/乱标点口语；
- 否定和自我纠正；
- 跨轮省略；
- 带依赖条件的成交请求。

条件不得丢失，依赖不能只靠文本顺序隐式表示。

此时仍使用现有执行器，以便把语义问题与图调度问题分开。修正已经误拆的行为是A阶段目标，不要求与错误基线保持一致；搜索/价格算法等不相关能力必须不退化。

## 4. B阶段：接入 LangGraph 专家工作流

B 阶段的目标不是“造一个新的 Executor”，而是把 LangGraph 真正放到三个专家上面的编排层，让它负责：

```text
任务进入图
→ 判断哪些任务当前可执行
→ 路由到对应专家节点
→ 收集每个专家结果
→ 根据依赖继续下一批任务
→ 所有任务结束
→ 输出 TaskResult[]
```

最终结构按下面这条主流程实现：

```text
真实闲鱼消息
    ↓
Worker
    ↓
/chat
    ↓
ChatService
    ↓
SessionManager.load()
    ↓
Planner
    ├─ 语义理解
    ├─ 识别 1～N 个独立诉求
    └─ 生成 Task DAG
    ↓
ItemContextResolver
    ↓
┌──────────── LangGraph 专家工作流 ────────────┐
│                                               │
│   Graph State                                 │
│      ↓                                        │
│   找出当前可执行任务                           │
│      ↓                                        │
│   根据 task_type / execution_mode 路由         │
│      ├─ Product / Technical Node              │
│      │      → ProductAgent                    │
│      │      → 商品事实 / RAG / 已有联网搜索    │
│      │                                        │
│      ├─ Price Node                            │
│      │      → PriceAgent                      │
│      │      → 标价 / 底价 / 运费 / 议价规则    │
│      │                                        │
│      ├─ Service Node                          │
│      │      → ServiceAgent                    │
│      │      → 售后 / 发货 / 店铺规则 / RAG     │
│      │                                        │
│      └─ Existing Capability Node              │
│             → order / general_rag 等已有能力   │
│                                               │
│   每个节点返回 TaskResult                     │
│      ↓                                        │
│   写入 results_by_id                          │
│      ↓                                        │
│   是否还有未完成任务？                         │
│      ├─ 有 → 回到“找出当前可执行任务”          │
│      └─ 无 → END                              │
└───────────────────────────────────────────────┘
    ↓
ResultMerger
    ↓
SessionManager.save_turn()
    ↓
Worker 只发送一次最终回答
```

这就是本项目接入 LangGraph 的目标形态。

### B1：Graph State

LangGraph 需要一个本轮共享状态。建议至少包含：

```text
run_id
message
context
tasks
pending_task_ids
ready_task_ids
active_task_ids
results_by_id
precomputed_responses
deadline
trace
```

含义：

- `tasks`：Planner 已经生成并校验好的 Task DAG，图内不再重新理解买家原话；
- `pending_task_ids`：还没有处理的任务；
- `ready_task_ids`：依赖已经满足、当前可以执行的任务；
- `results_by_id`：每个 task_id 的执行结果；
- `precomputed_responses`：商品缺失、冲突等在进入图前已经得到的结果；
- `trace`：记录节点、专家、工具、耗时和错误；
- `deadline`：控制整轮最大执行时间。

Graph State 只管理“当前这一轮的工作状态”，不替代现有 SessionManager 的跨轮会话记忆。

### B2：Graph 节点

第一版至少建立以下节点：

```text
prepare_ready_tasks
product_node
price_node
service_node
existing_capability_node
record_results
finish_or_continue
```

#### prepare_ready_tasks

职责：

```text
查看 pending tasks
↓
检查 depends_on_task_ids
↓
找出当前可以执行的任务
```

如果依赖失败：

```text
不要执行下游业务任务
→ 写入 dependency_unresolved
```

如果任务图有循环：

```text
→ dependency_graph_invalid
→ 结束相关任务
```

#### product_node

只处理 `product` / 技术商品类任务。

内部复用：

```text
ProductAgent
ItemFactResponder
KnowledgeService
已有 RAG
已有 Tavily / 联网搜索能力
```

LangGraph 不重新实现商品搜索。

例如：

```text
“Canon FTb 用什么电池？”
→ product_node
→ ProductAgent
→ 本地知识不足
→ 按第二部分既有规则决定是否联网
→ Tavily
→ 返回 TaskResult
```

#### price_node

只处理价格任务。

继续复用当前 `PriceAgent` 的确定性规则：

```text
标价
最低价
买家报价
包邮 / 不包邮
授权优惠
```

LangGraph 负责决定“什么时候执行价格任务”，不负责替 PriceAgent 决定底价。

#### service_node

处理：

```text
售后
发货
运费规则
交易规则
店铺规则
其他服务类问题
```

继续调用现有 `ServiceAgent`、KnowledgeService 和 RAG。

例如：

```text
“如果镜头裂了能退吗？”
→ Planner 只产生一个 service 任务
→ LangGraph 路由到 service_node
→ ServiceAgent
```

不会因为图里存在 Product Node 就自动再调用商品专家。

#### existing_capability_node

用于承接当前仍存在、但不属于三个核心专家的能力，例如：

```text
order
general_rag
missing_order_id
unsupported_action
```

第一版不因为引入 LangGraph 就删除这些现有能力。

### B3：Graph 的任务选择逻辑

LangGraph 不应该每一轮都把三个专家全部执行一次。

正确逻辑：

```text
Task DAG
↓
只选择当前真正存在的任务
↓
只进入对应节点
```

例如：

#### 单任务

```text
买家：最低多少？
Task[] = [price]
Graph：
START → price_node → END
```

#### 多任务

```text
买家：
这台修过没？最低多少？今天能发吗？

Task[]：
product
price
service

Graph：
START
→ prepare_ready_tasks
→ product / price / service
→ record_results
→ END
```

第一版可以先串行执行，确保结果稳定；第二阶段再对“没有依赖关系”的任务启用 LangGraph 并行分支。

#### 有依赖的任务

```text
买家：
如果没修过，1900我就买
```

可能形成：

```text
q1 product：核验维修事实
q2 price：判断1900是否可接受
q2 depends_on q1
```

Graph：

```text
START
→ q1 Product Node
→ 检查 q1 的结构化事实
→ 条件成立
   → q2 Price Node
→ 条件不成立 / unknown
   → q2 不确认成交
→ END
```

注意：`q1 status=answered` 不等于“没修过”这个条件成立。Graph 必须依据结构化事实或显式前置条件判断。

### B4：结果收集

每个节点都必须返回统一 `TaskResult`。

Graph 只负责收集：

```text
results_by_id = {
    "q1": TaskResult(...),
    "q2": TaskResult(...),
    ...
}
```

最终输出时：

```text
按 Planner 原来的诉求顺序
→ list[TaskResult]
→ ResultMerger
```

不要让：

```text
ProductAgent
PriceAgent
ServiceAgent
```

分别向闲鱼发消息。

每轮只允许：

```text
Graph 完成
→ ResultMerger 合并一次
→ Worker 发送一次
```

### B5：与已有代码的关系

为降低改造范围，可以让 LangGraph 工作流对外仍然提供与当前执行边界相近的调用形式，例如：

```python
results = await expert_graph.run(
    tasks=tasks,
    message=message,
    context=context,
    precomputed_responses=precomputed,
)
```

这里“保持调用边界”只是方便接入现有 ChatService，不代表 LangGraph 的目标是模仿旧 TaskExecutor。

真正的职责变化是：

```text
旧：
Python for-loop / ExpertOrchestrator 手工调度

新：
LangGraph State + Node + Edge
负责整个 Task DAG 的调度
```

原 `TaskExecutor` 中仍有价值的单任务适配、`to_expert_task()`、商品加载、结果转换等代码可以抽出来复用；旧的整轮调度循环在 Graph 稳定后退出主链。

### B6：第一版不要同时增加过多能力

第一版只实现：

```text
Task DAG 输入
节点路由
任务依赖
专家执行
结果收集
错误记录
一次最终输出
```

先不要同时加入：

```text
模型反思
自动自我修改计划
无限 retry
Graph 持久化记忆
自动人工审批
专家之间自由聊天
```

这些不是当前接入 LangGraph 的必要条件。

### B7：联网搜索保持为专家的 Tool 能力

第二部分已经完成的联网搜索继续放在需要它的专家内部。

正确关系：

```text
LangGraph
→ Product Node
→ ProductAgent
→ 判断需要公网知识
→ Tavily
```

而不是：

```text
LangGraph 先 Tavily 搜一次
→ ProductAgent 再搜一次
```

LangGraph 负责“谁执行、什么时候执行”；Tavily 负责“去互联网找资料”。

### B8：B阶段验收

至少验证：

1. 只有 `price` 任务时，只执行 Price Node；
2. `product + price + service` 三任务时，三个对应节点各执行一次；
3. 同一专家两个不同任务时，两项都执行，不能按专家名去重；
4. 有依赖任务时，依赖满足后才执行下游；
5. 依赖失败或条件不成立时，不误执行成交任务；
6. ProductAgent 的联网搜索仍可正常使用，不能因接入 Graph 被绕过；
7. Graph 内部失败不会导致已完成的无关任务丢失；
8. ResultMerger 只执行一次；
9. SessionManager 只保存一轮；
10. Worker 只生成一个最终发送候选。

完成 B 阶段后，系统应具备：

```text
Planner 决定“做什么”
LangGraph 决定“怎么执行”
专家决定“业务答案是什么”
ResultMerger 决定“怎么合并”
Worker 决定“怎么发送”
```

这五层职责不能互相重复。
