# 新旧链路问题与修复方案

## 一、检查范围

本次检查围绕 `/chat` 主入口、统一任务链路、闲鱼专家链路、订单链路以及旧的兼容逻辑展开。

当前主链路为：

```text
POST /chat
→ ChatService.chat_async()
→ SessionManager
→ Planner.plan()
→ ItemContextResolver（需要商品时）
→ TaskExecutor
→ 对应 TaskHandler
→ ResultMerger
→ SessionManager.save_turn()
→ API Response
```

总体判断：新链路已经接通，但目前仍然是“统一链路包裹旧业务链路”的过渡状态，存在重复规划、重复执行和旧逻辑未清理的问题。

---

## 二、需要修复的问题

### 1. Planner 和 XianyuExpertOrchestrator 重复规划

**涉及文件：**

- `app/services/planner.py`
- `app/services/task_executor.py`
- `app/services/xianyu/expert_orchestrator.py`

当前调用关系：

```text
Planner.plan()
→ build_expert_plan()

TaskExecutor
→ XianyuExpertTaskHandler.handle()
→ XianyuExpertOrchestrator.handle()
→ build_expert_plan()
```

外层 Planner 已经把用户问题拆成多个 Task，但执行每个 Task 时，专家编排器又重新规划了一次。

**影响：**

- 同一个问题可能被重复调用模型进行规划；
- 多问题场景可能重复执行专家任务；
- 知识库检索和模型生成次数增加；
- 响应时间和模型成本增加；
- 外层 Task 与内层 ExpertTask 可能出现不一致；
- 结果可能重复，最终只能依赖 `ResultMerger` 去重。

这是当前最优先需要修复的问题。

---

### 2. 项目中存在两套任务模型

当前同时存在：

- `app.services.chat_contracts.Task`
- `app.services.xianyu.experts.contracts.ExpertTask`

外层统一 Planner 先生成 `Task`，之后专家编排器又生成 `ExpertTask`。

**影响：**

- 任务 ID 需要在两层之间转换；
- 任务依赖关系可能丢失；
- `query_target` 等信息需要通过 metadata 传递；
- 外层和内层可能对同一问题拆出不同数量的任务；
- 后续维护时容易出现执行结果与计划不一致。

---

### 3. `OrderChatHandler.combined()` 已经成为旧链路

**涉及文件：**

- `app/services/order_chat_handler.py`
- `app/services/planner.py`

当前 Planner 已经把 `rag_mcp` 拆成两个普通任务：

```text
order Task
service Task
```

并没有再调用 `OrderChatHandler.combined()`。

**影响：**

- 旧的 combined 逻辑继续占用维护成本；
- `generate_combined()` 仍被保留，容易让后续开发者误以为它仍是主链路；
- 新旧订单与 RAG 合并方式可能产生行为差异。

---

### 4. `XianyuKnowledgeResponder.handle_item()` 与新专家链路职责重叠

**涉及文件：**

- `app/services/xianyu/knowledge_responder.py`
- `app/services/xianyu/item_fact_responder.py`
- `app/services/xianyu/expert_orchestrator.py`

旧链路的 `handle_item()` 自己完成：

- 商品事实判断；
- 知识库检索；
- 模型生成；
- 未知信息处理；
- handoff 处理。

新链路则由以下组件协作完成：

```text
ItemFactResponder
→ Expert Agents
→ XianyuKnowledgeResponder.prepare_evidence()
→ XianyuExpertOrchestrator
```

**影响：**

- 相同业务规则在新旧路径各维护一份；
- 修复一个事实判断问题时，另一条链路可能仍然存在旧行为；
- 测试覆盖容易分散；
- 后续无法明确哪条路径才是正式实现。

---

### 5. 事实回答逻辑存在重复

**涉及文件：**

- `app/services/xianyu/item_fact_responder.py`

`answer_intent()` 和 `answer_plan()` 都包含大量商品字段判断，例如：

- 价格；
- 在售状态；
- 成色；
- 配件；
- 维修记录；
- 发货信息；
- 售后规则。

**影响：**

同一个字段在单问题和多问题场景下可能使用不同的判断逻辑，导致回答格式或缺失字段处理不一致。

---

### 6. 多处重复处理响应状态

以下字段在多个模块中分别解释：

```text
action
can_answer
answer
reason
sources
```

涉及模块包括：

- `app/services/xianyu/responses.py`
- `app/services/task_executor.py`
- `app/services/xianyu/expert_orchestrator.py`
- `app/channels/xianyu/action_mapper.py`
- `app/api/chat.py`

**影响：**

不同模块可能对 `clarify`、`handoff`、`can_answer=False` 的含义解释不一致，导致 API、任务执行器和闲鱼渠道收到不同结果。

---

## 三、建议的修复方案

## 1. 让 Planner 成为唯一规划入口

建议调整为：

```text
Planner
→ 生成完整 Task 列表
→ TaskExecutor 按 Task 执行
→ Expert Agent 只执行传入的任务
→ ResultMerger 合并结果
```

具体做法：

1. 在 `XianyuExpertOrchestrator` 中增加只执行任务的方法，例如：

   ```python
   async def execute_tasks(
       self,
       tasks: Sequence[ExpertTask],
       context: ExpertContext,
   ) -> list[ExpertResult]:
       ...
   ```

2. 将当前 `handle()` 拆成两部分：

   - `build_plan()`：只负责规划；
   - `execute_tasks()`：只负责执行。

3. `XianyuExpertTaskHandler` 不再调用 `handle()` 重新规划，而是把 Planner 生成的任务转换成专家任务后直接执行。

4. 保留 `handle()` 作为兼容接口，但正式主链路不再调用它。

---

## 2. 逐步统一 Task 和 ExpertTask

建议短期内不强行一次性删除两套类型，而是先明确职责：

- `Task`：统一业务层任务，负责路由和执行边界；
- `ExpertTask`：专家内部任务，负责专家参数和专家依赖。

外层 Task 至少应显式保存：

- `task_id`；
- `task_type`；
- `query`；
- `query_target`；
- `depends_on_task_ids`；
- `execution_mode`。

然后增加一个明确的转换函数，例如：

```python
def to_expert_task(task: Task) -> ExpertTask:
    ...
```

不要继续依赖大量 metadata 隐式传递关键业务信息。

长期来看，如果两种任务模型字段和生命周期已经完全一致，可以合并为一种任务模型。

---

## 3. 清理 `OrderChatHandler.combined()`

建议按以下顺序处理：

1. 全项目搜索 `combined(` 和 `generate_combined(` 的调用；
2. 确认正式入口已经全部走 `order Task + service Task`；
3. 给旧方法增加 deprecated 注释；
4. 补充新链路的订单 + 知识问题测试；
5. 删除 `OrderChatHandler.combined()`；
6. 如果 `generate_combined()` 没有其他调用，再一并删除。

删除前需要确认外部脚本、旧测试和渠道 worker 没有直接调用这些方法。

---

## 4. 将 `handle_item()` 降级为兼容层并最终删除

建议不要立即删除 `handle_item()`，而是分阶段处理：

### 第一阶段

- 搜索全项目对 `handle_item()` 的调用；
- 标记它为 legacy；
- 新代码禁止继续调用；
- 为新专家链路补齐原有测试场景。

### 第二阶段

将旧方法改成兼容适配器，只调用新组件：

```text
handle_item()
→ ItemFactResponder
→ prepare_evidence()
→ ExpertOrchestrator
```

不要让它继续保留一套独立的事实判断和生成逻辑。

### 第三阶段

当确认没有外部依赖后，删除旧方法及其专属辅助函数。

---

## 5. 抽取统一的事实字段回答器

建议从 `ItemFactResponder` 中抽取字段级处理函数，例如：

```python
answer_price(item)
answer_sale_status(item)
answer_condition(item)
answer_history(item)
answer_accessories(item)
answer_shipping(item)
answer_after_sale(item)
```

然后：

- `answer_intent()` 负责单问题调用字段回答器；
- `answer_plan()` 负责遍历多个字段并组合结果；
- 所有字段缺失、冲突和未知状态由字段回答器统一处理。

这样可以避免单问题和多问题使用两套业务判断。

---

## 6. 统一内部响应契约

建议定义统一的内部响应对象或明确的 `TaskResult` 转换规则，至少包含：

```python
status: answered | clarify | unavailable | handoff
answer: str
reason: str | None
sources: list[Source]
metadata: dict
```

推荐链路：

```text
业务 Handler
→ TaskResult
→ ResultMerger
→ API Response
→ Channel Action
```

具体要求：

- Handler 不直接依赖渠道动作名称；
- `clarify`、`handoff`、`unavailable` 在内部统一定义；
- `action_mapper` 只负责把 API 响应映射为渠道动作；
- `reason` 不应在 API 层被意外丢失；
- 所有失败结果都必须保留稳定的 reason code。

---

## 四、推荐实施顺序

### 第一优先级

1. 修复 Planner 与 ExpertOrchestrator 的重复规划；
2. 增加复杂多问题场景的调用次数测试；
3. 确认每个用户问题只规划一次、每个专家任务只执行一次。

### 第二优先级

1. 明确 `Task` 与 `ExpertTask` 的转换边界；
2. 减少 metadata 中的隐式状态；
3. 统一任务 ID 和依赖关系。

### 第三优先级

1. 清理 `OrderChatHandler.combined()`；
2. 将 `handle_item()` 改为兼容适配器；
3. 删除确认无调用的旧代码。

### 第四优先级

1. 抽取商品字段回答器；
2. 统一 `TaskResult` 和 API/channel 响应转换；
3. 删除重复的状态判断和错误处理。

---

## 五、修复后的目标链路

```text
POST /chat
→ ChatService
→ SessionManager
→ Planner（唯一规划入口）
→ ItemContextResolver
→ TaskExecutor
   ├─ OrderTaskHandler → MCP
   ├─ ServiceTaskHandler → 普通 RAG / 闲鱼知识库
   └─ XianyuExpertTaskHandler
       → 已规划的 ExpertTask
       → ProductAgent / PriceAgent / ServiceAgent
→ ResultMerger
→ 统一 API Response
→ Channel Action Mapper
```

修复完成后应满足：

- 一个用户请求只进行一次统一规划；
- 一个任务只执行一次；
- 新链路不再重新进入旧的整段问答流程；
- 旧链路只作为短期兼容层存在；
- 事实回答、知识检索和响应状态都有唯一实现入口；
- API、任务执行器和渠道对回答状态的解释一致。
