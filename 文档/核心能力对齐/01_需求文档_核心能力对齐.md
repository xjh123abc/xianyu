## 一、目标与范围

**目标：复用现有主链路，尽快补齐目标项目已经具备的核心客服能力，不重做项目。**

要对齐的是使用能力：能连续议价，能带上下文回答，能查询型号技术资料，能读取商品介绍，能在人工与自动回复之间衔接，并能处理常见运行故障。不是复制目标项目的类名，也不是承诺两者每一句回答相同。

本轮不做管理后台、多平台接入、真实订单退款或改价、市场比价、情绪分析、换向量数据库、另建多 Agent 框架。目标项目 README 中的 Web 管理界面、市场比价等仍列为规划内容，不作为本轮前置条件。[B1]

## 三、实现顺序与需求对应关系

下表中的 T1—T5 是本次新计划的编号，不是以前文档的 S1—S10。

| 顺序 | 本次交付 | 对应需求 | 完成后能看到什么 |
|---|---|---|---|
| **第一步 T1** | 连续议价＋交易记忆 | **R01、R02** | 能接着上一轮谈价，记住报价和运费，不会越谈越乱。 |
| **第二步 T2** | 技术专家联网查证 | **R03** | 本地缺型号资料时能查可信来源，给出有依据的技术回答。 |
| **第三步 T3** | 自然对话＋语义兜底＋完整回答 | **R04** | 不只识别固定关键词，问候、追问、多问题都能正确处理。 |

**开发从 T1 开始。每一步完成对应验收就进入下一步，不等待所有回答都润色到“完美”。不再增加一轮架构设计作为前置任务。**

## 四、功能需求

### R01：连续会话与交易记忆

**要实现：**同一买家针对同一商品的后续问题，能沿用已经明确的报价和交易条件。

记住当前商品、已采用的让价档位、上一报价、买家出价、包邮条件、报价状态和适用的价格规则版本。复用现有会话数据库，不另建一套 Memory。

“多少钱”不消耗让价档位；“刚才那个价”“那不包邮呢”“就按这个来”必须结合前文理解。商品切换时，在本轮执行前就隔离旧商品交易状态，不能等回答完再清理。不同买家、不同账号不能串用报价。

报价状态至少区分“已生成”“已提交发送”“平台确认”“发送失败或结果不确定”。本地提交不是买家已收到。重复处理同一条平台消息，不得再次推进让价。

**验收：**连续三轮追问能引用正确金额；切换商品后不沿用旧报价；重启后在有效期内保留状态；发送失败不把未发送报价当成已完成协商。

### R02：受授权约束的连续议价

**要实现：**从单轮“报最低价”，升级为可连续协商的价格专家。

卖家按商品配置让价档位和底线。价格由代码计算，模型只能组织语言，不能创造优惠、赠品或包邮承诺。内部底价配置不得进入买家可见的商品信息、引用或错误原因。

买家出价低于授权范围时，明确拒绝或重申当前报价，不应回答“资料不足”。已经没有让价空间时，说明维持当前价格；不能因为继续追问就累计无限降价。买家出价在授权范围内被接受时，不主动报出比买家出价更低的金额。

“包邮”和“不包邮”使用各自授权条件；询问两种方案不代表买家选择了其中一种。买家确认当前报价时，重复价格和运费条件。未接入真实改价、下单工具时，不得说“已改价”“订单已创建”。

示例仅用于测试，不是当前真实商品的授权价格：

| 买家消息 | 预期行为 |
|---|---|
| 能便宜一点吗？ | 按第一档给出当前可报价，如 1490元包邮。 |
| 再少一点呢？ | 在授权范围内进入下一档，如 1460 元包邮。 |
| 1300 可以吗？ | 若低于授权底线，明确拒绝，不再无理由让价。 |
| 就按你刚才说的价格。 | 确认 1460元包邮，不声称已实际改价。 |

**验收：**金额和档位与测试配置一致；低价拒绝是正常业务回答；重复消息、运费切换、已售商品、失效规则均不能导致越权报价。

### R03：技术专家联网查证

**要实现：**对“型号功能、操作方法、兼容性”等问题，在本地证据不足时查询可信资料，再由现有模型回答。

处理顺序为：确认型号 → 查本地资料或有效缓存 → 必要时联网 → 核对型号与内容 → 回答并保留来源。联网能力必须在本轮实现，不能仅用“以后补知识库”代替。

只允许联网查询型号知识。某件实物是否摔过、维修过、配件是否齐全，只能依据该实物资料；店铺售后承诺只能依据店铺规则。不得把网上的型号介绍当作这件二手商品的检测结果。

结果必须包含可追溯的来源和获取时间。搜索无结果、型号不符、来源冲突、接口失败时，保留其他已知答案，仅对受影响的问题说明无法确认。

**验收：**本地有证据时不联网；本地没有时实际调用搜索；错型号资料不能被采用；搜索失败不导致其他子问题丢失；未配置搜索凭证时清楚记录“尚未启用”，不能标记真实搜索验收通过。

### R04：自然对话、语义兜底与多问题完整回答

**要实现：**保留规则优先的效率，同时处理规则未覆盖的口语表达，不依靠无限增加关键词。

未命中或语义不明确时，由现有模型进行一次完整消息的任务规划，输出经过校验的任务；不要让每个专家再次分类。模型只判断要处理的问题，不决定价格权限或商品事实。

问候、感谢、正常收尾可直接自然回复，不必强行检索售后文档。“还有吗”“能用不”等涉及商品情况的口语，不能被当成无关闲聊。系统事件和明确无需回复的消息不发送内容，也不发送目标项目使用的内部占位符 `-`。

一条消息同时问成色、价格、运费和售后时，分别完成对应任务，再合成一条清楚的回复。某项资料不足不能覆盖其他已经成功的答案。价格、时间、配件和交易条件在合并时不得被改写。

保留当前约定：缺少商品或商品冲突需要澄清；证据不足可说明无法确认；不因单次不会回答而自动永久切为 HUMAN。

**验收：**问候不查知识库；口语改写仍能路由；多问题没有漏项；纯无需回复不发消息；混合消息中的有效问题仍然回答；模型规划最多调用一次且失败时保留规则识别出的任务。

### R05：平台商品资料读取与更新

**要实现：**像目标项目一样读取平台商品介绍，减少手工维护，但继续保留当前商品绑定和归属检查。

只同步已经由卖家确认绑定的商品。读取平台标题、介绍、标价、售卖状态等公开信息，保存来源与更新时间；启动时或缓存过期时更新，不为每条买家消息重复请求平台。

同步资料与卖家人工维护的实物检测记录、议价授权、店铺政策分开保存。不得根据介绍没有提到某种损坏就认定没有损坏；不得从买家发来的链接自动创建可信商品。

平台标价、在售状态与本地记录冲突时，不静默沿用旧规则议价。已售商品停止谈价。同步失败时不删除已有资料；过期或冲突的价格不能被当作最新授权报价。

**验收：**已绑定商品能读到实际介绍；修改介绍后刷新可见；私有议价规则不被覆盖；无归属或未绑定商品不自动接入；同步失败、售出、价格变更有明确处理。

### R06：人工接管与恢复后的上下文衔接

**要实现：**沿用现有 takeover/release，而不是另建一套人工模式；补齐人工阶段的消息记录。

卖家接管后 AI 不抢答。人工阶段的买家消息、可确认的卖家人工回复，进入对应会话历史。恢复自动后，能理解“按刚才说的”“他刚刚已经回答过了”等后续内容。

机器人自己的发送回显不得当作新的人工回复。人工消息可作为对话历史，但不得自动改写永久底价或售后规则；涉及新的交易价格，必须保留人工来源，未通过授权核对时不能据此继续自动让价。

可增加明确的卖家控制词作为现有控制功能的快捷入口，默认不用容易误触的单个句号。控制词必须验证发送者身份，买家不能用相同文字切换卖家控制状态。

**验收：**接管期间零自动抢答；恢复后记得人工交代的信息；买家伪造控制词无效；发送回显不重复入库；生成过程中发生接管，旧回复仍被阻止发送。

### R07：稳定值守与真实链路验收

**要实现：**接收消息、心跳和令牌维护不被模型调用阻塞；正常断线有受限重连；需要人工重新登录时明确暂停并告警。

心跳要确认有效回应，不能仅记录“发送成功”。普通网络故障与登录失效、人机验证分开处理：前者可退避重试，后者停止无效重试，提示卖家处理，不尝试绕过验证。

重连或进程恢复不得清空会话记忆、去重记录，也不得擅自解除卖家的暂停或人工接管。已提交或发送结果不确定的消息，不盲目重发。

复用现有验收脚本和报告门槛，增加本轮多轮会话、联网搜索、同步、人工衔接及恢复测试。单元测试、真实模型、真实渠道结果分开记录。平台确认或买家端实际可见，才作为真实送达证据。

**验收：**正常消息能完成接收→规划→回答→发送；慢模型不阻塞接收与心跳；断线后按策略恢复；验证失效只告警和暂停；重连不重复发消息、不覆盖 HUMAN；报告写明实际运行时长，不能把短时测试称作“已证明 24 小时无人值守”。

## 五、整体完成标准

T1—T5 分别通过对应场景，既有回归测试无新增失败；所有未执行的真实模型、搜索、渠道测试必须标记 `not_run` 或 `blocked`，不得直接填 `passed`。

最终交付为：核心功能代码、必要配置示例、自动化测试、真实验收记录和简短启动说明。没有真实改价、退款或订单写入能力，也不影响本轮范围内的客服能力对齐；但不能声称这些能力已经具备。
