## 一、先确认开发主线

当前真正的执行入口已经是：

```text
闲鱼消息
  → XianyuStage3Worker
  → to_chat_message / ChatApiClient
  → POST /chat
  → ChatService
  → SessionManager.load
  → Planner.plan
  → TaskExecutor.execute
  → 现有商品 / 价格 / 客服专家
  → ResultMerger.merge
  → SessionManager.save_turn
  → action_mapper
  → 原发送器
```

本轮在这条主线上补功能。不能只修改旧 `XianyuExpertOrchestrator.handle()` 的规划逻辑，因为新 `XianyuExpertTaskHandler` 是把规划好的任务交给 `execute_tasks()`，不会重新进入旧规划入口。[C1]

两个数据库继续分工：`SESSION_DATABASE_PATH` 保存对话和交易状态，`XIANYU_CHANNEL_DATABASE_PATH` 保存控制状态、商品绑定、去重和发送记录。不要为了本轮功能合并两库，也不要让 API、运行器、CLI 指向不同的渠道库。[C7]

| 修改 | `app/services/session_manager.py` | 同步扩展 `_NEGOTIATION_KEYS` 和字段校验；通过现有存储持久化，不另建 Memory。 |

新增状态建议如下，沿用旧字段名，补齐明确含义：

```json
{
  "item_id": "TEST_NEG_001",
  "round": 0,
  "last_ai_offer": null,
  "last_buyer_offer": null,
  "shipping_condition": null,
  "policy_version": null,
  "offer_status": "none",
  "pending_offer": null,
  "last_committed_turn_id": null
}
```

`round` 在本方案中表示已采用的让价档位，不是所有聊天消息的数量。`last_ai_offer/last_buyer_offer` 使用整数分或 null；旧记录如不满足此契约，应清理相应交易状态而不是猜测金额单位。`offer_status` 明确区分 generated、submitted、confirmed、unknown 等状态。

本轮生成状态和已提交报价必须分开；不能在模型刚生成时，就覆盖上一轮已提交给平台的报价。商品切换、价格规则变更、售出和状态到期时使旧提案失效。未过期且适用条件相同的已提交报价，应作为续谈依据。

### 1.2 增加服务端私有价格策略（R02）

**新增：**`app/services/negotiation_policy.py`、`data/xianyu/negotiation_policies.json`。价格策略独立读取，不塞进会被 `/chat.item_info` 或商品 MCP 返回的公开 `facts`。

下面仅是新增测试商品的配置示例，不能直接改成真实商品授权：

```json
{
  "TEST_NEG_001": {
    "version": 1,
    "listed_price_cents": 150000,
    "seller_pays": {
      "offers_cents": [149000, 148000, 147000],
      "floor_cents": 147000
    },
    "buyer_pays": {
      "offers_cents": [148000, 147000, 146000],
      "floor_cents": 146000
    }
  }
}
```

加载时校验：整数且非负、档位不递增、所有档位不低于对应底线、策略商品与当前商品一致。运费承担条件必须有卖家授权；没有配置的条件不能自行补出价格。

新增策略优先生效；没有新策略的商品继续兼容原有明确授权规则，不能自动赋予多轮优惠。不要把原先“固定最多小刀”的一句文字擅自解释成若干额外优惠档位。新旧规则存在冲突时停止新增优惠并记录原因，保留可确认的商品回答。

### 1.3 改造 PriceAgent 的决策，不让模型决定金额（R02）

修改 `app/services/xianyu/experts/price_agent.py`，将核心计算组织为“标准化请求＋价格策略＋本轮前状态 → 决策＋状态提案”。沿用原价格格式化、金额校验和售卖状态检查。

| 输入情况 | 必须执行的规则 |
|---|---|
| 询问标价 | 报实际标价，不推进档位。 |
| 首次请求优惠 | 取第一档授权报价；使用“当前可以…”而不是把中间档谎称绝对最低价。 |
| 继续要求优惠 | 同一运费条件下进入下一档；到最后一档后维持，不无限累减。 |
| 买家报价低于底线 | 正常拒绝，保持当前报价；这是 `answered`，不是证据不足。 |
| 买家报价可接受 | 按买家报价确认，不给出比其报价更低的数额；附适用运费条件。 |
| 同时比较包邮/不包邮 | 分别列方案，不修改买家选定条件、不因两个任务推进两次档位。 |
| 改选运费条件 | 使用新条件下的绝对价格档位，不能把邮费折扣重复叠加。 |
| 接受上次报价 | 核对商品、规则版本、报价状态与运费条件后确认，不声称已实际改价。 |
| 商品已售或授权失效 | 不继续谈价；明确当前可确认状态。 |

同一买家消息可以有多个价格子任务，但只能产生一次一致的状态更新。同条件重复询价不额外让价。补齐“就这个价”等 `query_target` 时，在 `Planner` 和 `VALID_QUERY_TARGETS` 同步扩展，不让价格专家私下再做一轮模型分类。

### 1.4 把价格提案接到发送结果（R01、R02）

当前 `/chat` 的状态保存发生在渠道发送之前；worker 已有 `LOCAL_SUBMITTED/CONFIRMED/FAILED/UNKNOWN` 等发送记录。因此不能把“HTTP 返回了报价”直接解释成“买家已经收到报价”。[C1][C6]

为避免两套数据库相互替代，本轮只增加一条薄的内部回执通道：

| 操作 | 位置 | 内容 |
|---|---|---|
| 修改 | `app/services/chat_contracts.py`、`app/api/chat.py`、`app/channels/xianyu/adapter.py`、`chat_client.py` | 可选传递稳定 `turn_id`，由渠道以账号＋平台消息标识生成；旧请求仍兼容。真实身份由可信适配器提供，不使用 `ChatService` 中的 seller/buyer 占位值做隔离。 |
| 修改 | `ChatService`、`SessionManager` | 以 turn_id 保存价格提案、适用商品/策略版本；同一消息重试返回同一提案，不重新让价。 |
| 新增 | `app/api/chat_delivery.py`，并在 `app/main.py` 注册 | 内部回执接口 `POST /internal/chat/delivery`；携带 turn_id、proposal_id、发送状态，不接受外部指定金额。 |
| 修改 | `app/channels/xianyu/stage3_worker.py`、`chat_client.py` | 调用原发送器后，将已有发送状态回报；失败的回执可重试，不能因此重新发送买家消息。 |

内部接口使用配置令牌鉴权，默认仅供本机或受保护网络访问，令牌不能写日志。先核对提案归属、商品、规则版本和控制版本；已失效提案不得提交。

`LOCAL_SUBMITTED` 可把提案记为“已提交的本轮报价”并幂等推进一次档位，但不标记已送达；只有平台确认才记 confirmed。FAILED 不推进；UNKNOWN 保留待核对状态，不盲目重发或继续自动让价。回执重试和下一轮请求应在同一会话锁下协调，避免后续报价先于前一轮回执落库。

价格状态与相关会话更新在会话库中使用事务提交；发送记录仍留在渠道库，不声称两库与外部平台存在一个全局事务。

直接 `/chat` 测试没有实际发送时，报价保留为草稿。多轮自动化测试要显式模拟回执，并标注是模拟发送，不伪装成真实渠道成功。

### 1.5 T1 验收

在 `tests/` 中增加议价闭环用例：正常三轮、低于底线、接受买家出价、双运费比较、重复消息、切换商品、重启读取、发送失败/未知、过期回执、底价不出现在公开响应。

## 三、T2：技术专家联网查证

**对应需求：R03。不是再创建一套技术 Agent，而是给现有 ProductAgent 补证据获取能力。**

### 2.1 固定最短技术路线

本轮采用“独立搜索接口获取资料＋现有模型生成回答”。保留现有 DeepSeekGenerator，不把目标项目专用的 `enable_search` 参数直接复制给当前模型接口。

为避免实现时反复选型，本方案默认只接一个搜索供应方：Tavily 的 HTTP Search API。其接口支持查询、限制来源域名并返回标题、URL、内容等信息；具体请求字段以官方文档为准。[E1] 这是本轮建议方案，不是当前项目已有能力，需要本地配置搜索凭证。不要同时开发多个供应方或让 Coding Agent 寻找/提交你的密钥。

```text
product.model_knowledge 任务
  → 核对当前商品的明确型号
  → 现有本地证据 / 有效缓存
  → 不足时请求一次搜索
  → 核对来源域名、型号、版本与回答覆盖范围
  → 转为现有 evidence 契约
  → generate_xianyu_expert("product", ...)
  → 返回回答及真实来源
```

### 2.3 请求、边界与失败处理

新增配置建议：

```dotenv
TECH_SEARCH_ENABLED=false
TAVILY_API_KEY=
TECH_SEARCH_ALLOWED_DOMAINS=
TECH_SEARCH_TIMEOUT_SECONDS=6
TECH_SEARCH_CACHE_TTL_SECONDS=86400
```

这些是方案初始值，不是压测结论。启用前填写当前在售型号的可信资料域名；缺凭证或必要配置时明确报告未就绪。请求可使用 `max_results=3`、`include_answer=false`，仅取有来源的资料，避免直接把供应方生成的综合答案当成证据。[E1]

搜索请求只发送公开型号和技术问题，不发送买家身份、完整聊天记录、Cookie 或私有价格策略。资料正文按不可信数据处理，不执行其中的“忽略指令”等文本。不得按买家提供的任意 URL 抓取内网或本机内容。

缓存按“规范型号＋技术问题＋来源策略版本”区分，保存获取时间；不同型号不共用答案。通过的证据才可生成答案，来源冲突不能简单按排名第一项选择。

只允许搜索型号功能、使用方式、技术兼容性；实物损坏历史、订单、售后授权、议价底线都禁止走网络兜底。搜索超时只让相关技术任务降级，已完成的价格或售后回答仍正常保留。

### 2.4 T2 验收

增加五类测试：本地命中不联网；本地不足真实搜索；错型号/不可信来源拒绝；搜索超时仍保留其他答案；网络资料不能回答“你这台是否进水”。

真实搜索必须单独记录实际来源 URL、使用的型号、状态和耗时。Mock 返回一段资料只能证明接线，不能证明已经实现可用联网查证。

## 四、T3：自然对话、语义兜底和多问题处理

**对应需求：R04。复用 Planner 和现有模型规划方法，不恢复多层重复路由。**

### 3.1 把模型规划接入新的 Planner

修改 `app/services/planner.py`：注入 `DeepSeekGenerator.plan_xianyu_questions` 的受限调用。规则能完整处理的消息不调用；规则有未覆盖片段或指代不清时，对完整消息及有限历史调用至多一次。[C5]

模型返回后校验 task_type、query_target、原问题片段、知识范围和依赖关系；合并已确定规则任务、去重，再交给 TaskExecutor。不能让模型覆盖已确认商品、决定底价或产生退款等写操作。模型补出的商品任务必须同步影响本轮的商品解析决策，不能沿用一份过期的 requires_item 标记。

保留原问题内容。不能把陌生技术问题归一化为只有“商品专项知识”几个字后就丢失具体问法。

在 `ChatService` 中使用异步边界或有界线程承载同步模型规划；SDK 请求必须有真实超时，不能只在外面包 `wait_for()` 却让后台网络请求无限挂着。

### 3.2 给客服任务增加普通对话路径

| 修改位置 | 内容 |
|---|---|
| `app/services/xianyu/experts/contracts.py`、`planner.py` | 明确加入普通对话、无需回复对应的合法目标；沿用 service 任务类型，不新增一整套默认 Agent。 |
| `app/services/xianyu/experts/service_agent.py` | 问候、感谢和收尾先用短模板；需要解释时使用已有模型与历史。涉及事实时仍转对应证据任务。 |
| `app/generation/xianyu_expert_prompt.py`、`deepseek.py` | 补普通客服语言与历史使用规则；不更改代码计算出的金额和交易条件。 |
| `app/services/result_merger.py` | 忽略无需回复的子任务；全部无需回复才输出 `action="ignore"`，混合消息继续保留有效答案。 |
| `app/channels/xianyu/action_mapper.py` | 明确支持 ignore；不把空答复或内部占位符当作发给买家的文字。 |

目标项目使用 `-` 表示无需回复；本项目通过结构化 action 表达，不复制这个占位符到买家端。[B2][B3]

合并继续采用现有确定性方式，不额外加一次“全篇润色模型调用”。每个问题给必要回答即可，不照搬目标项目的极短字数限制而导致多问题漏答。

### 3.3 不破坏已经约定的失败行为

当前合并器已经能保留部分成功答案，应直接扩展而非重写。[C1] 缺商品走 clarify；有商品但证据不足可 reply 说明无法确认；真正系统错误单独记录。不能把这些情况都恢复成自动 HUMAN，也不能把“有答案”仅判断为 `action == reply`。

同样，不恢复已移除的笼统关键词拦截。应该验证事实、来源和交易授权，而不是看到某个售后词语就抹掉整条回答。

### 3.4 T3 验收

至少覆盖：“你好/谢谢”；两种不同口语表达的相同问题；一句含三个以上不同问题；一项未知但其余正常；纯系统事件；“谢谢，最低多少”这种混合表达；模型规划超时。

记录每轮模型规划调用次数，规则命中为 0，兜底最多 1。不能用另一个专家里的分类调用规避计数。

## 五、T4：平台商品同步与人工对话衔接

**对应需求：R05、R06。已有商品绑定和 takeover/release 保留。**

### 4.1 读取已绑定商品的公开资料（R05）

目标 `main.py` 会缓存商品资料并在缺失时调用平台查询；当前运行器已经加载固定版本的 `XianyuApis`，应复用这个接入，而不是再写爬虫或另启目标项目主程序。[B3][C7]

**新增：**`app/channels/xianyu/item_sync.py`；**修改：**`scripts/run_xianyu_stage3.py`、`app/services/item_service.py`。

按以下顺序实施：

1. 从当前渠道库读取已确认商品绑定，得到平台商品 ID 与本地 item_id；对请求的账号/商品归属再校验。
2. 通过现有平台客户端调用 `get_item_info`，只提取明确的标题、介绍、价格和状态，并校验格式。多 SKU 价格不强行压成一个最低价代表具体商品；无法确定对应规格就标记待核对。
3. 把平台快照写入**新增** `data/xianyu/platform_items.json`，保存账号、本地 item_id、平台 ID、来源和同步时间。原 `items.json` 和私有议价策略不被覆盖。使用单写入者和原子替换，失败时保留旧快照。
4. `ItemService` 增加快照加载和文件版本变化检查，将平台资料与人工资料按字段规则合并。后端不需要登录 Cookie，也不在 `/chat` 请求中调用平台网络。
5. 运行器启动或缓存过期时执行同步；对同一商品合并重复同步请求。未绑定的新商品只报告待绑定，不自动授权。

合并规则：标题/介绍保留平台来源；实物检测、维修历史和价格权限保留人工来源；新标价与人工记录或议价策略冲突时标记冲突并停止新增自动优惠；售出优先停止议价。没有提到损坏不等于没有损坏。

### 4.2 在不触发自动回答的情况下记录人工对话（R06）

修改 `stage3_worker.py` 和 `conversation_guard.py`：在仍然保留所有发送保护的前提下，为“人工阶段记录”和“控制消息”建立独立处理分支。

卖家控制词只接受经过身份校验的卖家消息，转调现有 `control.py`/store 的 takeover 或 release；不要由大模型识别一句话后就修改控制状态。快捷入口可配置，现有 CLI 不删除。

新增一个内部事件入口 `POST /internal/chat/events`，与 T1 回执接口使用同一鉴权机制。只接收可信渠道提供的消息标识、角色、会话和内容，调用 SessionManager 追加历史，不执行 Planner、不产生买家答复。对事件标识做幂等检查。

记录人工阶段买家消息和卖家人工回复；先与发送记录匹配，过滤机器人回显与控制词。仅凭“sender 是卖家”不足以认定是人工消息。无法可靠区分的回显不得据此更改交易权限。

人工报价记录来源，可供复述；只有通过当前授权核对的报价才能继续由自动议价流程承接。人工说过的话不能自动成为永久政策。恢复 AUTO 时保留历史，但旧的未提交 AI 报价提案需要重新核对或作废。

### 4.3 T4 验收

商品侧验证：绑定商品导入、介绍刷新、价格变动、售出、获取失败、不覆盖私有字段、跨账号/未绑定商品拒绝。

人工侧验证：接管→买卖双方交流→恢复→买家追问；机器人不抢答、历史不重复；买家伪造控制词无效；生成过程中接管仍使旧候选失效。验证使用同一渠道数据库，不通过换库“恢复”会话。

### 4.4 T4 实现进度（2026-09-26）

本轮已加入第一版实现，尚未完成自动化及真实平台验收：

- 闲鱼监听运行器启动时刷新已绑定商品，并按 `XIANYU_ITEM_SYNC_INTERVAL_SECONDS`（默认 900 秒）定时刷新。快照保存在 `data/xianyu/platform_items.json`，通过临时文件原子替换；仅查询当前账号已绑定商品。接口失败保留旧快照；取消绑定后，下次同步会清理该账号对应快照。
- 客服读取商品时把快照中的标题、描述、标价和可明确识别的在售状态合并进本地商品资料。实物检测、售后规则和议价配置仍来自卖家本地资料。平台标价与本地价格不一致时保留新公开标价并标记价格事实冲突，价格专家暂停报价，需先核对本地议价策略。
- HUMAN 会话中的买家文本和卖家文本通过受 `XIANYU_DELIVERY_TOKEN` 保护的 `POST /internal/chat/events` 追加到现有会话历史；该接口不调用 Planner 或生成回复。渠道消息 ID 用于去重，已发送自动回复的卖家回显会过滤。历史保存在现有 `SESSION_DATABASE_PATH` 对应会话库中。

待完成：补齐 T4 自动化测试与运行验收；用真实已绑定商品确认接口字段、描述刷新和状态识别；验收人工接管→双方交流→恢复后追问的完整链路。未验收前不启用正式自动发送。

## 六、T5：常驻恢复与整链验收

**对应需求：R07，并验证 R01—R06 在真实链路中生效。**

### 5.1 只补现有运行器的必要运行能力

当前运行器在接收循环中 `await worker.process(...)`，会等待整次业务处理；心跳函数定时发包，但这不等于已核实有效回应。单次 WebSocket 异常后退出，也不等于已具备完整自动恢复。[C7]

修改 `scripts/run_xianyu_stage3.py`；代码较长时将连接维护拆入**新增** `app/channels/xianyu/runtime_supervisor.py`，不要修改固定版本目标仓库里的源码。

| 工作 | 实现要求 |
|---|---|
| 接收与处理分开 | 接收/协议应答只做快速解析、控制事件处理和入队；业务消费者调用 worker。队列有容量上限，同会话保持顺序，不无限创建任务。 |
| 心跳核验 | 关联发送标识和有效回应，使用明确截止时间；失效后关闭旧连接并进入恢复流程。不能把任意消息都当成心跳成功。 |
| 令牌与连接恢复 | 对可恢复网络故障使用有上限的退避重试；需要时重新获取令牌并重新注册；同步请求使用真实网络超时。 |
| 登录失效 | 检测到登录无效或人机验证，暂停受影响账号、发送一次有节制的告警，等待卖家重新认证；不无限重试或尝试绕过验证。 |
| 保留人工控制 | 重连不重置数据库。恢复进程不能无条件 enable；已暂停账号仍可监听必要控制事件，但不能自动生成或发送业务回答。 |
| 处理残留状态 | 依据现有发送状态恢复：未发送候选重新核对控制版本；已提交/结果不确定的记录不盲目重发；T1 回执可补报但不重发买家消息。 |
| 整轮耗时 | 从 ChatService 开始建立一份 deadline，传给规划、检索、模型和执行；多个任务共享剩余预算，而不是每个任务重新得到完整超时。 |

本轮不要求把 TaskExecutor 全部并行化。先保证接收与业务互不阻塞、整轮超时有界；不能为了优化延迟重写完整调度系统。

根据当前 Windows 使用环境，补一种本机常驻启动方式及停止/恢复说明即可。启动器不得把 Cookie 或 API key 写入命令行、仓库或普通日志；也不要同时交付 Docker、Kubernetes 和多套云部署作为本轮前置条件。
