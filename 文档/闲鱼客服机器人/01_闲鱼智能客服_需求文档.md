# 闲鱼智能客服改造需求文档

版本：V1.0 规划稿
日期：2026-09-09
主旨：在现有电商 AI 客服上增加闲鱼场景，不另起一套 AI 系统。

> 本文规划的是待实现功能，不代表已经完成改造或实机验收。现有项目情况来自你此前提供的调用链和测试结果；本次已阅读参考项目的 README 与主要源码，但没有审查你本地最新代码，也没有登录闲鱼账号测试。

## 1. 项目目标

把现有客服改造成一个面向单个闲鱼卖家的文本客服：能识别买家正在咨询的商品，依据卖家提供的资料回答问题，记住同一会话的上下文，在卖家授权范围内报价；不能确定或需要卖家决策时，停止自动回复并交给卖家处理。

最终目标链路：

```text
闲鱼买家消息
  → 闲鱼消息接入
  → 现有 ChatService
  → 当前商品信息 / 原有 RAG / 受控议价规则
  → 现有回答生成与可靠性判断
  → 回复买家，或进入人工接管
```

第一版先做好“问答与接管”，不把项目扩展成商品发布、订单履约、营销运营的全套平台。

## 2. 现有基础怎么利用

| 现有能力 | 改造方式 |
| --- | --- |
| FastAPI、`POST /chat`、ChatService | 保留；增加闲鱼场景参数和渠道入口，旧请求继续可用。 |
| 本地 Embedding、Qdrant、BM25、RRF、Rerank | 保留模型和检索算法；增加闲鱼知识域、商品范围过滤。 |
| Context Builder、DeepSeek、Sources | 保留；补充当前商品的公开事实，调整为卖家客服话术。 |
| 回答可靠性与转人工返回 | 保留证据不足判断；把“转人工字段”落实为可持续生效的会话状态。 |
| MCP 及已有订单工具 | 保留现有调用机制；新增只读商品信息工具，原订单工具保留回归测试。 |
| chat_id、多轮对话相关代码 | 优先复用；验证不同买家隔离、同一买家切换商品及三轮追问。 |
| pytest、检索评估程序 | 保留；添加闲鱼样例，不覆盖原评估集。 |

原来讨论过的 Web 页面可以继续利用，但不能据此假设页面已经实现。

### 参考项目的取舍

`XianyuAutoAgent` 的参考价值主要在于消息收发、商品信息获取、上下文关联和人工接管。它的 README 将 RAG 列为规划项；其回答侧采用分类、价格、技术、默认回复等 Agent。[S1][S2][S3]

本项目借鉴它的渠道接入，不引入第二套模型客户端、专家 Agent、会话历史和回答生成器。

## 3. 第一版范围

第一版限定为：一个卖家账号、文本消息、先用三件示例商品联调，再由卖家选择少量真实商品启用。商品资料先人工维护，不以自动抓取和实时同步为前提。

### 3.1 必须实现的需求

| 编号 | 需求 | 用户能看到的结果 |
| --- | --- | --- |
| F01 | 商品明确的问答 | 咨询 A 商品，只使用 A 商品资料和适用的通用规则，不引用 B 商品的成色或配件。 |
| F02 | 连续对话 | 第一轮说明商品，后面问“那有配件吗”“能便宜点吗”，仍知道在问哪件商品。 |
| F03 | 授权范围内的议价 | 按卖家预先设置的可报价格回复，不自行降价，不公开内部底价。 |
| F04 | 闲鱼消息接入 | 能接收买家文字消息，并将经过检查的回复发回原会话；重复推送不重复回复。 |
| F05 | 人工接管 | 卖家接管或系统判断需人工处理后，自动回复停止，直到卖家明确恢复。 |
| F06 | 精简工作台与验收 | 能查看会话、当前商品、回复草稿及接管状态，并通过固定用例验证。 |

### 3.2 第一版明确不做

不做多账号运营、图片和语音理解、商品自动发布、自动改价、自动下单、自动发货、自动退款、市场比价、复杂阶梯议价及完整经营看板。

真实闲鱼订单查询也不列为本版必达能力。参考代码中出现的交易状态通知，不足以证明存在可直接复用的完整订单查询链路；你原来的 `TEST1001` 等测试订单不能作为真实闲鱼订单返回。[S2]

这不是删除 MCP，而是复用 MCP 的工具调用能力，并明确每个工具实际连接的数据源。

## 4. 核心业务要求

### 4.1 商品和知识必须分清楚

公开商品信息包括标题、卖家维护的标价、售卖状态和更新时间；详细成色、瑕疵、配件、使用说明等放入对应商品资料。

发货、运费和售后说明只使用卖家确认过的内容。不能直接把旧电商知识库里的“24 小时发货”等规则当作闲鱼卖家的承诺，也不能把某个卖家的规则写成闲鱼平台统一规定。

金额、售卖状态等易变化字段只保留一个维护来源，避免 JSON 和 Markdown 各写一份、互相矛盾。第一版的人工维护数据属于快照，不得宣称已经实时查询平台库存或订单。

买家没有提供商品线索且会话尚未关联商品时，先询问是哪件商品。对真正不依赖商品的通用问题，可以使用已确认的卖家通用规则回答。

### 4.2 对话记忆必须跟着会话和商品走

不同买家的历史不能混用。同一买家切换到另一件商品后，不能沿用前一件商品的价格、配件和议价结果。

至少验证三轮商品追问。只生成但没有发送的草稿，不能作为“已经对买家说过”的历史。

### 4.3 议价先用简单规则，不让模型决定价格

第一版采用“固定授权报价”：卖家为商品设置是否允许自动议价，以及一个允许自动报出的价格。内部底价只由程序用于检查配置和报价，不能进入知识库、模型提示词、买家回复或公开接口。

例如：标价 500 元，授权可报 480 元，内部底价 450 元。买家连续要求便宜，机器人可以维持 480 元的授权报价，但不能自行报出 470 元，也不能说“卖家底价是 450 元”。以上数字仅为测试示例。

涉及多件打包、附加赠品、未授权包邮或其他附加条件时，交给卖家决定。机器人提供报价不等于已经修改商品页面价格或完成交易。

### 4.4 人工接管必须真正暂停自动回复

出现主动找卖家、订单付款核查、退款争议、资料冲突或无法确认的交易条件时，应进入人工接管；只缺商品编号等可补齐信息时，先澄清。

接管必须保存为会话状态，程序重启后仍有效。只由卖家明确恢复，不照搬定时自动恢复。生成过程中发生接管，待生成回复也不能继续自动发出。

转人工后，工作台必须可见该会话及原因。提示买家的文字不能声称“人工已经接通”或承诺响应时间。卖家通过闲鱼原生聊天界面完成实际人工回复。

### 4.5 接入和发送分开验收

默认关闭闲鱼连接。接入后先使用观察模式：收消息、生成草稿，但不自动发送。只有经过验证并由卖家明确开启，才允许对选定商品自动回复。

发送失败或无法确认发送结果时，要显示失败/待核查状态，不能把“代码执行了发送函数”直接算成买家已收到，也不能盲目重复发送。

## 5. 分阶段成果

以下六个阶段按顺序实施。详细修改步骤见《技术文档》第 5 节。

### 阶段一：确认基础和接入可行性

**需求目标：** 证明现有主链路仍可运行，并尽早确认参考项目的消息接入在当前账号环境下是否可行。

**完成步骤：** ① 只读核对现有代码及已知问题；② 跑旧接口、MCP 和关键测试；③ 在独立验证入口测试授权账号的消息接收，必要时人工触发一条测试发送；④ 记录通过项、阻塞项及下一阶段范围。

**交付成果：** 现有模块对应表、基线测试记录、接入探测记录。不得在这一阶段重写检索链路或接入全自动回复。

**通过标准：** 原主链路没有新增失败；接入能力明确标记为已实测或尚未通过。渠道未通过时，可继续做本地业务版，但不能宣称已完成真实闲鱼接入。

### 阶段二：实现按商品范围回答

**需求目标：** 先在原来的 `/chat` 中完成闲鱼商品问答，不依赖真实消息连接。

**完成步骤：** ① 准备三件示例商品和卖家规则；② 新增只读商品 MCP 工具；③ 通过原入库流程建立闲鱼知识域；④ 为 Dense 与 BM25 增加一致的商品过滤；⑤ 调整证据拼接和话术，验证商品明确、商品缺失和资料不足三类输入。

**交付成果：** 本地可演示的闲鱼商品问答；原电商模式仍可使用。

**通过标准：** 商品 A、B 的资料不串用；价格等结构化事实不因检索分数低被误拒；没有资料的问题不会凭空承诺。

### 阶段三：实现多轮对话、授权议价和接管状态

**需求目标：** 让业务逻辑完整，能够在本地连续演示。

**完成步骤：** ① 复用会话记忆并关联商品；② 在现有路由中区分商品事实、知识规则、议价和人工处理；③ 实现固定授权报价；④ 实现持久化接管与恢复；⑤ 完成三轮追问、切换商品和连续砍价测试。

**交付成果：** 不接闲鱼也能演示的“闲鱼业务版客服”。

**通过标准：** 上下文不串人、不串商品；报价不越权、不泄露底价；人工模式下不自动回复。

### 阶段四：接入真实闲鱼消息并受控发送

**需求目标：** 将真实消息送进已有 ChatService，而不是再调用参考项目的回答 Agent。

**完成步骤：** ① 整理独立的渠道适配模块；② 统一消息字段并过滤非买家文本；③ 实现去重、顺序处理和发送记录；④ 先观察模式联调；⑤ 检查发送前的接管状态与发送结果，再对选定会话/商品开启自动回复。

**交付成果：** “真实闲鱼消息 → 现有客服 → 原会话回复”的闭环及故障状态记录。

**通过标准：** 授权账号实测通过；重复消息不重复处理；自己发出的消息不触发机器人回环；掉线、登录失效或发送结果不明时，不继续盲目自动发送。

### 阶段五：完成精简工作台

**需求目标：** 卖家看得到、能暂停，不做复杂后台。

**完成步骤：** ① 复用已实现页面，未实现则按此前精简设计搭建；② 展示会话、当前商品、消息/草稿及待人工原因；③ 增加接管/恢复与渠道状态显示，并联调真实状态。

**交付成果：** 一个最小可用的卖家客服工作台。

**通过标准：** 点击接管后后端确实停止自动发送；刷新页面或重启服务不丢接管状态。人工回复仍在闲鱼原生界面完成，不增加后台人工发送系统。

### 阶段六：评估和小范围实机验收

**需求目标：** 用固定样例证明功能可用，再启用少量真实商品。

**完成步骤：** ① 增加 30 个闲鱼场景用例；② 跑旧项目回归与新业务测试；③ 在本地问答、观察模式、真实发送三个层面分别验收；④ 保存结果和已知限制，由卖家明确开启选定范围的自动回复。

**交付成果：** 测试结果、失败样例、运行说明，以及“本地业务版/真实接入版”的明确状态。

**通过标准：** 安全边界用例全部通过；可回答样例的正确且有依据回答比例达到本项目初始目标 90%；真实接入必须有实机记录，不能用 mock 测试代替。

## 6. 验收口径

30 个新场景建议分为：商品事实与范围 8 个、知识规则与拒答 6 个、多轮会话 5 个、议价 5 个、消息与接管 6 个。一个多轮场景可以包含多条消息，这里按场景计数。

必须全部通过的边界包括：不串商品、不跨买家读历史、不泄露底价、不越权报价、不把测试订单当真订单、人工模式不自动发送、受控重复消息测试不重复发送。

“正确回答比例”只对预先标注为有充分资料可答的样例计算；澄清、转人工和忽略分别按预期动作验收。90% 是本项目建议的初始目标，不是行业标准，也不是当前已经测出的成绩。原来的 Recall@5、MRR 等指标继续用于 RAG 子集，不强行套用于商品工具和议价规则。

## 7. 必须明确的限制

参考实现使用网页登录 Cookie、Token 和 WebSocket。阅读源码只能确认实现方式，不能保证它在当前账号下稳定工作，也不能把该实现视为已取得平台官方授权。接入必须使用自己有权操作的账号，遵守适用的平台要求；登录失效或遇到验证时停止自动处理，由账号持有人在官方页面完成验证。[S1][S2][S4]

Cookie、模型密钥、内部底价和真实会话数据库不提交 Git，也不贴进 Codex 提示词或普通日志。复用参考仓库代码前，核对其标示的 GPL-3.0 许可证和发布要求。[S1]

第一版可以交付一个可测试、可演示、可控的单账号客服，但不以“无人维护、永久在线、自动完成交易”作为承诺。
