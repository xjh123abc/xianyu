# 闲鱼智能客服改造技术文档

版本：V1.0 规划稿
日期：2026-09-09
配套需求：`01_闲鱼智能客服_需求文档.md`

> 这是增量实施方案，不是已经完成的代码审查或测试报告。现有文件位置以阶段一读取本地仓库的结果为准；下文新增文件和接口名称是建议，不要求为了匹配目录而搬迁旧代码。

## 1. 技术方向

保留现有 FastAPI → ChatService → RAG/MCP → 回答生成链路，把闲鱼当成新的消息渠道和业务场景。

参考项目的 `main.py` 负责消息接收、商品关联、调用 `bot.generate_reply(...)` 以及发送；`XianyuAgent.py` 负责另一套 Agent 回复；`context_manager.py` 保存会话和商品信息。[S2][S3][S5]

改造时借鉴渠道部分，但回复必须进入自己的 ChatService，不能把参考项目的 Agent、模型客户端和上下文管理器整套搬入，否则会形成两套业务主链路。

| 事项 | 本版决定 |
| --- | --- |
| 模型与算法 | 沿用本地 Embedding、现有 Reranker、DeepSeek、Dense/BM25/RRF，不换模型。 |
| 商品知识 | 原入库流程新增闲鱼知识域；Dense 与 BM25 使用相同资料范围。 |
| 商品工具 | 复用当前 MCP 调用机制，在已有工具服务中新增只读商品查询。 |
| 议价 | 普通 Python 规则计算/选择授权报价，不增加价格 Agent。 |
| 会话与状态 | 复用现有 Memory；没有持久化时补 SQLite，不另建第二套记忆系统。 |
| 渠道运行 | 第一版单 FastAPI 进程、单闲鱼连接任务、一个顺序处理队列。 |
| 页面 | 复用已有前端；未实现时只搭建最小会话工作台。 |
| 部署范围 | 本机、单账号、少量商品；不引入 Redis、消息中间件、微服务和多租户。 |

## 2. 改造后的调用链

```text
原 Web /chat 入口 ───────────────────────┐
                                        │
闲鱼 WebSocket → 渠道适配器 → 标准消息 ──┤
                                        ↓
                            现有 ChatService
                                        ↓
                      去重 / 会话状态 / 当前商品
                                        ↓
                              复用现有路由
                    ┌───────────────────┼───────────────────┐
                    ↓                   ↓                   ↓
             商品公开事实           说明与规则            议价请求
             现有 MCP 客户端        现有 RAG             PricingService
             get_item_info          商品范围过滤          固定授权报价
                    ↓               Dense + BM25             ↓
                    │               RRF → Rerank             │
                    └───────────────────┼───────────────────┘
                                        ↓
                        分别检查事实 / 证据 / 价格权限
                                        ↓
                    复用 Context Builder + DeepSeek
                    （价格金额与关键交易承诺使用确定性模板）
                                        ↓
                     reply / clarify / handoff / ignore
                                        ↓
                观察模式只存草稿；自动模式检查后发送
                                        ↓
                    记录发送状态和真正已发送的历史
```

这里的“分支”不是三个新 Agent。商品事实和知识规则可以组合回答：比如“这件带什么配件，怎么发货”，可以先查询公开商品信息，再检索该商品说明和卖家规则。

**可靠性按证据类型判断：** RAG 证据才检查检索质量；商品工具检查数据是否存在、属于当前商品且能支持回答；价格规则检查授权。不能让所有请求先通过同一个 Rerank 分数阈值，再决定是否调用工具。

## 3. 数据与接口约定

### 3.1 商品数据分为公开资料和内部规则

建议使用以下布局，不改动原来的电商资料：

```text
data/
├── 原有目录与电商资料                         # 保留
├── xianyu/
│   ├── items.json                            # 商品公开结构化事实
│   └── knowledge/
│       ├── common/seller_rules.md             # 卖家确认的通用规则
│       └── items/
│           ├── DEMO_ITEM_001.md               # 商品 A 详细说明
│           ├── DEMO_ITEM_002.md               # 商品 B 详细说明
│           └── DEMO_ITEM_003.md               # 商品 C 详细说明
└── private/
    └── pricing_rules.json                    # 内部底价与报价权限，不入库
```

`DEMO_ITEM_*` 是测试编号，不是真实闲鱼商品编号。真实接入时建立明确映射或使用经过验证的真实编号，不能默认它们天然对应。

`items.json` 最少维护：`item_id`、`title`、`listed_price_cents`、`sale_status`、`data_source`、`updated_at`。售卖状态允许 `listed`、`sold`、`unknown`；未知不能自动补成在售。金额用整数分保存，展示时转换为元。

详细成色、瑕疵、配件、使用说明放入对应 Markdown；不要在 Markdown 重复维护标价和售卖状态。通用规则和商品特殊说明冲突时，未核实前转人工，不让模型任选一条。

第一版 `data_source` 可以是 `seller_manual`，表示卖家维护快照。工具返回更新时间；机器人不得把该快照描述成“刚刚查询到平台实时库存”。资料未确认、变更未同步或来源冲突时，停止相关承诺。真实商品接入自动回复前，由卖家核对页面与本地资料。

内部规则可包含 `allow_auto_bargain`、`approved_quote_cents`、`min_price_cents`。只允许 PricingService 读取内部字段；商品 MCP 工具、Sources、对话接口和前端接口都不能返回底价。

入库器只读取 `data/xianyu/knowledge/`，不能递归扫描整个 `data/`。真实 Cookie、底价文件、会话数据库和真实对话日志加入 `.gitignore`；仓库中只放无敏感信息的示例配置。

### 3.2 知识范围与检索过滤

保留原 `ecommerce_documents`，新增配置指向 `xianyu_documents`，使用同一 Qdrant 实例和现有向量维度。这是新增数据域，不是重做数据库。BM25 也单独使用同一批闲鱼知识文件，不能仍检索旧电商资料。

在原有 `source`、`chunk_index` 等元数据上补充：

```json
{
  "source": "xianyu/items/DEMO_ITEM_001.md",
  "chunk_index": 0,
  "scope": "item",
  "item_id": "DEMO_ITEM_001"
}
```

通用卖家规则使用 `scope=common`。实际 payload 字段路径沿用你目前的存储方式，不为了字段命名重写 Point 结构。

当前商品为 A 时，两路召回的可见范围都必须满足：

```text
scope == common
OR
(scope == item AND item_id == A)
```

Qdrant 支持按 payload 条件过滤，并组合逻辑条件；这里直接利用该能力，不更换检索方案。[S6]

Dense 在查询时传过滤条件。BM25 可以保留全闲鱼语料的打分，但必须先筛选允许的文档，再取 Top K；不能先取全库 Top 5，再把不属于 A 的结果删掉，否则正确资料可能根本没进入候选集。

未知商品的通用问题只查 `common`；需要商品事实时先澄清，不能放宽成所有商品。RRF 和 Rerank 接收的已经是合规范围内候选，不负责弥补商品过滤缺失。

更新 Markdown 后，复用原入库流程刷新闲鱼 Qdrant 与 BM25。两路未同步时暂停受影响商品的自动问答；不删除或重建原电商 collection。

### 3.3 会话与发送记录

真实渠道的会话键建议由后端生成：

```text
xianyu:{seller_account_id}:{platform_chat_id}
```

不能拿商品 ID 当会话 ID，因为不同买家会咨询同一件商品；也不能只拿买家 ID 当当前商品。买家身份和会话编号来自已验证渠道事件，不从聊天文本提取为授权身份。

在现有 Memory 基础上保存当前商品、会话模式及需要的公开报价记录。商品切换时，重置商品相关状态；历史消息带商品标记，本次回答只使用适用历史，不能把上一商品的缺陷、价格或附件接续过来。

至少持久化两类状态：

- 会话状态：`chat_id`、当前商品、`auto/manual`、接管原因与更新时间。
- 消息处理记录：账号、平台消息 ID、会话、商品、内容类型、处理状态、回复草稿、发送状态。

复用现有消息表即可，不要求照着参考仓库重新建一套表。没有持久化时用 SQLite 补齐。对 `(seller_account_id, platform_message_id)` 建唯一约束，避免同一推送重复执行模型和发送。

没有稳定平台消息 ID 时，阶段一必须验证可用的替代标识；不能仅按文本内容去重，否则买家两次发送“还在吗”会被误判为重复。

观察模式的草稿、发送失败和结果未知的回复，不放入“已发送助手历史”。卖家人工回复应进入历史，但需要区分机器人消息回流，避免重复记录。Web 本地测试成功展示的回复可按原逻辑记录。

### 3.4 兼容原来的 /chat

保留原 `query`、`chat_id`。可以新增可选 `scenario` 和 `item_id`；`scenario` 默认仍为原电商模式。下例是拟新增的本地测试请求，不代表当前代码已经支持：

```json
{
  "query": "这件有没有维修过？",
  "chat_id": "demo_xianyu_001",
  "scenario": "xianyu",
  "item_id": "DEMO_ITEM_001"
}
```

真实渠道在服务内部传入更多上下文：`channel`、账号、买家、平台会话、平台消息 ID、时间、消息类型和可选商品 ID。不要要求真实买家输入 `chat_id`，也不要把 Cookie 放入请求正文。

保留 `answer`、`sources`、`can_answer`、`next_step`、`route` 等原字段，可增加内部/渠道用的 `action` 和 `item_id`。已有枚举需要扩展时，在旧测试通过的前提下修改。

| action | 业务含义 | can_answer 与 next_step |
| --- | --- | --- |
| `reply` | 有依据的正常回复或授权报价 | `true`；`next_step=null`。 |
| `clarify` | 缺少商品等必要信息，先问清楚 | `false`；`next_step=clarify_question`（新增枚举值）。 |
| `handoff` | 需要卖家判断，并写入人工模式 | `false`；沿用 `human_handoff`。 |
| `ignore` | 自己的消息、系统通知、人工模式下的普通输入等不自动作答 | `false`；不生成可自动发送的正文。 |

观察模式不改变业务判断，只改变投递行为：即使 `action=reply`，仍然只保存草稿。

Sources 继续留在内部结果中用于核查。可给公开商品证据新增 `source_type=item`、`item_id` 和更新时间，但不能把工具证据伪装成某个 Markdown chunk。发到闲鱼的通常只有自然语言正文，不发送检索分数、本地文件路径、完整 metadata 或内部规则。

## 4. 建议修改范围

以下是职责映射，不是强制创建的完整新目录：

```text
app/
├── api/                         # 沿用 /chat；补会话查询与接管接口
├── services/
│   ├── 现有 ChatService         # 增量加入闲鱼场景编排
│   ├── item_service.py          # 读取公开商品事实
│   └── pricing_service.py       # 确定性报价规则
├── rag/                         # 原模块；增加范围过滤与公开证据拼接
├── channels/xianyu/
│   ├── adapter.py               # 连接、收发、转换、投递状态
│   └── protocol.py              # 隔离参考项目的协议细节
└── 现有 memory / infrastructure # 复用会话；必要时补 SQLite 持久化

mcp_servers/                     # 在已有 server 内增加商品只读工具
eval/                            # 沿用评估程序，增加闲鱼场景数据
tests/                           # 按新能力补测试
```

已有同等职责的文件就原位扩展，不创建同名的新实现。不要为了新增 `get_item_info` 重写 MCP 客户端或额外引入 Agent 框架。

## 5. 六阶段实施步骤

### 阶段一：确认基础和接入可行性

**本阶段不开发完整业务，只解决“从哪里接、哪些已稳定、接入能否验证”。**

#### 1.1 只读核对当前仓库

让 Codex 找到 `/chat`、ChatService、检索入口、Context Builder、可靠性判断、Memory、MCP 客户端/服务端和测试入口，记录真实文件路径及调用关系。

重点确认你之前出现过的“有检索结果但无法回答”“三轮订单追问信息不足”在当前版本是否仍存在。记录现象和原因，不顺带进行全仓库重构，也不把参考项目的目录搬进来。

#### 1.2 保存旧链路基线

运行原 pytest，并实际验证一个原知识库可答问题、一个知识不足问题和一次原订单 MCP 调用；保留一组已有多轮样例及现有检索评估结果。检查模型仍从原本地路径加载。

若已有失败，区分原有问题和本次新增问题。只修复会阻塞后续增量工作的基础问题；不是要求先消灭项目所有缺陷。

**输出：** 简短基线记录，写明命令、通过/失败、关键输出和真实文件位置。

#### 1.3 在隔离入口做渠道探测

记录实际采用的参考仓库提交版本。在独立探测脚本或独立运行环境中验证，不覆盖原项目依赖，也不启动参考项目的自动回答 Agent。

由账号持有人在本地提供自己的授权登录态；先只接收双方知情的测试文本，核对买家、会话、商品、时间、消息唯一标识以及消息类型。若执行测试发送，只人工触发一条已明确的测试文本，并在闲鱼界面核实结果。

同时确认可用的发送回执或机器人消息回流关联方式。未拿到商品 ID、收到批量同步包和收到自己消息等情况，都记录为实际协议样例，不预设每条文本都必有商品 ID。

参考代码的 Cookie、Token 和 WebSocket 实现只能作为探测起点，不是今天必定可用的保证。[S2][S4]

#### 1.4 给出两个独立结论

结论 A：现有业务主链路是否能继续增量开发。结论 B：当前闲鱼账号是否已实测可接收/可发送。

若 B 不通过，阶段二、三和本地页面仍可推进，阶段四的实机完成状态必须保持“阻塞”。不要把 fake 消息收发测试写成平台接入成功。

**阶段验收：** 无未经说明的基线变化；有可复现的探测记录；没有引入自动对外发送。

---

### 阶段二：实现按商品范围回答

**本阶段交付可在旧 /chat 中使用的闲鱼问答。**

#### 2.1 准备三件不同的示例商品

准备成色、配件、标价存在明显区别的 A、B、C 三件商品，并让其中一件售卖状态未知或已售出，方便验证边界。资料是明确标注的测试样例，不能冒充卖家的真实商品。

准备一份卖家通用规则。旧电商规则只有逐条确认适用后才可以迁入，不能把原十二份 Markdown 整体复制后就默认适用于闲鱼。

#### 2.2 复用 MCP 查询公开商品事实

在现有工具服务内增加只读 `get_item_info(item_id)`，读取 `items.json` 或当前已存在的等价商品存储。工具只返回当前卖家资料集合中匹配的公开字段和更新时间，不返回内部报价配置。

复用现有 MCP 客户端及 `mcp/rag_mcp` 编排；具体 route 名称以当前代码为准。先验证直接调用工具，再验证 ChatService 经 MCP 获取相同结果，确保不是仅做了一个没接入的函数。

现有测试订单工具不删除；在闲鱼场景的真实订单请求中禁用测试数据返回，改为人工核查。未来获得可信订单来源时再接入，不在本阶段承诺。

#### 2.3 复用原入库流程，增加闲鱼知识域

通过当前 Loader → Chunker → Embedding → Qdrant 流程入库闲鱼 Markdown，给商品 chunk 标记 `scope/item_id`；BM25 使用同一知识清单。模型和原切分策略先不变。

原电商和闲鱼的 collection/corpus 选择随场景配置，不重载两份模型。若原代码把 collection 硬编码在查询里，只把选择参数传到已有检索入口，不重写检索引擎。

#### 2.4 在两路召回之前限定范围

Dense 使用 Qdrant payload 过滤；BM25 对允许候选应用同样范围后再 Top K；RRF 与 Rerank 保留原实现。

验证“商品 A 的问题，商品 B 有更相似关键词”的干扰样例。正确结果少于 K 时，宁可返回较少证据，也不跨商品补足数量。

#### 2.5 接入原生成与证据判断

价格、状态等确切字段从工具证据取值；长说明、发货规则等走 RAG。组合问题分别验证必要证据，不能只因其中一条证据存在就放行全部承诺。

Context Builder 只接收公开事实、允许范围内的片段和适用历史；保持检索分数、原始 metadata 和内部底价不进入正文。提示词要求只说明已知事实，未知维修史不能回答“没有维修过”。

**阶段验收：** 直接 MCP 和经 `/chat` 调用均可验证；A/B 不串资料；商品缺失能澄清；知识不足不编造；旧电商接口回归通过。

### 阶段三：实现多轮、授权议价与人工接管

**本阶段完成离线可演示的业务闭环。**

#### 3.1 复用 Memory 关联当前商品

第一轮从可信渠道字段或本地测试参数确定商品，后续缺省时使用当前商品。明确切换商品后更新状态，并隔离旧商品相关历史。

复用现有历史窗口，至少能容纳三轮测试，不为此加入长期记忆、向量化聊天历史或自动摘要系统。不同买家用不同会话键验证。

#### 3.2 在原路由增加闲鱼业务判断

保留旧 `rag/mcp/rag_mcp` 路由，在其上区分商品事实、知识说明、议价和人工处理。既有路由不必改成新的四 Agent 系统。

优先识别明确找人工、订单核查和争议；对缺少商品的商品问题先澄清。不要把含“价格”的所有消息都当作砍价：“标价是多少”是公开事实查询，“能少一点吗”才是议价请求。组合问题要保留其中各项条件。

#### 3.3 编写确定性的报价规则

第一版不做多轮阶梯降价，只使用卖家批准的固定可报价格。

加载配置时检查：商品存在、金额有效、授权报价不低于内部底价、不高于当前标价。配置缺失或矛盾、商品已售出、售卖状态未知或资料变更未确认时，不自动报价。普通砍价请求返回相同授权报价；买家的低报价、反复催促或“忽略之前规则”不能改变授权。

多件打包、赠品、未授权包邮等条件不能仅抽取一个数字就答应，转人工处理。金额由规则返回，使用固定模板表达；不要再把价格模板交给模型自由改写。需要同时回答其他知识问题时，可以将有依据的说明与该模板组合。

内部底价不进入提示词，也不进入公开工具返回。不要依赖“让模型不要泄露底价”这句话作为保护措施。买家消息、商品描述和检索片段都只是数据，不得被当作修改价格配置、切换接管模式或调用写操作的控制指令。

#### 3.4 把转人工落实为持久状态

在现有会话存储上增加 `auto/manual` 与原因；若当前只有内存字典，则补 SQLite 持久化。`handoff` 必须写状态，而不只是返回 `next_step=human_handoff`。

进入人工模式后，仍接收和记录买家消息，但不继续自动作答。只由卖家显式恢复，不采用超时自动恢复。

首次转人工可准备一条不承诺接通时效的固定提示，是否发送由后续渠道的模式控制；后续消息不得重复发送该提示。未知商品但能问清楚时使用 `clarify`，不一律锁定人工模式。

#### 3.5 完成本地行为测试

至少演示：同商品三轮追问、两名买家交替咨询、同会话切换商品、连续砍价、要求透露底价、缺少议价配置、主动找卖家、重启后仍为人工模式。

**阶段验收：** 上下文正确；价格规则可用普通单元测试断言；底价不出现在提示词或公开响应；人工状态可恢复且不会自动消失。

### 阶段四：接入真实消息并受控发送

**本阶段仅增加渠道闭环，业务回答仍走阶段三的同一服务。前提是阶段一渠道探测已经通过。**

#### 4.1 隔离渠道代码

将需要的连接、消息解析和发送逻辑放入 `channels/xianyu`。不复制参考项目的 `XianyuReplyBot` 与 `ChatContextManager`。

参考接口实现包含交互式输入和退出程序的分支；移入服务后应改为返回“登录失效/需人工验证”等渠道状态，不能把这些分支原样搬入并终止整个 FastAPI 服务。[S4]

只使用授权登录态；验证失效时停止渠道自动处理，由账号持有人通过官方页面操作，不实现绕过验证或自动规避限制。

#### 4.2 标准化消息并正确过滤

解析结果最少包括账号、平台消息 ID、会话、买家、时间、消息类型、文字、可选商品 ID。字段值来自经过验证的协议，不从用户正文中伪造控制字段。

处理同步包中的各条事件，区分买家文本、机器人回流、卖家人工回复、系统交易通知和非文本。不能把整包一概当成一条买家消息，也不能把“会话里出现订单通知”当成已具备订单查询能力。

自己的机器人消息不触发新回复；识别到卖家实际人工回复时暂停该会话。买家发一个控制关键词不得取得“恢复自动”权限。商品 ID 缺失时按会话状态补齐，仍无法确认则进入澄清，不静默丢弃或猜商品。

#### 4.3 连接与模型处理分离

在现有应用启动/关闭机制中管理一个闲鱼连接任务和一个顺序处理队列；已有生命周期管理就扩展它，没有时可用 FastAPI `lifespan`。关闭应用时清理连接和任务。[S7]

接收、确认消息和心跳不等待本地 Rerank 或模型生成结束。复用当前异步服务；其中同步的模型推理或网络调用放入适当线程池/现有执行器。普通同步辅助函数不会仅因在异步函数里被调用就自动变成非阻塞，应明确检查这一点。[S8]

进入处理前以持久化唯一键去重；第一版单队列顺序处理，暂不做复杂并发。连接重放、程序重启等情况都不能仅依赖内存集合防重复。

默认 `XIANYU_MODE=off`。真实渠道运行只使用一个应用进程，不开开发热重载，避免重复连接和重复发送。原本的开发启动方式仍可在渠道关闭时使用。

#### 4.4 观察模式验证，不对外自动发送

`XIANYU_MODE=observe` 时，真实消息进入原 ChatService，生成结果标记为草稿。工作台未完成前，可以通过临时只读接口/本地记录检查草稿；不能为此新建第二套对话业务。

草稿不进入已发送助手历史，不让后续回复误以为买家已经看到。保留用户消息、草稿、来源和处理动作，日志脱敏。

先核对原会话、商品对应、回复依据、人工模式和去重，再进入自动发送验证。

#### 4.5 发送前检查与发送结果记录

自动发送必须同时满足：全局自动模式、会话未被接管、当前商品已被卖家启用、消息未处理发送、回复动作允许且所需证据通过。对于没有商品的输入，仅允许在已启用账号内发送不含商品承诺的澄清；正常业务回复不能绕过商品启用范围。

生成完成后、真正发送前，重新检查会话模式、当前商品和最新报价授权，避免卖家已经接管、商品已经切换或授权价格已经改变，旧回复仍被发出。接管状态变化与待发送任务需协调；已经提交给平台的消息无法靠接管按钮撤回。

首次转人工提示作为一次性的状态切换通知处理，不构成人工模式下持续回复的例外。

至少区分 `draft`、`send_attempted`、`sent`、`failed`、`unknown`。发送尝试前保存记录；能够按验证过的回执或消息回流确认时才记为 `sent`，这里表示发送已确认，不表示买家已读。网络中断导致结果不明时标记 `unknown`，不盲目自动重发。

确认发送的内容才进入已发送助手历史。失败、结果未知的消息留给卖家核查；在缺乏平台幂等发送保证时，不承诺网络异常下数学意义上的“恰好发送一次”。

**阶段验收：** 授权账号真实消息进入原 ChatService；观察模式零自动发送；受控重复推送只处理/发送一次；自发消息不回环；人工接管能够取消未发送回复；发送失败与未知状态可见。

### 阶段五：完成精简工作台

**本阶段只让卖家看得到和能接管，不做大型管理后台。**

#### 5.1 复用前端基础

检查你之前规划的页面是否已有代码。有则增量改，没有则按已经讨论过的精简风格搭建，不重新设计一套复杂产品。

页面只保留会话列表、聊天/草稿区域、当前商品和接管状态。渠道连接状态用小型状态提示即可；不加经营图表、权限管理和复杂商品编辑器。

#### 5.2 接入真实后端状态

复用已有接口，必要时补充会话列表、会话消息、接管/恢复和渠道状态四类能力。参考路径可以是 `GET /sessions`、`GET /sessions/{id}`、`PATCH /sessions/{id}/mode`、`GET /channels/xianyu/status`，最终路径以旧 API 结构为准。

草稿与已发送内容必须视觉区分。待人工原因要可见；模式切换只有在后端成功后才更新页面，不能只切一个前端按钮。

本版仅本机访问。底价和 Cookie 不通过这些接口暴露；真实部署不直接把未认证的控制接口开放到公网。

#### 5.3 验证接管闭环

在生成回复期间点击接管，验证尚未发送的回复被停止；刷新页面、重启服务后，人工模式仍保持。卖家使用闲鱼原生界面回复，回复回流后进入会话历史。

本版不增加后台人工发送、人工审核发件箱或复杂工单系统。观察模式可以查看/复制草稿，实际发送仍由卖家在闲鱼原生界面完成。

**阶段验收：** 页面展示的商品、草稿、发送和接管状态与后端一致，且不存在纯前端“假接管”。

### 阶段六：回归评估与小范围实机验收

**本阶段区分“测试通过”和“真实平台验证通过”。**

#### 6.1 增加 30 个有标注的闲鱼场景

在现有 eval 下增加闲鱼样例，不覆盖旧 50 条或已准备的 hard case。建议分布：商品事实与范围 8、知识规则与拒答 6、多轮 5、议价 5、消息与接管 6。

样例最少标注：场景 ID、商品、输入/多轮消息、预期动作、关键事实或允许报价、正确来源、禁止出现的承诺。预期答案以事实约束为主，不要求自然语言逐字相同。多轮按场景计数。

#### 6.2 分层运行测试

先跑不联网、不下载模型、不登录真实账号的单元测试，覆盖过滤、工具字段、报价、路由、状态和消息去重。正常 pytest 不得意外连接真实闲鱼或发送消息。

再使用现有本地模型和知识库执行真实业务评估。最后单独运行授权账号实机测试，并保留去敏记录。复用当前评估入口；确实缺少的行为测试再补脚本，不预先假定某个新命令已经存在。

保留原项目回归。新增商品工具和场景不能破坏原 `/chat` 请求、原 MCP 订单测试或原检索结果结构。

#### 6.3 使用适合各分支的指标

RAG 子集继续看 Recall@5、MRR、Rerank Top1/Top3，并检查检索到的证据属于正确商品。商品工具看字段正确性；议价看授权边界；人工接管看状态和发送行为。

初始目标：所有边界测试通过；有充分证据可答的场景中，正确且有依据的回答不少于 90%。单独报告澄清/转人工/忽略动作是否符合标注，不能把这些场景混入可答率分母。

分数门槛以闲鱼样例结果校准。不要一开始同时更换模型、提高 Top K、改变切分和大改提示词，否则无法知道哪项变化起作用。这是后续实验顺序，不是认为当前阈值已经正确。

#### 6.4 保存结果并小范围启用

记录基线、真实模型结果、平台实测结果、失败用例及已知限制。先由卖家核对资料，再显式启用少量商品；不是一接通账号就放开全部自动回复。

运行说明必须能回答：如何关闭渠道、如何观察草稿、如何开启已验证商品、如何接管/恢复、登录失效如何停止并提示、如何查看失败或发送结果不明的消息。

**阶段验收：** 本地业务、渠道实机和旧功能回归均有独立记录；通过项和未通过项明确；不能把单元测试截图作为“闲鱼真实接入已完成”的证据。

## 6. 每次交给 Codex 的任务边界

每次只实施一个阶段中的一个明确步骤。任务中写清目标、允许改动范围、保留内容、测试样例和验收方式。

要求 Codex 的每次输出包含：实际修改文件、关键调用链变化、执行的测试及结果、尚未验证的内容。没有实机环境时就标记未验证，不生成“已接入成功”的结论。

例如第一条任务应是“只读核对当前项目并给出模块对应和基线执行方式”，而不是“按照参考仓库把整个项目改成闲鱼客服”。

实现顺序不变：先确认基础，再按商品问答，再多轮与议价，之后接入渠道、补工作台、做分层验收。真实渠道探测提前做，但完整渠道不抢在业务规则之前。
