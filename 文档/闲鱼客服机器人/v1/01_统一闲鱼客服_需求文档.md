# 统一闲鱼客服需求文档

版本：V2.0｜日期：2026-09-10  
配套文档：`02_统一闲鱼客服_技术文档.md`

> **主旨：先清理现有项目中已经确认无用的代码，再把商品查询、商品说明、售后、退款和物流问答融合到同一个客服中。用户不需要选择“闲鱼模式”或“旧客服模式”。**
>
> 本版替换旧方案中“按模式选择两套客服”的设计，重点修正现有第二阶段；不推翻已经完成的 MCP、RAG、模型和接口。本轮不扩展自动发送、议价和前端。

## 1. 最终要做成什么

同一个买家、同一个会话、同一个商品，可以连续咨询商品信息和售后信息；也可以在一句话里同时问两类问题。

例如，当前商品是 `DEMO_ITEM_001`：

| 买家问题 | 系统应该怎样处理 |
| --- | --- |
| “这个相机多少钱？” | 使用现有商品 MCP 查标价，回答 1280 元。这个金额来自当前测试数据，不是真实平台报价。[E2] |
| “收到后发现有质量问题怎么办？” | 使用现有 RAG 查卖家已经确认适用的售后规则，不要求切换模式。 |
| “多少钱？收到有问题能退吗？” | 同时查询商品事实和售后规则，合成一次回答；哪部分不知道，就明确说明哪部分不能确认。 |
| “你们店一般怎么处理售后？” | 即使没有指定商品，也能查店铺通用规则。 |

**融合的是服务能力，不是把所有数据无区别地混在一起。** 商品价格仍应精确查表，售后规则仍应检索资料；内部可以按需要调用不同能力，但不能让用户先判断该选哪个模式。

## 2. 当前已经有什么，哪些还不能下结论

| 当前情况 | 本轮处理 |
| --- | --- |
| 用户已实测三个 `DEMO_ITEM_*` 可以经 `get_item_info_via_mcp()` 返回商品事实。[E2] | 保留这条 MCP 链路，不重新开发。 |
| 已有三件商品及 `data/xianyu/items.json`，不是此前示例中的 A001/B001/C001。[E1][E2] | 后续测试全部使用真实测试编号，不再造另一套商品。 |
| 已有 ChatService、MCPService、RAG、Context Builder、DeepSeek 和相关测试。[E1] | 原地整理和复用，不另外建立一个闲鱼客服服务。 |
| 用户的 `/chat` 价格测试返回旧知识检索结果，并被低分拦截。[E3] | 需要检查请求字段传递与编排，不通过降低阈值掩盖问题。 |
| 上传材料只有代码搜索片段，部分测试使用 Mock/FakeRag。[E1] | 不能据此认定所有分支都是冗余，也不能认定真实 `/chat` 已接通。 |

本次交付是实施方案。尚未取得本地完整仓库，因此**没有执行实际代码删除**；第一阶段必须在完整源码上审查、列出证据后再清理。

## 3. 本轮必须实现的需求

### R01：功能修改前先检查和清理

先查整个项目的代码入口、实际调用、测试、启动脚本和配置，找出确定不再使用的代码。清理对象包括死代码、被替代的重复实现、失效配置、废弃脚本及无用依赖。

每项删除都必须说明“删什么、为什么无用、谁在调用、用什么测试验证”。不能只凭“文件很长”“没有普通函数调用”“暂时没用到”就删除。

第一轮先删除不影响现有行为的冗余。仍在运行、需要被统一链路替代的旧分支，等替代完成后立即删除，不保留两套长期实现，也不提前删坏现有功能。

### R02：只有一个客服入口和一套业务编排

继续使用现有 `/chat` 和 ChatService。商品问答、售后问答和组合问答都进入这套服务。

用户不需要传 `scene=xianyu` 才能查询商品；渠道信息只能用于标记来源、关联会话和确定店铺资料，不能用来把商品能力与售后能力分开。

### R03：商品事实沿用现有 MCP

标题、标价、售卖状态和更新时间继续通过 `get_item_info(item_id)` 查询。不同商品返回自己的数据；找不到商品时不能用其他商品代替。

本地商品数据是卖家维护的测试快照，不得描述成“已实时查询闲鱼库存”。内部底价不进入公开工具返回、模型输入或买家答案。

### R04：原有售后知识必须真正被利用

保留原来的 RAG 能力，并将原知识中适用于当前卖家的售后、退换货、物流等内容纳入店铺知识范围。

旧资料逐条分成“可以沿用、修改后沿用、暂不适用”。不能因为文件属于旧电商目录就全部排除，也不能因为出现“售后”两个字就把整份文件默认当成卖家承诺。未确认的条款保留原文，但不参与本店回答。

### R05：一句话需要两类信息时，必须一起回答

“多少钱，多久发货？”必须分别取得商品标价和适用发货规则，再给出一条完整回复。不能只回答价格，也不能把“价格”当普通知识检索来猜。

已经查到价格、但没有售后依据时，要保留正确价格并说明售后暂不能确认。不得因为一项资料缺失就把另一项有效信息丢掉，也不得因为一项有效就允许另一项编造。

### R06：商品上下文属于会话，不是模式开关

本地测试可通过 `item_id` 指定商品；真实渠道以后由消息适配器提供。用户文本明确写了一个商品编号时，也应识别；后续“这个”“它”可沿用同一会话已经确认的商品。

新会话没有商品线索时，商品问题先澄清；通用售后问题直接查通用规则。同一买家换商品后不能沿用旧商品事实，不同会话不能串商品。

### R07：知识能融合，商品必须隔离

问商品 001 时，允许使用“商品 001 资料 + 适用的店铺通用规则”；不能引用商品 002、003 的配件、瑕疵或维修记录。

Dense 和 BM25 都要执行这个范围限制。返回证据不够 Top K 时，宁可少返回，也不拿其他商品补足。

### R08：证据不足时明确说明，不靠阈值掩盖错误

商品事实根据 MCP 返回内容判断，不能被无关 RAG 的 Rerank 低分拦截。RAG 继续保留原有可靠性判断，但高分本身不等于资料能支持全部承诺。

`unknown` 不能回答“在售”；没有维修史记录不能回答“没修过”；没有真实订单来源不能返回测试订单冒充实单。

## 4. 本轮做什么、不做什么

保留本地 Embedding、Qdrant、BM25、RRF、Reranker、DeepSeek、已有 MCP 和 Memory。允许删除重复实现，但不能删除它们承载的有效能力。

本轮只做：代码清理、统一请求、会话商品关联、知识整合、统一编排、证据判断和验收。

本轮不新增：多 Agent 框架、第二套模型客户端、第二套会话系统、自动议价、真实订单接入、自动发货退款、闲鱼自动发送和新的前端后台。已完成的渠道代码不因本轮暂不用就判为死代码；本轮验收不依赖 Cookie，也不向买家发消息。

## 5. 实施顺序：五个阶段、十七步

每阶段都要有可运行成果。不能一次把所有代码改完，再统一猜问题在哪里。

### 阶段 0：先审查并清理冗余代码（4 步）

**0.1 读取现状。** 找出 `/chat` 请求模型、服务调用链、MCP、检索、生成、会话、脚本和测试的实际位置。

**0.2 保存基线。** 记录修改前的测试结果、三个真实 MCP 查询和当前 `/chat` 失败表现，保存本地修改状态。

**0.3 完成第一轮清理。** 删除已经证实无用的代码、配置和依赖；仍承载业务的重复路径列入“替换后删除”。

**0.4 验证清理。** 重跑基线，确认清理没有新增失败，并形成逐项删除记录。

**阶段成果：** 项目仍能运行，有清理清单；不再积累确认无用的代码。

### 阶段 1：统一请求与当前商品（3 步）

**1.1 统一 `/chat` 参数。** 保留 `query`、`chat_id`，让可选 `item_id` 实际传入 ChatService；不要求模式字段。

**1.2 复用会话保存当前商品。** 明确编号、文本商品线索和已有会话共同确定当前商品，处理切换和冲突。

**1.3 验证入口。** 不传模式也能传入商品；没有商品时，通用问题不被拦，商品问题会澄清。

**阶段成果：** 用户不再需要知道“闲鱼模式”这个概念。

### 阶段 2：整合商品资料与售后知识（3 步）

**2.1 审核原知识条款。** 把确认适用的旧售后、退款、物流内容纳入店铺规则，记录原来源。

**2.2 使用原入库链路更新同一店铺知识范围。** 商品说明和店铺规则都能被同一个 RAG 服务检索；不复制检索引擎。

**2.3 验证检索范围。** 商品 001 可查自己和通用规则，不能查到 002；没有商品时可查通用规则。

**阶段成果：** 商品资料与售后资料能一起使用，但不串商品。

### 阶段 3：统一 ChatService 的证据处理（4 步）

**3.1 判断问题需要哪些信息。** 识别商品事实、知识问题以及两者混合，不再按“旧客服/闲鱼客服”二选一。

**3.2 调用已有能力。** 商品事实走现有 MCP，知识走原 RAG，组合问题两者都调用。

**3.3 分别判断、统一回答。** 逐项处理有证据和无证据的部分，汇总成一条回复，保留来源。

**3.4 删除被替代的旧路径。** 统一链路通过测试后，移除旧互斥入口和重复拼接、判断、生成逻辑。

**阶段成果：** “多少钱，收到有问题怎么办？”可以在一次请求里得到两部分有依据的回答。

### 阶段 4：真实验收与最后整理（3 步）

**4.1 跑自动化测试。** 单元测试检查分工、过滤和错误处理；真实 MCP 与真实 `/chat` 联调不能用 Mock 代替。

**4.2 按下表手工验收。** 使用当前三件商品和实际规则，核对问题、答案和证据。

**4.3 收尾清理。** 删除迁移后残留代码、过期参数和旧示例；交付实际运行命令及测试结果。

**阶段成果：** 一套精简的统一客服，以及可以复现的验收记录。

## 6. 验收用例

以下金额和状态取自用户已提供的实测输出，执行前应核对 `items.json` 是否有变更。[E2] 配件、维修史和售后条款尚未提供完整原文，测试时必须先读实际资料再确定标准答案，不能自行编造。

| 编号 | 测试输入或动作 | 通过标准 |
| --- | --- | --- |
| A01 | 分别问 001 标价、002 是否还能买、003 是否在售 | 001 为 1280 元；002 已售出；003 状态未知，不承诺可买。 |
| A02 | 新会话，无 `item_id`：“你们店售后怎么处理？” | 使用确认适用的通用规则，不要求先选商品或模式。 |
| A03 | 001：“多少钱？收到有质量问题怎么办？” | 同次请求有真实 MCP 与 RAG 证据，回答两部分；售后条件与原文一致。 |
| A04 | 问资料未记录的事实，再与价格合并提问 | 不编造；组合问题仍保留正确价格，并说明未知部分。 |
| A05 | 新会话、无商品：“这个多少钱？” | 询问具体商品，不随机选一件。 |
| A06 | 商品编号 `XXX999` | 明确未找到，不用别的商品或旧价格规则顶替。 |
| A07 | 同一会话：先问 001 价格，再问售后，再问“它有什么配件？” | 不切换模式；第二、三轮仍关联 001，配件与其资料一致。 |
| A08 | 同一会话改问 002；再新建另一个会话 | 前者使用 002；后者不继承上一会话的商品。 |
| A09 | 问 001，但问题关键词只在 002 中出现 | Dense、BM25、最终来源均不引入 002；不知道就说明不知道。 |
| A10 | 问一条尚未确认适用的旧承诺 | 不把旧规则直接承诺给当前买家，也不偷偷回退到旧全库。 |
| A11 | 只问商品价格，RAG 没有可用证据 | 已有有效 MCP 事实时仍可回答；不被 Rerank 阈值误拦。 |
| A12 | 组合问题中模拟 MCP 失败，但售后规则可用 | 不编价格；已确认的通用规则仍可说明，并标明价格查询失败。 |
| A13 | 不传 `scene/scenario`，只传 `query/chat_id/item_id` | 商品信息和售后信息均能使用，实际参数没有被接口丢弃。 |
| A14 | 跑旧测试、真实联调，再检查清理清单与公开输出 | 无未解释的回归；无底价、Cookie 泄露；无两套残留客服主链路。 |

全部用例应逐项记录“通过、失败或阻塞”。Mock 测试通过、接口返回 200、答案偶然正确，都不能单独证明本轮完成。

旧测试若与新目标冲突，应更新对应预期并说明原因；不得删除测试或跳过失败来制造“全部通过”。旧知识中不再适用的承诺不要求原样回复，但通用问答、商品工具和有效功能不能因此损坏。

## 7. 最终交付标准

交付一套修改后的现有项目，不是旁边新增的另一套客服。必须同时交付：实际清理明细、统一接口示例、真实验收结果和可直接执行的运行命令。

**完成的判断只有两个：用户能在同一会话自然地问商品和售后；开发者只维护一套编排、检索和回答逻辑。**

## 8. 依据与边界

- [E1] 用户上传的 `粘贴的文本 (1).txt`：包括 `ItemService`、MCP 服务与客户端、ChatService 调用片段、配置和部分测试。只能证明片段中可见的事实，不能替代完整代码审查。
- [E2] 本次对话中用户提供的直接函数调用、商品编号列表、三个 `get_item_info_via_mcp()` 实测结果。
- [E3] 本次对话中用户提供的 `/chat` 失败响应：价格问题返回旧知识片段，可靠性判断未通过。未提供该次完整请求和最新接口源码，不能仅凭响应确定唯一根因。
- [E4] 旧 V1.0 需求、技术文档及本次明确的方向修订。V1 中保留两套业务模式的要求不再执行；有效模块和经确认适用的知识继续复用。
