## 2. 目标调用方式

```text
/chat 或已有闲鱼消息入口
        ↓
同一个 ChatService
        ↓
确定会话与当前商品
        ↓
判断本次需要哪些事实、哪些知识
        ↓
按需要调用已有 MCP 和已有 RAG，可同时使用
        ↓
分别检查每个问题是否有证据
        ↓
同一个 Context Builder / 回答生成与汇总入口
        ↓
answer + sources + can_answer + next_step
```

内部仍然需要条件判断，但判断的是“需要查什么”，不是“用户属于哪个客服模式”。不是每条消息都必须同时调用两个能力。

## 4. 阶段 1：统一请求与会话商品（对应 R02、R06）

### 1.1 让 `/chat` 接受统一请求

本轮交付后的商品请求约定：

```json
{
  "query": "这个商品多少钱？收到有质量问题怎么办？",
  "chat_id": "qa_unified_001",
  "item_id": "DEMO_ITEM_001"
}
```

通用规则请求不需要商品：

```json
{
  "query": "你们店一般怎么处理售后？",
  "chat_id": "qa_general_001"
}
```

保留原 `query/chat_id` 语义；`item_id` 可选。现有老调用只传 `query/chat_id` 仍能问通用问题，不要求补 `scene/scenario`。

已经存在的渠道字段可以保留作来源信息；确有调用方使用旧模式参数时，只在 API 入口做薄兼容，转换后进入同一服务，不保留两套业务。没有调用方就删除废弃参数和文档示例，不凭空兼容所有猜测名称。

检查请求模型、路由传参、服务签名三处一致。Pydantic 在默认配置下可能忽略未声明的额外字段，因此“请求返回 200”不代表 `item_id` 已被接收；实际行为以项目版本和模型配置为准。[T1]

**验收：** OpenAPI 展示真实支持的字段；接口测试捕获传给 ChatService 的 `item_id` 并断言一致；随后补真实调用验证，不能只测 Mock。

### 1.2 复用 Memory 确定当前商品

按以下顺序处理，不增加“商品模式”：

1. 本次结构化 `item_id` 或真实渠道提供的当前商品，是明确线索。
2. 本次文本明确写出商品编号时，提取为候选；没有结构化编号时可替代旧会话商品。不能把任意数字、价格当商品编号。
3. 本次没有新线索时，沿用同一 `chat_id` 已确认的商品。
4. 本次结构化编号和文本编号冲突、出现多个候选或名称有歧义时，先澄清，不静默选一个。

商品候选通过现有 MCP 确认；同一请求取得的结果后面直接复用，不再重复查询。有效商品才能写入当前会话；明确换成不存在的商品时，不能又退回旧商品回答本次问题。

通用售后问题不依赖商品，不必为了它先调 MCP。混合问题缺少商品时，可以先回答有依据的通用规则，同时询问具体商品。

商品切换后，不把旧商品价格、配件或缺陷作为新商品证据。保留必要聊天历史，但按商品关联选择适用内容；不同会话独立。不得使用进程级全局变量保存唯一“当前商品”。

### 1.3 先验证入口和上下文，再改回答编排

验证“带 `item_id`”“文本带实际编号”“仅同一会话追问”“新会话无商品”“本次编号冲突”五种输入。此时测试重点是解析和传参，不把尚未完成的答案生成功能算作通过。

**阶段成果：** ChatService 能稳定收到问题及正确商品，用户不再需要模式参数。

## 5. 阶段 2：整合资料并统一检索范围（对应 R04、R07）

### 2.1 审核原知识，形成当前店铺的有效规则

读取原十二份 Markdown 与现有闲鱼知识。对售后、退换货、物流等条款逐项确认：适用则沿用，需修改则由卖家确认，不适用或未确认则不进入当前店铺回答范围。

优先核对已在响应中出现的 `09_after_sales.md`、`03_refund_return.md`、`02_shipping.md`；文件名只是查阅线索，不代表整份文件已经适用。[E3]

可直接沿用的整份资料保留唯一原文件，通过已有入库清单引用；只有部分适用的文件，整理为一份卖家确认版本，并记录原文件和章节。不能把同一段规则以两份来源重复入库。旧原文保留，不用删除知识文件来代替适用性审核。

同一条规则只保留一个生效版本。商品特殊约定与通用规则冲突时，先核实、修订；未核实不能交给模型任选一条。

**输出：** 规则确认表：原文件/章节、沿用或修改内容、适用范围、是否确认、当前生效来源。卖家未确认时可完成机制和测试样例，但不能宣称真实店铺规则已验收。

### 2.2 继续使用现有入库链路和一个店铺检索入口

本轮优先复用配置里已有的 `xianyu_documents` 和闲鱼知识清单，把当前商品 Markdown 与已确认的旧售后/物流内容共同纳入。名称叫 xianyu 不影响它同时服务商品和售后。[E1]

```text
当前店铺有效知识清单
＝ 商品说明
＋ 已确认的原售后、退款、物流条款
＋ 现有有效卖家规则
        ↓
原 Loader → Chunker → Embedding → Qdrant
        ↓
同一清单供 BM25 使用
```

旧 collection 保留作原数据和回归资产，不再作为“没搜到就扩大到旧全库”的兜底。融合业务不要求合并数据库全部历史数据，也不要求重新加载两套模型。

商品标价和售卖状态仍以 `items.json` 为唯一维护来源，不在 Markdown 另写一份。当前只服务一个卖家，不新增多租户管理系统。

沿用现有 `source/chunk_index`，保留已经实现的 `scope/item_id`。统一一种通用范围名称：下文用 `common` 示意；实际若已有 `seller_general` 就沿用它，不能两套名称混用。

```text
商品片段：scope=item，item_id=DEMO_ITEM_001
通用规则：scope=common，不归属某件商品
```

只有规则确认表中生效的资料参与当前入库。执行前检查原删除旧 chunk 的逻辑：本次只更新目标 collection/清单的资料，不误删原库或其他来源。更新后同步刷新 Dense 与 BM25，并验证旧规则撤下后两路都不再返回它。

### 2.3 两路使用同一可见范围

```text
有明确且有效商品：
  scope=common
  或（scope=item 且 item_id=当前商品）

无商品的通用问题：
  仅 scope=common
```

Dense 在 Qdrant 查询时传 payload 过滤条件；Qdrant 提供 AND/OR 等组合过滤能力，可表达以上范围。字段路径沿用实际 payload 结构。[T2]

BM25 沿用原打分实现，但先选出允许的候选编号，再在这些候选内排序取 Top K。不能先对全库取 Top K 再删除其他商品，否则正确资料可能已经被挤出去。

RRF、Rerank 继续使用原实现，只接收范围内候选。数据更新及去重后不允许重新引入其他商品。没有足够候选就少返回，不跨范围凑数。

**验收：** 对当前商品 001，构造一个 002 关键词更匹配的测试样例，分别检查 Dense、BM25 和最终证据；同时验证无商品的通用售后问题能查到规则。干扰样例放测试夹具或测试数据集，不篡改卖家生产资料。

## 6. 阶段 3：统一证据编排与回答（对应 R03、R05、R08）

### 3.1 在现有路由上判断“需要什么”，不新增 Agent

复用现有意图识别，输出最小内部计划。下例只是内部结构，不是给买家新增接口参数：

```json
{
  "item_fields": ["listed_price_cents"],
  "knowledge_questions": [
    {"question": "收到有质量问题怎么办？", "scope": "common"}
  ]
}
```

| 问题 | item_fields | knowledge_questions |
| --- | --- | --- |
| 多少钱、标价多少 | listed_price_cents | 空 |
| 还在卖吗、卖掉了吗 | sale_status | 空 |
| 一般怎么处理售后 | 空 | 适用售后规则 |
| 这件有什么配件 | 空 | 当前商品配件说明 |
| 多少钱、多久发货 | listed_price_cents | 适用发货规则 |

允许多个需求同时成立，不能在识别到“价格”后立即返回，丢掉后面的售后问题。

明确问题可用现有规则快速判断；歧义或换一种说法时，复用当前模型路由能力做语义判断，至多补一次有必要的分类调用。已有判断能用就不再加调用，不建立新的分类 Agent 或模型客户端。不要仅靠一个“价”字判断，否则“运费价格”也可能被误当商品标价。

分类结果必须落在受支持的字段/范围内；无法判断则澄清，不能凭空生成价格或回退旧客服模式。模型只识别需求，不编造商品编号、账号权限或店铺政策。

### 3.2 使用同一执行流程收集证据

以下是流程说明，不是可直接复制的项目代码：

```text
确定问题与商品线索
→ 生成最小需求计划
→ 需要商品事实/商品资料时，复用现有 MCP 确认商品
→ 需要知识时，使用统一 RAG 检索对应子问题
→ 收集有效事实、有效片段及未解决的问题
→ 交给同一回答汇总入口
```

商品调用沿用：

```text
ChatService
→ MCPService.get_item_info
→ get_item_info_via_mcp
→ get_item_info
→ ItemService
```

同一请求对同一商品最多查一次。商品详细说明不在工具字段里时，走 RAG，不要求扩大 MCP 返回所有资料。

组合问题要保留各自查询：检索“收到有问题怎么处理”时，不把整句价格咨询原样当成唯一检索问题。多条知识问题可逐条复用当前检索函数，不新建并行任务框架。

MCP 失败只阻止依赖它的事实；独立的通用规则仍可查。RAG 失败只阻止相应知识承诺；已验证的价格仍可回答。商品找不到时不检索其他商品替代，独立通用问题仍只查 common。

### 3.3 分别判断证据，再统一输出

#### 商品证据怎么判断

检查 `found`、返回编号、公开字段及数据类型。金额继续保存整数分，展示时精确转换为元，不把 `128000` 当成 128000 元。

`sold` 要明确已售；`unknown` 不能推断在售。`data_source=seller_manual` 表示本地维护资料，不宣传实时平台核验。只查价格时，RAG 可以不执行，RAG 的低分不能否定有效商品事实。

#### 知识证据怎么判断

沿用现有 Rerank 和可靠性配置，本轮不换模型、不修改阈值、不混用分数尺度。对每个知识子问题独立判断，不能用“全体证据最高分”给整句话放行。

除分数外，还要检查片段是否在允许范围、是否覆盖当前问题。描述“功能正常”的片段不能证明“没有维修过”。所有交易条件都必须保留原文限制，缺少对应条款就说明无法确认。

先复用现有证据覆盖检查；如果只有分数判断，则在同一次知识生成中为各子问题返回最小结果：`status`、`text`、`source_ids`。无支持、冲突或没有有效引用的部分不能输出肯定承诺；不再另开一个审核 Agent。

引用存在只证明来源真实，不能自动证明推理正确。因此验收必须人工对照资料，检查是否保留条件、有没有过度推断。

#### Context Builder 与生成怎么改

只整理三类输入：当前商品公开事实、允许且相关的知识片段、适用的近期会话。价格底价、Cookie、原始 metadata 和检索分数不进入正文；片段标识可保留用于引用。

纯商品事实可沿用现有确定性模板，不强制调用模型。涉及说明/规则时复用现有 DeepSeek 生成器；组合回复在一个汇总位置合成。金额、售卖状态按工具事实核对，不能由模型改写成另一个值。最终只产生一条买家回复。

保留原 `sources`，工具引用和文档引用能区分。优先复用已有来源结构；确需扩展时，为工具证据增加可选的类型、商品编号和更新时间，不把工具事实伪装成 Markdown chunk，不复制一份完整商品数据到多个字段。

调试结果可记录工具名称、商品编号、实际知识来源和检索分数，但不要记录凭证或整段生产对话。检查 API 响应模型没有把必需的来源字段过滤掉。

#### 回答字段的统一语义

| 情况 | answer | can_answer | next_step |
| --- | --- | --- | --- |
| 所有问题都有充分依据 | 完整回答 | true | 沿用现有完成值 |
| 缺少商品编号等可补齐信息 | 已知部分 + 明确追问 | false | 沿用或补充澄清值 |
| 价格已知，维修史/售后条款未知 | 正确价格 + 未知说明 | false | human_handoff |
| 无可支持事实，或资料冲突 | 说明无法确认或查询失败 | false | human_handoff |

`can_answer=false` 不等于一定要把 `answer` 清空。接口或现有展示代码不能丢掉已经有依据的部分回复。本轮不扩建人工工作台，也不宣称人工已经接通。

`reliability` 不再作为整个请求的前置总开关。纯 MCP 请求可为 `null`；混合请求由证据汇总决定整体是否完整，不能把单个 RAG 子问题的通过状态直接复制为整体通过。需要保留 `route` 时，它只能描述 MCP/RAG 的使用情况，不能成为用户必须选择的模式。

### 3.4 统一链路通过后，立即完成第二轮删除

检查并删除已经被替代的“按 scene/scenario 提前返回不同客服”的逻辑，以及重复的 prompt、回答拼接、结果转换和错误兜底。删除前确认有效行为已经迁移到统一入口。

不同 collection 的两个配置项不一定是冗余；MCPService 和传输客户端职责不同，也不因有几层调用就一概删除。真正要消除的是重复业务实现，不是必要的职责边界。

**阶段成果：** 同一个 `/chat`、同一个会话同时具备商品和售后能力，代码里没有仍承载相同业务的两套长期分支。

## 7. 阶段 4：验收、收尾和交付

### 4.1 分清单元测试与真实联调

上传片段中的部分测试把 MCP、RAG 或 ChatService 替换为测试对象。[E1] pytest 的 monkeypatch 可替换函数和依赖，这适合隔离测试，但不能证明被替换的真实外部调用成功。[T3]

保留这些单元测试，额外完成三层验收：

| 层级 | 允许替代什么 | 必须证明什么 |
| --- | --- | --- |
| 单元测试 | 可模拟工具、检索和模型 | 组合计划、过滤范围、未知处理、会话隔离。 |
| 真实 MCP 联调 | 不替换 MCP 客户端或 Server | 三件商品与不存在编号的真实协议调用。 |
| 真实 `/chat` 联调 | 不替换 ChatService、MCP、Qdrant、BM25、Reranker 或所需生成器 | 不传模式能回答商品、规则和组合问题，证据来自真实链路。 |

价格请求不调用模型是合理实现，不要求为了测试人为调用。需要知识生成的用例则必须使用实际配置的模型，并记录失败/不可用情况。测试没有执行时写“未执行”，不能写 PASS。

按需求文档 A01—A14 逐项验收。售后规则、配件和未知字段先读真实资料建立预期；通过不能只看最终文字，还要核对工具调用与检索来源。

### 4.2 提供一个统一验收入口，避免用户手动拼调用

优先复用已有验收入口；如果现有脚本只测订单，新增一个 `scripts/smoke_unified_chat.py`，不要每个测试再写一个脚本。

本轮约定它支持从项目根目录运行：

```powershell
python -m scripts.smoke_unified_chat --base-url http://127.0.0.1:8000
```

它调用正在运行的真实 `/chat`，根据固定用例逐项记录输入、期望、响应和通过/失败原因，并保存到现有测试结果目录。已知价格/状态可以自动断言；开放式售后回答除来源与边界检查外，输出供人工核对，不能靠“包含售后二字”判定通过。

常规 pytest 不自动触发这类模型/服务联调；脚本不读闲鱼 Cookie、不发聊天消息、不改知识库、不改价格和售卖状态。通过本地 `/chat` 产生测试会话是预期行为，使用专门的 `qa_*` 会话编号。

### 4.3 最后整理与交付

删除迁移后不再引用的旧模式示例、废弃配置和死代码；重复跑相关测试及基线回归。旧测试若只断言废弃模式行为，应按新需求更新并保留原有效功能覆盖，不能删除失败测试躲避问题。

交付以下实际记录，写入现有项目说明或验收输出，不再创建一套庞大的文档系统：

```text
1. 修改/删除文件及理由
2. 第一轮和第二轮清理结果
3. 统一 /chat 的真实请求格式
4. 实际启动、入库、验收命令
5. A01—A14 的结果、证据与未解决问题
```

## 8. 给使用者的最短操作顺序

以下是本轮实现完成后的操作，不表示当前代码已经支持所有字段或已存在验收脚本。

### 第一步：启动项目

在 PowerShell 中执行；若已有旧 FastAPI 进程，先在对应窗口按 `Ctrl+C` 停止，再启动新代码：

```powershell
cd "D:\rag demo智能客服\ecommerce-ai-customer-service"
conda activate "D:\conda_envs\rag-customer-service"
python -m uvicorn app.main:app --reload
```

### 第二步：通过网页发一条统一问题

浏览器打开：

```text
http://127.0.0.1:8000/docs
```

找到 `POST /chat`，点击 `Try it out`，输入后点 `Execute`：

```json
{
  "query": "这个商品多少钱？收到有质量问题怎么办？",
  "chat_id": "qa_unified_001",
  "item_id": "DEMO_ITEM_001"
}
```

核对价格是否为 1280 元；售后内容是否与已确认条款一致。资料不全时应说明哪部分无法确认，不能只看到一句流畅回答就判定通过。

### 第三步：在同一会话继续问售后

```json
{
  "query": "那退货运费怎么处理？",
  "chat_id": "qa_unified_001"
}
```

不填模式，也不重新填商品。应使用适用的规则；没有运费条款就明确无法确认。

### 第四步：用新会话测试通用问题

```json
{
  "query": "你们店一般怎么处理售后？",
  "chat_id": "qa_general_001"
}
```

没有商品也应能检索通用规则，不应要求先“进入闲鱼模式”。

### 第五步：运行统一验收

另开 PowerShell，进入同一目录、激活同一环境，执行第 7.2 节的验收命令。按结果逐条检查需求文档的 A01—A14；代码没有按文档交付入口时，应标为未交付，不能再让使用者猜命令。
