# 闲鱼 AI 客服需求文档

> 版本：V2.0｜日期：2026-09-10  
> 配套文档：`02_闲鱼AI客服_技术文档.md`  
> 本版替代旧版的“草稿 → 逐条审核 → 发送”主流程。目标是 AI 自动客服，不是卖家回复辅助工具。

## 1. 项目目标与当前起点

### 1.1 最终要做成什么

买家在闲鱼发来咨询后，系统自动识别会话与商品，调用已有 `/chat`，利用商品事实和卖家规则生成回答，并自动发回闲鱼。正常咨询不需要卖家逐条查看、修改或点击发送。

人工只负责维护商品资料、处理机器人无法解决的个别问题，以及登录失效等运行异常。验收时要证明“人在不盯着聊天窗口时，普通咨询仍能自动完成”，而不是只证明 AI 能生成文本。

### 1.2 已有能力，本次不重建

根据项目方提供的进度，已完成当前商品识别、商品上下文，以及同一条 `/chat` 中的商品事实与卖家通用规则处理。现有 RAG、MCP、Embedding、Reranker、Qdrant 和回答模型继续使用。

这些是需求输入，不代表本文已经审计本地代码。开发开始时只需确认现有接口与回归测试，不再建设第二套客服大脑。

### 1.3 关于参考模板的说明

当前可读取的历史及旧文档没有保留原先闲鱼模板的准确仓库地址，**尚不能确认哪一个仓库就是此前指定的模板**。本次实际核查了公开项目 `shaxiu/XianyuAutoAgent` 的收发、上下文和部署源码，技术文档列明版本与对应位置；它是本版的公开技术参考，不冒称已确认的原模板。[S1]

实施阶段 S1 要优先核对本地原模板的地址和版本；若与上述参考不同，以原模板的真实收发实现为准，修正渠道映射。本文的自动客服目标、已有 `/chat` 复用原则和验收要求不因此改变。

公开代码存在，不等于目标账号当前能够稳定接通，更不等于平台承诺允许或长期支持该接入方式。必须完成目标账号实测，并核对平台使用要求。本文不包含绕过验证码、规避账号限制或使用他人登录凭据。

## 2. 第一版范围

第一版聚焦一个卖家账号、已配置的商品和文本咨询。卖家配置好资料并一次性启用后，范围内的正常问题由 AI 自动处理。

| 本版需要实现 | 本版不作为前置条件 |
|---|---|
| 真实买家消息接收、真实回复发送 | 多账号、多店铺、营销群发 |
| 正确会话和商品映射，连续追问 | 重新训练模型、改造检索算法、多 Agent |
| 商品事实、卖家规则及两者组合回答 | 复杂客服后台、逐条审核页面 |
| 自动澄清、异常转人工、随时暂停 | 自动改价、退款、赔偿、发货等业务写操作 |
| 消息去重、重连、重启恢复、异常通知 | 图片或语音理解、跨平台统一客服 |
| 商品维护、备份、运行记录 | 没有真实数据来源的订单和物流查询 |

已有订单 MCP 的演示数据不能用于真实买家回复。后续增加订单查询，要另行完成真实数据接入与订单归属校验。

## 3. 正式工作流程与客服行为

```text
买家在闲鱼咨询
  → 接收并识别买家、会话和商品
  → 排除重复消息、机器人回显、无需回复的系统事件
  → 调用已有 /chat：商品事实 + 卖家规则
  → 根据结果执行：
       answer         → 自动发送回答
       clarify        → 自动发送澄清问题
       human_handoff  → 建立待人工事项、暂停该会话、通知卖家
       ignore         → 不发送
  → 保存处理与发送结果
```

### 3.1 哪些情况 AI 自己处理

| 买家问题 | 预期行为 | 必须遵守的边界 |
|---|---|---|
| “带原装充电器吗？” | 查询当前商品，自动回答 | 资料必须明确记载，不能由商品型号推测配件 |
| “摔过吗？”“修过吗？” | 有明确记录则自动回答 | 没记录不是“没摔过”；需确认时转人工 |
| “一般什么时候发货？” | 依据卖家有效规则自动回答 | 通用安排不是某笔订单已经发货的证明 |
| “带数据线吗？什么时候发货？” | 同轮结合商品事实与规则自动回答 | 不能答出一半后编造另一半 |
| “那另外一台呢？” | 有明确商品关联则切换；有歧义则自动追问 | 不要求买家输入内部 `DEMO_ITEM_001` |
| “退款规则是什么？” | 规则明确且适用于当前卖家时自动说明 | 解释规则不等于批准退款 |
| “便宜 500 卖吗？” | 有明确卖家策略时按策略答；否则转人工 | 不自行创造底价，不执行改价 |
| “给我退款／赔偿”“我要投诉” | 转人工 | 不代卖家承诺赔付或裁定争议 |
| 发来暂不支持的图片或语音 | 自动请求文字说明；仍处理不了则转人工 | 不假装已经理解附件 |
| 平台系统通知、自己的回复回显 | 忽略或更新状态 | 不能形成机器人回复自己的循环 |

商品资料只有部分答案时，可以自动回答已确认部分并明确哪一部分需要卖家确认；涉及关键判断不能靠无依据补全。连续两次澄清仍不能定位问题时转人工，避免反复追问。

### 3.2 自动运行不是逐条审核

正式会话只有 `AUTO`（机器人处理）与 `HUMAN`（人工接管）两类工作状态；账号另有总暂停开关。

开发可以使用模拟消息，首次联调可以使用固定测试回复，但它们只是技术验证。**不设置“卖家必须审核每条 AI 答案”这一产品流程，也不建设草稿审批系统。** 新安装先关闭真实发送，卖家完成配置并明确启用一次；启用后不再逐条确认。

### 3.3 转人工必须实际可用

转人工要同时做到：保存问题与原因、将会话切到 `HUMAN`、阻止新的普通 AI 回复、通知卖家。只返回一个 `human_handoff` 字段不算完成。

渠道正常时，可自动发送一次说明：“这个问题需要卖家确认，已记录，卖家看到后会处理。”不承诺无人负责的响应时间。卖家通过闲鱼原生界面回复，处理后明确恢复机器人；不靠一个定时器自动解除人工接管。

卖家原生发言能可靠识别时触发接管；无法识别时，必须支持“先接管，再用闲鱼回复”。机器人自身回显不能被误判为人工发言。暂停生效后不能再启动新发送，但已提交给平台的在途消息可能无法撤回。

## 4. 核心需求

| 编号 | 需求 | 完成后的表现 |
|---|---|---|
| R01 | 真实渠道收发 | 买家消息能进入程序，程序回复能在正确买家会话中看到 |
| R02 | 买家、会话、商品映射 | 同一会话持续追问不丢商品；换买家、换商品不串线 |
| R03 | 复用现有客服链路 | 商品事实和规则继续由现有 `/chat` 处理，不另接一套 LLM 取代它 |
| R04 | 自动回答与澄清 | 正常咨询和补充问题自动发送，不逐条人工批准 |
| R05 | 人工接管与暂停 | 异常进入可见待办；卖家能暂停账号、接管和恢复单个会话 |
| R06 | 消息与发送可靠性 | 不重复回复、不自聊；发送失败与结果不明可区分，不能无条件重发 |
| R07 | 常驻与恢复 | 关闭终端仍运行；短暂掉线、进程退出后能恢复；登录失效能通知 |
| R08 | 记录、状态与通知 | 能查消息处理结果、当前故障、待人工事项，负责人能实际收到通知 |
| R09 | 数据维护与备份 | 商品和规则变更能生效；重启不丢接管状态；备份可实际恢复 |

正常自动回答仍使用现有模型。程序只负责检查动作、接收对象、会话状态和明显异常，不再添加一套重复的客服推理系统。

## 5. 分阶段实施需求

阶段顺序固定为：**真实接收 → 可控发送 → AI 自动闭环 → 常驻恢复 → 长期运行验收**。各阶段的详细技术步骤见配套文档同名章节。

### S1：核对模板并接收真实消息

**要解决的问题：** 闲鱼里发生的咨询，能否准确进入当前项目？

依次确认原模板及版本、运行环境与账号连接方式，隔离模板原 AI 发送路径，然后接收真实测试咨询，记录买家、会话、商品和消息标识。保存脱敏报文用于后续测试。

**本阶段完成后：** 程序能识别真实买家咨询；此时没有 AI 自动发送，原因是收发适配尚在实现，不是要求卖家长期审核。

**验收：** 两件商品、两个参与测试的买家，至少 10 条授权测试消息全部映射正确；模拟重投和非文本事件可识别。原模板地址缺失、连接未成功等情况必须如实记录，不能用“Adapter 类已经写好”代替接入完成。

### S2：跑通可控的消息发送

**要解决的问题：** 程序能否把一条文本发给正确买家，且不会重复发、自己回自己？

先在授权测试会话中，收到指定测试消息后自动发送固定测试文本；同时完成基本去重、发送记录、账号暂停、单会话接管和自身回显识别。这些基础控制不能推迟到真实 AI 自动回复之后。

**本阶段完成后：** 已具备“闲鱼消息 → 程序 → 闲鱼回复”的自动收发通道，尚未接入 AI 内容。

**验收：** 至少 10 次指定测试咨询收到正确回复，不需要点击发送；同一消息重投 3 次只产生一次有效回复；暂停后新消息不再触发发送。明确区分本地提交、平台确认和买家侧看到三种证据。

### S3：接入 `/chat`，实现 AI 自动客服 V1

**要解决的问题：** 把固定回复换成现有商品事实与规则客服，让正常咨询无人逐条操作也能完成。

完成平台商品映射和真实商品资料确认；将模板原 AI 调用替换为现有 `/chat`；根据 `answer / clarify / human_handoff / ignore` 执行动作。实现人工待办和有效通知，验证不同买家、三轮追问和换商品。

**本阶段完成后：** 买家提问后，AI 自动查询、回答和发送；必要时自动追问或转人工。卖家不需要守着审批页面。

**验收：** 第 6 节的 40 条客服测试集通过规定门槛；其中至少 10 条使用真实测试会话完成“发问到收到 AI 回复”，包含商品事实、卖家规则、混合问题和三轮追问。正常自动处理路径中，人工发送确认次数必须为 0。

### S4：常驻部署与故障恢复

**要解决的问题：** 卖家退出终端或短时不在线时，机器人仍能工作；故障后不会乱发。

复用并核实模板心跳、登录维护与重连，补齐进程自动启动、持久化恢复、发送结果不明处理、异常通知和备份。部署在满足当前模型资源需求的常开主机上。

**本阶段完成后：** 网络恢复和普通进程退出可自动恢复；需要重新登录时停止自动发送并通知卖家；已发消息不会因重启再次发送。

**验收：** 完成断网、杀进程、主机重启、模型超时、登录失效和备份恢复演练；连续观察至少 24 小时。登录维护及历史补消息能力要以实测结果说明，不能承诺 Cookie 永久有效或掉线消息必然全部补回。

### S5：长期试运行与日常维护

**要解决的问题：** 证明它不只在演示时成功，而能持续替卖家处理咨询。

在已配置商品范围中运行至少 7 个连续自然日，统计自动解决、澄清、转人工、失败和告警；收集错误案例，更新商品资料与规则，并验证版本回退和恢复流程。

**本阶段完成后：** 可称为“单账号、小规模长期运行的闲鱼 AI 客服 V1”。不是零维护、永不掉线或平台永久兼容的保证。

**验收：** 满足第 6 节全部长期运行门槛。咨询量不足时如实标记“时间观察通过、样本不足”；不能把模拟回放混进自然咨询数量，也不向真实买家批量制造测试消息。

## 6. 验收标准：怎么证明真的完成

以下数量、比例与时间是本项目拟定的 V1 验收目标，**不是行业统计、平台承诺或已测试成绩**。开始验收前固定测试数据、机器配置和统计口径，失败后不能临时降低门槛。

### 6.1 关键验收用例

| 编号 | 操作或输入 | 必须观察到的结果 | 阶段 |
|---|---|---|---|
| AC01 | 两名买家分别咨询两件商品 | 买家、会话、商品匹配正确 | S1 |
| AC02 | 接收一个包含多条事件的同步包 | 每条有效事件都处理，不只读取第一条 | S1 |
| AC03 | 授权测试消息触发固定回复 | 正确买家收到自动发送文本，无点击发送 | S2 |
| AC04 | 同一消息重复投递 3 次，再重启 | 不新增重复业务回复；相同文本的新消息不误去重 | S2、S4 |
| AC05 | 机器人自己的消息回流、平台通知 | 不回复自己；不误触发接管 | S2 |
| AC06 | 商品 A：成色如何 → 摔过吗 → 带线吗 | 三轮都使用 A 的真实资料；未知事实不编造 | S3 |
| AC07 | 同会话明确换商品 B，再问配件 | 改用 B；无法判断时自动澄清 | S3 |
| AC08 | 同轮问“带线吗，什么时候发货” | 商品事实与卖家规则一起回答 | S3 |
| AC09 | 缺少关键定位信息，返回 clarify | 自动发出澄清，即使 can_answer 为 false | S3 |
| AC10 | 询问退款规则；另一次要求退款赔偿 | 前者可解释有效规则，后者转人工，不执行退款 | S3 |
| AC11 | 触发转人工、卖家接管、程序重启 | 待办可查、通知收到；接管仍有效，恢复前不抢答 | S3、S4 |
| AC12 | 生成过程中点击暂停／执行接管 | 未开始发送的旧答案不再发送；在途结果可核对 | S3 |
| AC13 | 模型或 MCP 超时、抛错、返回空值 | 不发送报错堆栈，不无限重试；转待人工并记录原因 | S3、S4 |
| AC14 | 临时断网后恢复；Cookie 确定失效 | 前者重连；后者通知重新登录，不无限重启或终端等待输入 | S4 |
| AC15 | 平台可能已收消息，但本地等待超时 | 标记结果不明；无可靠依据不得自动重发 | S2、S4 |
| AC16 | 杀进程、关闭终端、重启主机 | 服务自动恢复；消息记录、商品关联和接管状态保留 | S4 |
| AC17 | 商品配件或卖家规则变化 | 发布后新咨询使用新资料；旧版本待发回答不被误发 | S4、S5 |
| AC18 | 恢复备份；监测整机掉线 | 恢复后先核对，不批量重发；独立监测方实际发出告警 | S4、S5 |

### 6.2 客服质量与自动化验收

准备固定的 40 条独立测试咨询：24 条资料充分、应直接回答的问题；8 条应澄清的问题；8 条应转人工或忽略的问题。另含至少 4 组、每组三轮的连续会话测试，可与上述咨询对应，需标明会话关系。

- 24 条应回答问题中，至少 22 条正确自动回答并发送；不得全部转人工来“保证不出错”。
- 8 条澄清及 8 条转人工／忽略问题，动作全部正确；其中明确未知的跌落、拆修事实不能被编成肯定结论。
- 错买家、错商品、重复业务回复、泄露凭据、越权执行写操作为 0；真实发送测试中不依赖逐条审批。

正确回答需同时满足事实正确、规则适用、没有无依据承诺和发到正确会话。不按“有输出”“HTTP 200”或检索分数判定正确。

### 6.3 长期运行门槛

| 检查项 | 通过条件 |
|---|---|
| 观察时间 | 连续 7 天；严重问题修复后重新观察受影响链路 |
| 样本量 | 至少 100 条有效渠道咨询；自然咨询与获授权测试咨询分别列数，测试样本不冒充自然流量 |
| 自动化效果 | 对经事后核对属于“资料充分、正常自动范围”的咨询，正确自动回答比例至少 90%；明确列出分母 |
| 响应时间 | 正常负载、依赖可用时，至少 95% 自动回答在收到消息后 60 秒内取得可核验的平台接收确认；无该确认能力时报告买家侧抽查耗时，不冒充机器确认指标 |
| 故障恢复 | 在测试网络恢复且凭据有效的前提下，渠道 2 分钟内重新接通；模型冷启动单独记录，恢复后再验证完整自动问答 |
| 异常通知 | 可检测故障在 5 分钟内送达配置好的负责人；整机失联由独立于该主机的监测发现 |
| 发送可靠性 | 验收样本中无错收件人、无重复回复；所有结果不明均有明确记录和处置，不从分母删除 |
| 数据恢复 | 至少一次恢复成功；恢复后会话、接管和商品映射可核对，历史回复不被批量重发 |

这组试运行结果只能证明该版本、账号、商品范围和测试环境下达到小规模目标，不能推导出无限流量或永久可用。

## 7. 卖家实际需要做什么

**正常使用：** 配好账号和商品，一次性开启自动客服；机器人处理普通咨询，卖家不逐条审核。

**收到通知：** 登录失效就重新登录；需要确认商品事实或处理争议，就在原生闲鱼接手该会话。人工处理完成后明确恢复机器人，不将所有新咨询都变成人工任务。

**维护资料：** 商品售出、配件变化、价格或承诺调整时更新资料；每日查看异常和待人工事项，每周抽样复盘自动回复。事后抽查用于改进，不阻塞每条消息发送。

**维护服务：** 每日自动备份，至少保留一份异机副本；更新程序前保留可回退版本。7 天验收必须覆盖至少一次商品更新与故障恢复，不能只让程序空跑。

长期运行的含义是“正常工作自动完成，常见故障能恢复，少数异常有人处理”，不是要求卖家每天陪着机器人工作，也不是完全不需要任何维护。

## 8. 交付与执行约束

每个阶段只交付该阶段的代码、测试结果和必要运行说明，记录通过、失败与未验证事项。先读现有代码，再增量修改；普通测试不用真实买家，不下载模型，不为接闲鱼更换现有检索方案。
