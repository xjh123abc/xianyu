# 闲鱼 AI 客服技术文档

> 版本：V2.0｜日期：2026-09-10  
> 配套需求：`01_闲鱼AI客服_需求文档.md`  
> 实施主线：复用参考项目的闲鱼收发连接，把原来的 AI 调用替换成现有 `/chat`，再补齐长期运行能力。

## 1. 实施基线：哪些已经有，哪些这次才做

已有商品上下文、RAG + MCP 和统一 `/chat` 以项目方提供的完成情况为输入。本次不重建它们；也没有读取或测试用户 Windows 本地仓库。因此，下文新增目录、接口、配置与命令是**开发约定**，不能当作当前已经存在的代码。

当前可读取材料未保留原先指定的闲鱼模板地址。本次实际读取的公开参考是 `shaxiu/XianyuAutoAgent`，固定提交：

```text
540bbc26cf02ee6348d997843942776a9be9460b
```

不能把它冒称为已确认的原模板。S1 先核对本地原模板；若不同，更新本节和渠道代码映射，继续沿用“收消息 → 现有 /chat → 自动发送”目标。不要因此重新设计客服核心。

### 1.1 公开参考实际怎样运行

下表是源码事实，不是对当前账号可用性的保证。[S1][S2][S3][S4]

| 环节 | 实际位置 | 本项目怎样处理 |
|---|---|---|
| 登录凭据与连接令牌 | `XianyuApis.py` 的 `get_token`、`hasLogin` | 复用已验证的连接方式；失效改为可通知、可恢复的状态 |
| 长连接注册和收消息 | `main.py` 的 `XianyuLive.init/main` | 封装为独立渠道连接器 |
| 解析消息、买家和商品 | `handle_message` | 标准化后进入现有 `/chat`，补消息缺失和换商品处理 |
| 原来的 AI 调用 | `bot.generate_reply(...)` | 替换为 `ChatApiClient`，不保留第二套回答模型 |
| 将文本发回闲鱼 | `send_msg` | 保留协议封装，增加去重、暂停检查和发送结果记录 |
| 连接维护 | `heartbeat_loop`、`token_refresh_loop` | 复用意图，核实超时确实触发重连 |
| 历史持久化 | `context_manager.py` 使用 SQLite | 借鉴轻量存储，不再复制一套与现有 Memory 竞争的上下文 |
| 常驻部署 | `docker-compose.yml` 的重启及目录挂载 | 采用自建、固定版本镜像，并增加核心 API 与状态检查 |

这条参考链路本身就是生成后直接发送，没有逐条人工审批环节。它使用网页登录凭据及 WebSocket 实现收发，并非本文已经取得的官方聊天 SDK。[S1][S2]

### 1.2 不原封不动照搬的地方

参考实现有定时退出人工模式、缺商品 ID 直接返回、同步包只取首项等处理；发送函数完成本地 WebSocket 写入即返回；令牌异常分支还可能要求终端输入凭据。[S1][S2]

本项目因此补齐四件事：逐项处理有效消息并保留商品上下文；人工状态持久化且明确恢复；确认发送结果而非只记录函数返回；常驻服务遇到登录问题发通知，不挂在 `input()` 上。这些是长期自动客服的必要增量，不是重写整套系统。

复制或修改参考代码时记录来源，核对并遵守仓库 `LICENSE`。真实使用还需核对平台及目标账号的使用要求；公开代码能演示收发，不代表平台承诺长期兼容。[S0]

## 2. 技术选择与最小架构

### 2.1 采用哪些技术

| 部分 | 本版选择 | 具体作用 |
|---|---|---|
| 客服核心 | 现有 Python、FastAPI、RAG、MCP | 保留商品事实和卖家规则统一回答 |
| 闲鱼收发 | 参考模板已验证的 Python WebSocket 客户端 | 收事件、维护连接、发送文本；不新增客服推理 |
| 并发处理 | `asyncio`，接收、保活、业务处理分开 | 等待模型时仍能接收心跳和消息 |
| 调用 `/chat` | HTTPX `AsyncClient` | 异步调用、连接复用，分别设置网络超时与总期限 [S6] |
| 渠道状态 | SQLite + Python `sqlite3` | 保存消息处理结果、接管状态、商品映射；无需新增数据库服务 [S7] |
| 单实例保护 | 现有锁工具；没有则使用 `filelock` | 同一账号只允许一个收发进程，防重复启动 [S11] |
| 日志与测试 | 现有日志库、pytest、脱敏事件回放 | 定位哪条消息在哪一步失败 |
| 常驻部署 | Docker Compose + 常开主机 | 独立启动核心 API、渠道进程和现有 Qdrant [S9] |
| 人工控制与通知 | 本地控制命令 + 一种现有可用通知渠道 | 暂停、接管、恢复、查看待办，不建设审批后台 |

有等价持久化实现就复用，不为了本文强制迁移数据库。没有时采用 SQLite；本版不新增 PostgreSQL、Redis、Celery、Kafka 或多 Agent。

参考依赖文件锁定了 `websockets==13.1` 等版本。[S5] 先在隔离环境验证模板，再与当前环境做依赖检查；不要把模板全部依赖覆盖进现有项目。`websockets` 新旧实现的导入及参数有变化，照抄旧代码却安装最新依赖可能不兼容，按实际通过测试的版本锁定。[S10]

### 2.2 最小运行结构

```text
闲鱼买家
   ↕
独立 xianyu-worker：连接、解析、去重、发送、控制
   ├─ SQLite：渠道状态、消息账本、商品绑定
   ├─ 通知：需要人工／登录失效／运行异常
   └─ 内网 HTTP → 现有 FastAPI /chat
                       ├─ 现有商品上下文与 Memory
                       ├─ MCP：商品事实
                       ├─ RAG：卖家规则
                       └─ 现有回答模型
```

渠道进程不加载 Embedding 或 Reranker；模型仍由现有 API 进程管理。初版只运行一个 API worker、一个渠道 worker、一个生成消费者，不为尚未出现的并发量增加副本。

渠道进程内，接收循环只做协议处理和短时间落库；业务消费者再调用 `/chat`。`asyncio.Queue` 只能用于唤醒或调度，数据库才是重启后的消息账本。不要在接收循环里同步等待一次完整模型推理。

## 3. 渠道消息怎样进入现有 `/chat`

### 3.1 标准消息与字段映射

下面是本项目内部结构，不是闲鱼官方报文；示例 ID 均为占位值。

```json
{
  "channel": "xianyu",
  "seller_id": "seller_example",
  "buyer_id": "buyer_example",
  "platform_chat_id": "conversation_example",
  "platform_message_id": "message_example_001",
  "platform_item_id": "item_example_a",
  "message_type": "text",
  "text": "这台相机带数据线吗？",
  "sent_at": "2026-09-10T12:00:00Z"
}
```

从真实样本核实字段：参考实现从聊天内容的发送者字段取买家，从会话字段取聊天 ID，从关联地址提取商品 ID。[S1] 样本必须包括首次咨询、后续追问、商品切换、卖家发言和系统通知，不能只用一种报文套全部消息。

特别核实：外层包的请求 ID 不一定是业务消息 ID；重连后是否稳定，要重放验证。同一同步包包含多项时逐项处理。协议 ACK 与业务消息保存的顺序按实测协议决定，不能猜测“不 ACK 就必然重投”。

### 3.2 会话和商品绑定

| 对象 | 约定 |
|---|---|
| 内部 `chat_id` | 使用带渠道、卖家和平台会话命名空间的稳定标识；重启不变 |
| 买家身份 | 来自可信渠道事件，保存并核对与会话归属，不由模型决定 |
| 商品映射 | `seller_id + platform_item_id → 当前 MCP 使用的真实 item_id` |
| 当前商品 | 当前消息有可信关联则更新；没有则使用本会话已确认商品；歧义则澄清 |
| 收件对象 | 始终来自原入站会话和经过校验的买家 ID，不接受 LLM 输出覆盖 |

不能让所有会话共用 `chat_id="string"`，也不能把所有闲鱼商品映射到 `DEMO_ITEM_001`。卖家未确认的演示知识库规则不得自动变成真实经营承诺。

对于当前价格、库存和是否仍在售等动态问题，要查询已接通的有效数据源；未实现刷新时不把旧商品缓存当实时状态。该能力未接通的动态咨询转人工，不妨碍配件、成色记录和通用规则继续自动回答。

原来商品上下文在哪里维护，继续以那里为唯一业务事实来源；渠道只保存映射和投递状态。现有会话存储若只在内存中，补一个持久化实现，不另保留模板的 AI 历史管理器作为第二个权威来源。

### 3.3 对接请求与返回动作

先按真实请求模型调用，保留已有三个主字段：

```json
{
  "query": "这台相机带数据线吗？",
  "chat_id": "xianyu:seller_example:conversation_example",
  "item_id": "LOCAL_ITEM_A"
}
```

`LOCAL_ITEM_A` 必须由实际映射取得。先读取现有 Pydantic 请求模型和 `/chat` 返回结构，不能按本文示例猜测已支持所有字段。

| 核心返回动作 | 渠道执行 |
|---|---|
| `answer` | 非空有效回答自动发送；事实和规则判断继续由现有核心负责 |
| `clarify` | 自动发送面向买家的澄清；`can_answer=false` 不阻止澄清发送 |
| `human_handoff` | 进入待人工，暂停该会话，发通知；可发送一次固定说明 |
| `ignore` | 记录原因，不发消息 |
| 无动作、冲突字段、空回答或无效结构 | 作为异常转人工，不靠有文本就发送 |

旧字段存在 `clarify_question` 等命名时，在边界处做显式映射，并测试真实响应。保留原有 `route`、`sources` 和 `reliability`，不要求 MCP 回答也必须有 RAG 分数，不用新的统一阈值把商品事实答案拦掉。

### 3.4 “已生成”和“已发送”要分开记录

中间结果自动落库不代表要求卖家审批。它只用于处理发送失败和重启恢复。

检查现有 Memory：若 `/chat` 一返回就把助手文本记为买家已经见过，增加可选的渠道投递模式：回答先记为 `pending_delivery`，确认发送后再纳入“已对买家说过”的历史。Web 调用保持原行为。

建议最小扩展：可选 `request_id` 关联同一入站消息，并对用户历史和生成结果去重；一个受保护的投递确认服务按 `request_id` 幂等提交实际发送文本。新增字段名称由现有模型规范决定，但上述语义必须实现。

发送失败或结果不明时，不把候选回复当成已经发出。确认后历史提交失败，可以只重试本地提交，不能再发一次消息。卖家真实回复也要进入同一会话历史，机器人回显不能重复记账。

## 4. 消息、状态与人工控制怎样保存

### 4.1 四类必要数据

优先扩展现有表；以下名称仅是建议。

| 表 | 关键内容 |
|---|---|
| `channel_state` | 卖家账号、发送开关、启用时间、登录状态、最近保活、断线缺口、控制版本 |
| `channel_sessions` | 平台会话、内部 chat_id、买家、AUTO/HUMAN、接管原因、通知状态、控制版本 |
| `channel_messages` | 稳定消息 ID、入站内容与时间、处理动作、候选及实际发送文本、发送请求 ID、状态、错误、数据版本 |
| `item_bindings` | 卖家和平台商品到现有 item_id 的绑定、资料版本、启用状态 |

现有 Memory、商品事实和规则依旧存放在它们原有位置。未发送的候选、发送回执和人工待办可以直接挂在消息记录中，不为了名词再拆一套审批表、工单平台或消息中间件。

普通日志只记录定位问题所需信息，聊天正文保存在受控存储；Cookie、Token、模型密钥不写入业务表或日志。默认聊天明细保留期可设为 30 天，实际按卖家需要和适用要求配置；清理记录不能重新激活旧消息，超过保留窗口的历史重投只留诊断、不自动补发。

### 4.2 去重、顺序与单实例

入站消息以“账号 + 平台稳定消息 ID”为唯一键；若平台仅保证会话内唯一，加入会话 ID。不存在可靠 ID 时必须核实替代标识及碰撞风险，不能用“同样一句话”去重。

先写入消息记录，再进入业务处理；重复键命中只更新必要接收信息，不再生成和发送。数据库提交失败时停止正常处理并告警，不把消息悄悄扔进内存就称为可靠接收。

初版全局一个生成消费者，同会话按可靠顺序号或本地到达顺序处理。没有平台顺序保证时如实记录，不宣称还原了绝对顺序。新的可信商品切换或人工操作使旧处理中答案失效，发送前检查上下文版本。

启动时对本机持久化目录中的账号锁文件获取排他锁；第二个同账号进程无法获取就退出。`filelock` 可提供跨进程锁，但本方案仅用于同主机本地磁盘，不当成分布式锁。[S11]

### 4.3 发送结果与重启规则

```text
RECEIVED → PROCESSING → READY → SENDING
                                  ├─ CONFIRMED：有已核实的有效回执
                                  ├─ FAILED：确认未成功
                                  └─ UNKNOWN：可能已发，但无法确定

其他终态：IGNORED、HUMAN_REQUIRED、SUPERSEDED（已过时或被人工处理）
```

在 `SENDING` 前保存最终文本与稳定发送请求标识，不能先发再补账。若仅完成 `ws.send`，只记录“本地已提交”，等待已验证的回执或可靠自身回显；**它不是买家已收到或已读的证明**。参考发送函数需要补的就是这层结果关联。[S1]

回执按请求标识区分注册、心跳与发送，不能把任意 `code=200` 都当作心跳成功并直接吞掉。没有可核实回执或查询能力时，发送确认属于已知限制，不能编造确认字段。

明确未发出且允许重试的临时错误，有限重试；可能已发出的超时进入 `UNKNOWN`，先对账，不盲目重发。平台支持真正幂等时使用同一个幂等键；本地 UUID 本身不证明平台具备幂等能力。

| 重启时已有状态 | 恢复方法 |
|---|---|
| RECEIVED／PROCESSING | 核对已保存结果；在时效内继续，用户历史按 request_id 去重 |
| READY | 重查账号、人工状态、商品与规则版本，再决定发送 |
| SENDING 没有可靠确认 | 转 UNKNOWN，先核对；不能直接重发 |
| CONFIRMED | 不再发送，只补尚未完成的本地历史提交 |
| HUMAN_REQUIRED／SUPERSEDED | 不自动回复；人工处理或过时状态继续保留 |

### 4.4 人工接管不能和发送抢跑

暂停、接管和发送许可使用同一数据库控制版本，并在短事务中串行更新。SQLite 可用 `BEGIN IMMEDIATE` 建立写事务；它仍可能遇到锁等待，需有限等待与明确错误处理，不能在事务中等待模型或网络。[S8]

发送前事务检查：账号已启用、会话允许自动、版本未变化、消息未过期、没有已确认或不明的重复发送，然后将该条标记为 `SENDING`。暂停或接管事务生效后不能再取得新发送许可；已经取得许可的视为在途，允许其完成并保存结果。

自动转人工产生的“一次性说明”是独立受控类型，只允许当前接管事件发送一次，仍受账号暂停与版本检查；不能借它绕过人工接管持续输出普通答案。卖家明确接管会使尚未发送的旧答案和旧说明失效。

CLI 或已有页面至少提供：状态、全局暂停、全局恢复、会话接管、会话恢复、待人工列表、发送不明核对。会话恢复不批量发送接管期间的旧答案；这些消息应由人工处理或标记过时，恢复主要面向后续新消息。

## 5. 分阶段实施步骤

### S1：核对模板并接收真实消息

**对应需求：R01、R02。产出：能接到真实买家咨询的渠道连接器。**

1. **确认两个仓库。** 在原模板目录记录远端地址和提交号，在当前项目读取 `/chat`、商品工具、Memory 与配置。没有原模板地址时标注未确认，不将公开参考默认改称原模板。
2. **先隔离运行参考连接。** 独立环境安装经过检查的依赖，使用卖家有权使用的登录凭据；先切断原 `bot.generate_reply → send_msg` 路径。不要直接启动模板原程序后让它用旧 Prompt 回复真实咨询。
3. **沿模板连接主线定位。** 核实凭据读取、Token 获取、WebSocket 注册、同步事件和心跳。相关协议代码集中封装，不让字段路径散落到 RAG 中。
4. **收集真实样本。** 两名参与测试的买家对两件商品发送至少 10 条消息；保存脱敏样本，核对买家、会话、商品和稳定消息 ID。明确记录平台是否支持断线补消息和发送回显，不预设具备。
5. **实现标准化与持久化。** 建立最小消息账本，逐项解析同步包，区分文本、系统事件、卖家消息和附件；未知报文只记录必要诊断并告警，不让整个监听器退出。

**验证方法：** 用脱敏样本做解析测试，真实会话人工核对字段；满足 PRD 的 AC01、AC02。真实收消息未成功就不能标记 S1 已完成。

**本阶段不做：** 不调用新的 AI，不重写 RAG，不建设人工审核页面。

### S2：跑通可控的消息发送

**对应需求：R01、R05、R06 的基础。产出：自动固定文本收发闭环。**

1. **复用发送封装。** 将模板发送方法封装成唯一出口，发送对象只能来自已校验的入站会话。先只对配置好的测试会话启用固定文本自动回复。
2. **先补去重和单实例。** 同消息重投只处理一次；重复启动同账号进程必须失败；系统通知和机器人回显不触发新的回复。
3. **核实回执。** 在买家侧确认回复，同时关联本地发送 ID、回执和自身回显。区分本地提交与平台确认，记录协议无法确认的边界。
4. **实现控制。** 增加账号暂停和会话接管，状态写库。发送前再次检查控制版本；模拟生成或发送延迟，验证暂停时旧回复不会在之后突然出现。
5. **测试发送异常。** 模拟发送前连接中断、平台已接收但本地超时。前者按确认信息有限重试；后者标 UNKNOWN，不能再次盲发。

**验证方法：** 至少 10 次指定测试咨询自动收到固定回复；重投 3 次不重复；买家侧、发送记录与会话一致。通过 AC03—AC05、AC15；初步验证 AC12。

**重要：** 这不是卖家批准后发送，程序本身已经自动发；固定文本仅用于把连接问题和 AI 问题分开验证。无法得到任何可靠回执或自身回显时，可记录“买家侧实测收到”，但后续自动确认与发送恢复能力仍为未完成，不能包装成长期运行已验收。

### S3：接入 `/chat`，实现 AI 自动客服 V1

**对应需求：R02—R06、R08 的业务部分。产出：真正自动回答的闲鱼客服。**

1. **确认真实商品资料。** 建立平台商品与 MCP 商品记录映射，核对配件、成色、拆修记录、卖家发货与售后规则。原演示资料未确认前不对买家使用。
2. **替换原 AI 调用。** 用 `ChatApiClient` 调用现有 `/chat`，移除渠道侧原专家分类、议价模型和第二套历史拼装。模板的网页商品信息可接入现有商品存储，但不绕过 MCP 另塞入一份冲突事实。
3. **接好四种动作。** answer 和 clarify 自动发送；human_handoff 建立待办、通知并暂停会话；ignore 不发。遇到字段冲突、空答案和异常时有明确降级，不直接发内部 JSON。
4. **接好唯一会话历史。** 核实 request_id 去重、候选与实际发送的区分；三轮追问使用同一 chat_id。商品切换、人工接管与资料版本变化，使旧结果失效。
5. **把通知真正发出去。** 选择卖家现有可用的一个通知渠道，例如其已配置的 SMTP 邮箱；内容包含会话、商品和原因，不包含登录密钥。测试负责人确实收到，不只检查返回码。
6. **验证自动闭环。** 跑 PRD 的 40 条测试集，再选至少 10 条通过真实测试会话发问与收答，覆盖商品事实、规则、混合问题及三轮上下文。普通路径不要求卖家点击发送。

**验证方法：** AC06—AC13 全部按预期；24 条应答题至少 22 条正确自动回答，动作边界全部正确，关键安全错误为 0。原有 RAG/MCP 回归仍通过。

**本阶段结束后：** AI 自动客服 V1 已具备功能闭环；可以进入受控运行，但还不能宣称已经完成长期稳定性验收。

### S4：常驻部署与故障恢复

**对应需求：R06—R09。产出：关闭终端仍工作、常见故障可恢复的服务。**

1. **拆开收消息与业务等待。** 接收、心跳、令牌维护和业务消费独立运行。同步网络调用设置真实网络超时，必要时使用受限线程执行；不能把协议参数里的 timeout 当作 Python HTTP 请求一定会终止。
2. **核实心跳是真保活。** 关联心跳请求与回应；超过设定期限没有有效回应，应关闭旧连接、清理旧任务并建立新连接，而不是仅结束心跳协程。WebSocket 协议 Ping/Pong 与模板业务心跳分别处理，不能混为同一种。[S10]
3. **统一登录状态。** 凭据与刷新后的 Cookie 使用同一个管理入口，并让重连使用更新后的值。短暂网络错误退避重连；确定失效或需要验证时进入 `AUTH_REQUIRED`，暂停发送并通知卖家。后台不执行交互式 `input()`，不因同一个失效凭据无限重启；卖家通过正常登录恢复后再验证连接。
4. **实现任务恢复。** 按第 4.3 节区分未处理、未发、已发和不明状态。处理过期消息时标记过时或待核对，不能恢复后批量补发陈旧答案。确认模板是否真能补回断线消息；没有证据就保留缺口并通知核对，不能仅重连成功就宣称消息无丢失。
5. **部署独立进程。** 在满足现有模型资源需求的常开主机上，使用 Compose 启动 API、渠道 worker 和现有 Qdrant；持久化数据、只读挂载模型、限制日志大小。核心 API 不使用 `--reload`，渠道监听器不放进每个 API worker 的启动钩子。
6. **落实状态与通知。** 记录连接、登录、worker 心跳、最近成功处理、最老待处理消息、发送不明和通知失败。配置另一台设备或外部探测检查整机失联，不能只在业务主机内监控自己。
7. **实现备份与恢复。** 每日备份 SQLite、现有 Memory、商品资料、规则和配置版本，并存一份异机副本；使用数据库备份接口或停写一致性备份，不直接随意复制运行中的数据库文件。[S7] 在隔离目录实际恢复一次，再核对消息和会话。
8. **做故障演练。** 依次断网、终止进程、重启主机、模拟模型超时和登录失效，再观察至少 24 小时。杀进程时覆盖“收消息落库后”和“发送调用后、确认落库前”两个关键位置。

**验证方法：** AC04、AC11、AC13—AC18；暂停状态与已确认记录重启后保留，异常通知实际收到。初版单机方案不承诺整机损坏时无停机，按备份恢复流程处置。

### S5：长期试运行与日常维护

**对应需求：全部需求的实际运行验证。产出：可核对的运行结果与简短维护手册。**

1. **锁定验收版本。** 固定代码提交、依赖、实际参考模板、模型配置和商品规则版本；通知、负责人及启用商品范围配置齐全。
2. **执行部署回归。** 运行现有测试与渠道测试，再用真实模型验证业务质量。不把 Mock 通过当作回答正确，不在测试中重新下载模型。
3. **持续运行。** 至少 7 个连续自然日，累计至少 100 条有效渠道咨询。自然咨询与经同意的测试咨询分别计数；模拟回放另列。低流量时报告样本不足，不制造对真实买家的批量消息。
4. **核对指标和问题。** 按 PRD 口径统计正确自动回答、澄清、转人工、发送失败、不明状态、时延和故障。至少完成一次商品资料更新和一次恢复验证；异常不从统计中悄悄删除。
5. **形成维护闭环。** 把错误咨询加入脱敏回归集，先修事实缺口、映射、动作或连接问题，只有明确定位到检索失效才调整 RAG。保留上一正常版本和恢复步骤，安排每日异常检查与每周事后抽查。

**验证方法：** 以 PRD 第 6 节为唯一指标门槛，不在技术文档另设一套宽松标准。关键错误先暂停受影响会话或商品，再修复回归；通过后才宣称“可长期运行的小规模 V1”。

## 6. 长期运行的具体约定

### 6.1 超时、重试与积压

下表是本项目起始配置，不是平台官方限制；根据目标机器和真实渠道限制在验收前调整、锁定。

| 项目 | 起始约定 | 到边界时怎样处理 |
|---|---|---|
| 生成并发 | 全局 1，同会话串行 | 先落库排队，不无限新建模型任务 |
| `/chat` 单条处理总期限 | 60 秒，含重试 | 超时转待人工；迟到结果不能重新获得发送权限 |
| 生成重试 | 最多 2 次总尝试，共用上述期限 | 只对明确暂时故障重试，并使用同一 request_id |
| 自动回复时效 | 入站后 120 秒 | 超时标记待人工或过时，不在恢复时突然补发 |
| 明确未发出的重试 | 最多 2 次总尝试 | 遵守平台限制及剩余时效；UNKNOWN 不自动重发 |
| 网络重连 | 2、4、8、16、32、60 秒，上限 60 秒，可加小幅抖动 | 登录失效不走网络重试循环；持续断线告警 |
| 发送节奏 | 单账号串行，默认间隔至少 2 秒 | 有更严格平台限制时以其为准；同会话不乱序 |
| 运行状态 | worker 每 10 秒更新状态 | 失联或任务无进展触发检测，不能依赖有没有买家说话 |
| 日调用上限 | 部署前由卖家配置正整数 | 达到上限保留消息并通知，不静默调用产生无限费用 |

HTTPX 的读取超时是等待数据块的时限，不等于整条客服任务总耗时；要另加覆盖生成和重试的总截止时间。[S6] HTTP 超时后，核心中可能仍有任务运行，必须通过 request_id、并发限制与结果状态排除迟到回复，不能不断产生后台重复推理。

模板业务心跳初值可以沿其现有配置实测，不能把它当作官方协议保证。慢模型响应期间心跳仍应正常；心跳协程退出但接收循环没有关闭的情况也要故障注入验证。

### 6.2 登录、平台变化与消息缺口

记录 `ONLINE / RECONNECTING / AUTH_REQUIRED / ERROR` 等连接状态，但它们与账号发送开关分开：连接在线不代表允许发送；账号启用也不能绕过失效登录。

普通短时故障可以自动重连；平台要求正常重新登录或验证时，需要卖家处理。恢复后用当前有效凭据验证接收及一次授权测试，再恢复自动模式。不实现验证码绕过、批量换账号或隐藏风控失败的循环。

逐项核实断线消息恢复：平台是否重放、标识是否保持一致、有无可用的历史查询。能补拉时按标识去重并过滤过时任务；无法补拉时保存缺口起止时间并通知核对，未知不能写成“没有漏消息”。

没有任何可靠发送回执、查询或自身回显时，不承诺自动确认送达；正常发送记录与买家侧抽查分开。此限制若导致每条回复都需要人工核对，说明该接入实现尚不满足本项目长期自动运行目标，应先完善或更换渠道实现，而不是把逐条核对变成产品常态。

### 6.3 部署与启动

开发继续使用现有 Windows 环境。长期运行使用常开主机；先实测当前 Embedding、Reranker 与核心服务的内存、显存、冷启动和单轮耗时，再确定部署资源，不默认任意小服务器都能运行。

Compose 至少包含：

| 服务 | 启动与数据要求 |
|---|---|
| `api` | 现有 FastAPI，一套本地模型；模型目录只读挂载；MCP 生命周期沿用现有实现 |
| `xianyu-worker` | 单实例；不加载模型；与 API 内网通信；渠道状态目录持久化 |
| `qdrant` | 复用当前配置和知识库；持久化现有数据 |

各服务使用经过验证的固定镜像或提交，不用浮动 `latest`。可使用 `restart: unless-stopped`；Docker 的退出重启策略不等于健康检查失败就必然重启。[S9] 卡死但未退出的任务应由进展监测发现；账号验证问题则保持暂停并通知，不用重启风暴解决。

启动顺序是：Qdrant 与必要存储就绪 → 核心 API 及模型就绪 → 渠道 worker 接通 → 一次性明确启用真实发送。API 冷启动时间单独记录，渠道尚不就绪时不谎报客服已上线。

继续用 Windows 长期运行时，也必须验证机器不休眠、Docker 或进程管理环境随系统启动、退出终端后服务仍在，以及系统重启后的恢复。单纯开着 PowerShell 不算常驻部署。

### 6.4 备份、更新和恢复

数据库备份使用 Python `sqlite3.Connection.backup()` 或经验证的一致性方案；该接口支持数据库使用期间的备份。[S7] 同时备份现有 Memory、商品原始资料与卖家规则。Qdrant 要么沿用已经验证的备份方式，要么验证从版本化原始资料重建的流程与耗时。

每日备份至少保留一份异机副本，限定读取权限，不夹带明文 Cookie。每日备份在整机存储损毁时仍可能损失最近一个备份周期的数据；它不等同于普通进程重启会丢掉已提交记录。

恢复顺序：关闭发送 → 恢复数据库与对应版本 → 核对会话、商品、接管和未完成发送 → 用渠道记录或原生界面处理恢复边界内的不明记录 → 验证核心与收发 → 明确恢复自动客服。

普通进程重启可以保留原来的 AUTO 状态并按消息账本恢复；**从旧备份恢复必须先关闭发送**，因为备份后平台上可能已经发出了新消息。不能运行旧数据库里的待发任务来“自动补齐”。

更新商品或规则时，先验证新资料，再切换版本；正在生成但依赖旧版本的回答失效并在期限内重新生成，否则待人工。若现有入库流程无法完整切换，短暂暂停相关商品自动回复，避免半新半旧。

程序更新先暂停新发送、核对在途任务、备份，再发布已测试版本；保留上一正常版本。数据库有结构变化时先验证兼容，回退代码不自动代表数据库也已经回退。

### 6.5 日志、通知与隐私

每条消息至少能查到：关联 ID、会话、商品、接收时间、处理动作、耗时、发送状态、错误类型和使用的数据版本。状态页或状态命令显示：登录、连接、待处理数量、最老任务、不明发送和待人工事项。

通知重点是登录失效、长期断线、处理连续失败、发送不明、数据库或磁盘异常、备份失败。相同故障合并通知，恢复后发一次恢复说明；不按每条重试轰炸卖家。

业务主机完全掉线时，主机内通知进程也会停，必须由独立设备或外部探测发现。通知渠道不是“打印了一行日志”，要有负责人实际收到的测试记录。

凭据从环境变量或受限文件读取，不提交 Git、不出现在截图和普通日志中。核心 API 和管理入口仅内网或受认证访问；不向公网裸露商品、聊天记录和控制接口。调用模型只传当前回答所需数据，不将登录凭据及无关个人信息发送给模型。

## 7. 最小目录与开发命令约定

实施时优先合并到现有同职责模块，不机械创建重复目录。

```text
app/
  channels/xianyu/
    client.py          # 参考模板的登录、连接、接收与发送封装
    adapter.py         # 原始事件 → 标准消息、买家与商品映射
    chat_client.py     # 调用现有 /chat，不加载模型
    worker.py          # 去重、消费、动作执行、回执与恢复
    store.py           # 渠道消息账本、状态和商品映射
    control.py         # 暂停、恢复、接管、状态、待人工处理
  ...                  # 原 API、RAG、MCP、Memory 继续复用
tests/
  channels/            # 脱敏回放、发送模拟、重启与异常测试
scripts/
  backup_service.py    # 备份与恢复验证；已有脚本则复用
data/channel/          # SQLite、锁文件；不提交 Git
```

下面是需要在实现后交付的命令形式，**当前文档没有生成这些 Python 模块，不能宣称现在即可执行**：

```bash
# 启动独立渠道进程（配置默认不允许真实发送）。
python -m app.channels.xianyu.worker

# 查看状态与待人工事项。
python -m app.channels.xianyu.control status
python -m app.channels.xianyu.control pending

# 首次配置、真实收发验证通过后，一次性启用。
python -m app.channels.xianyu.control enable

# 暂停所有新发送；显式恢复面向后续消息。
python -m app.channels.xianyu.control pause
python -m app.channels.xianyu.control resume

# 接管某一会话，处理后再恢复。
python -m app.channels.xianyu.control takeover --chat-id <内部会话ID>
python -m app.channels.xianyu.control release --chat-id <内部会话ID>
```

命令中的 `<内部会话ID>` 要替换为状态列表显示的实际值，不原样执行。控制命令通过同一数据库事务更新状态；启动、暂停、恢复和失败都应返回清楚结果。恢复不默默发送过时待办；发送不明的核对功能必须记录依据，不提供一个无条件“再发一次”按钮。

配置至少包括：API 地址和内部认证、凭据文件位置、卖家账号、启用商品、渠道状态路径、总截止时间、重试次数、每日调用上限、通知接收人。本地模型路径沿用当前配置；容器只改变挂载路径，不重新下载或更换模型。

## 8. 测试怎样组织、每次开发怎样交付

### 8.1 三层测试缺一不可

| 测试层 | 具体方法 | 证明什么 |
|---|---|---|
| 单元与故障测试 | 脱敏真实报文 + 假 WebSocket／假 HTTP；重复、超时、断线、回显、暂停 | 协议映射、状态与恢复逻辑正确 |
| 真实模型业务测试 | 固定商品和规则，运行 PRD 的 40 条测试集及多轮会话 | 现有 /chat 真正答对且动作正确 |
| 真实渠道与长跑 | 同意测试的账号真实收发，再按 PRD 做 7 天运行记录 | 真能接通、自动发回，并能持续运行 |

普通 pytest 不联网、不加载大模型、不发送真实买家消息；真实模型和渠道测试使用显式开关独立执行。还需模拟买家要求泄露密钥、修改卖家规则或指定其他收件人的输入，验证它不能改变权限、事实来源或发送对象。测试隔离凭据，防止 CI 意外连到生产账号。

### 8.2 两个必须自动化的故障案例

**案例 A：处理到一半退出。** 让消息提交成功后终止 worker，重启后应继续处理一次；再在发送调用已经执行但确认尚未提交时终止，重启后应先进入 UNKNOWN 核对，不能直接发第二次。

**案例 B：人工接管与慢答案。** 让 `/chat` 延迟返回，在此期间接管会话；答案返回后应被版本检查拦住。明确恢复机器人后，也不能把被人工处理过的旧答案重新激活。

### 8.3 阶段交付格式

每个阶段记录：实现的需求编号、改动文件、复用点、实际测试命令与结果、脱敏证据、未验证能力。S1/S2 以渠道样本为证据，S3 以完整自动问答为证据，S4/S5 以故障演练和运行记录为证据。
