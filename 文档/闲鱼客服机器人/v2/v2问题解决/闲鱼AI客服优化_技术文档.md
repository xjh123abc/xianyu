# 闲鱼 AI 客服优化技术文档

## 1. 本次技术目标

本次不重做现有 RAG / MCP，而是在现有客服主链路上补三个关键能力：

```text
消息进入
   ↓
① 判断 AI 有没有资格介入
   ↓
② 确定当前会话正在讨论哪件商品
   ↓
③ 获取商品事实 / RAG / MCP
   ↓
④ 生成自然、简短、不越界的客服回复
   ↓
⑤ 发送前再次检查会话状态
   ↓
发送
```

要解决的问题分别是：

1. **介入边界错误**：我方作为买家时 AI 仍参与回复；
2. **商品上下文丢失**：连续对话时重复索要商品编号；
3. **回复表达生硬**：回答像数据库报告，不像客服交流。

---

# 2. 第一阶段：先建立 AI 介入边界

这是本次最优先处理的部分。

如果“该不该说话”都判断错了，后面回答得再自然也没有意义。

## 2.1 目标

在进入 `/chat`、RAG、MCP、LLM 之前，先增加一层：

```text
Conversation Guard
```

它只负责回答一个问题：

> 当前这条消息，是否属于我方卖家客服应该处理的会话？

---

## 2.2 判断原则

只有同时满足下面条件，才允许 AI 继续：

```text
我方是当前商品卖家
AND
消息来自对方买家
AND
当前商品属于我方已绑定商品
AND
当前会话 AI 托管已开启
AND
没有人工接管
```

否则：

```text
直接 return IGNORE
```

注意：

`IGNORE` 不是 `HUMAN`。

二者含义不同：

```text
IGNORE
= 这件事本来就不属于 AI 客服
= 不回复

HUMAN
= 这是客服问题，但 AI 无法安全回答
= 转人工
```

---

## 2.3 需要确认的原始消息字段

先打印或只读检查闲鱼收到的原始事件结构，确认实际能取得哪些字段。

重点找：

```text
conversation_id / chat_id
sender_id
receiver_id
item_id / product_id
seller_id
buyer_id
message_direction
item_owner_id
```

实际字段名以当前闲鱼消息为准，不要为了完成逻辑凭空假设字段存在。

---

## 2.4 推荐判断方式

### 第一优先级：商品归属

如果当前聊天关联商品为：

```text
item_id = CANON_FTB_001
```

并且本地绑定表明确记录：

```text
该商品属于我方卖家账号
```

则这是“可能允许 AI 接待”的卖家会话。

如果商品属于别人：

```text
直接 IGNORE
```

---

### 第二优先级：发送者身份

确认当前进入系统的是：

```text
对方买家 → 我方卖家
```

而不是：

```text
其他卖家 → 我方买家
```

不要使用下面这种错误逻辑：

```text
只要是“对方发来的消息”
→ 就认为是买家消息
```

因为当我方在买东西时，其他卖家的回复同样属于“对方发来的消息”。

---

## 2.5 建议新增统一入口

示意：

```python
decision = conversation_guard.check(event)

if decision == "IGNORE":
    return

if decision == "ALLOW":
    handle_customer_service(event)
```

后续 `/chat`、RAG、MCP 都只能出现在 `ALLOW` 后面。

---

## 2.6 第一阶段验收

至少准备两类真实测试。

### 用例 1：别人咨询我方商品

```text
买家 → 我方商品
```

结果：

```text
ALLOW
→ 调用 /chat
→ 正常回复
```

### 用例 2：我方咨询其他卖家

```text
我方是买家
→ 其他卖家回复
```

结果：

```text
IGNORE
→ 不调用 /chat
→ 不发送任何消息
→ 不触发企业微信转人工
```

通过这一阶段后，再做后面的功能。

---

# 3. 第二阶段：保存“当前会话正在聊哪件商品”

## 3.1 当前问题

现在很可能存在这种情况：

```text
第一轮：
消息里带 item_id
→ 系统知道是 Canon FTb

第二轮：
“这是 50mm 镜头吗？”
→ 当前消息没有再次携带有效 item_id
→ /chat 认为不知道商品
→ 要求用户重新提供商品编号
```

也可能是：

```text
item_id 实际传进去了
→ 但某个回答分支没有使用
→ 仍然返回“请提供商品编号”
```

因此这一阶段第一步不是直接加 memory，而是先定位：

> 第二、第三轮调用 `/chat` 时，实际传入的 `item_id` 到底是什么？

---

## 3.2 增加 Conversation Context

为每个会话保存最小状态：

```json
{
  "conversation_id": "xxx",
  "current_item_id": "CANON_FTB_001",
  "ai_enabled": true,
  "human_takeover": false,
  "updated_at": "..."
}
```

第一版只保存必要字段，不做复杂长期记忆。

---

## 3.3 绑定规则

当买家从某件商品进入聊天，并且系统成功识别该商品后：

```text
conversation_id
      ↓
绑定
      ↓
current_item_id
```

例如：

```text
chat_123
→ CANON_FTB_001
```

后续买家说：

```text
这个
这台
它
带镜头吗
50mm 吗
```

都默认使用：

```text
CANON_FTB_001
```

---

## 3.4 item_id 解析优先级

推荐：

```text
1. 当前消息明确携带新的商品 ID
2. 当前会话保存的 current_item_id
3. 无法确定时才进入澄清
```

不要反过来每轮都重新要求买家提供编号。

---

## 3.5 区分两种“未知”

这是这一阶段最重要的逻辑之一。

### 情况 A：不知道是哪件商品

```text
current_item_id = None
```

可以澄清。

但面对真实买家时，应尽量用自然语言：

> “你问的是刚才那台 Canon FTb 吗？”

而不是：

> “请输入 DEMO_ITEM_001。”

---

### 情况 B：知道商品，但不知道某个属性

例如：

```text
current_item_id = CANON_FTB_001
lens_focal_length = unknown
```

这时绝对不能返回：

> “请提供商品编号。”

应该进入“商品属性缺失”处理：

> “镜头焦段这部分我这边还没有确认。”

必要时再转人工。

---

## 3.6 第二阶段验收

连续发送：

```text
这个相机还在吗？
↓
这是 50mm 镜头吗？
↓
这个镜头一起出吗？
```

检查：

- 三轮 `conversation_id` 一致；
- 后两轮仍能取得同一个 `current_item_id`；
- 不重新索要内部商品编号；
- 属性未知时只说明该属性未知。

---

# 4. 第三阶段：检查并补齐商品事实

## 4.1 为什么要做

“知道当前商品”并不等于“知道所有商品信息”。

例如系统知道：

```text
商品 = Canon FTb
```

不代表系统一定知道：

```text
镜头是不是 50mm
镜头是否随机器一起出售
有没有摔过
有没有维修过
```

如果这些事实不在商品数据里，Prompt 再好也不能安全回答。

---

## 4.2 商品数据建议包含

按实际业务需要逐步补，不要求一次性全部增加。

例如：

```json
{
  "item_id": "CANON_FTB_001",
  "title": "Canon FTb 胶片相机",
  "sale_status": "listed",
  "lens": {
    "included": true,
    "focal_length_mm": 50,
    "model": "..."
  },
  "condition": "...",
  "known_issues": [],
  "accessories": []
}
```

未知就保持未知，不要填猜测值。

---

## 4.3 事实优先级

建议明确：

```text
结构化商品事实
   ↓
卖家人工维护资料
   ↓
RAG 知识
   ↓
LLM 组织语言
```

LLM 最后只负责：

> 把已确认事实说得自然。

LLM 不负责：

> 猜商品到底有没有某个配件。

---

## 4.4 第三阶段验收

分别测试：

```text
已知字段
→ 能准确回答

未知字段
→ 明确说未确认

冲突字段
→ 不擅自选择，转人工
```

---

# 5. 第四阶段：重做回复策略，解决“生硬”

前面三阶段保证“说不说”和“说什么”是对的。

这一阶段才处理：

> 怎么说得像正常客服。

---

## 5.1 先检查固定模板

先全局搜索当前代码中的这些文本：

```text
请提供具体商品编号
卖家资料标记为
下单前建议再次联系卖家确认
这个问题需要卖家确认
已记录，卖家看到后会处理
```

确认它们到底来自：

```text
A. Python 固定模板
B. Prompt
C. LLM 自由生成
```

如果是 A：

```text
改 Prompt 没用
```

必须直接调整模板或分支逻辑。

---

## 5.2 正常回复规则

正常客服回答统一遵守：

```text
1. 第一小句直接回答问题
2. 默认 1～2 句话
3. 不复述完整商品标题
4. 不输出 item_id
5. 不说“数据库显示”“卖家资料标记”
6. 不重复已经确认过的信息
7. 不做未经执行的承诺
8. 不确定就明确说哪里不确定
```

---

## 5.3 推荐生成输入

不要只把用户最后一句话丢给模型。

建议至少传入：

```text
当前商品事实
+ 当前会话商品
+ 最近少量对话
+ 当前用户问题
+ 回复规则
```

例如：

```text
当前商品：
Canon FTb 胶片相机

状态：
在售

镜头：
是否 50mm：未知

最近对话：
买家：这个相机还在吗？
客服：还在的，这台目前还没出。

当前问题：
这是 50mm 镜头吗？
```

模型才能正确理解：

> “这”指的是什么。

---

## 5.4 Prompt 约束重点

Prompt 不需要写得特别长，重点是明确。

示例规则：

```text
你是卖家侧客服。

只基于提供的商品事实回答。
先直接回答用户当前问题。
回复尽量控制在 1～2 句话。
使用自然、口语化但不过度热情的中文。
不要出现内部商品编号、数据库字段、系统术语。
如果当前商品已经明确，不要再次要求商品编号。
某个属性未知时，只说明该属性尚未确认。
禁止编造库存、镜头、配件、成色、发货和卖家动作。
```

再补几组项目自己的好/坏示例。

---

## 5.5 示例

### 在售

不好：

> “‘Canon FTb 胶片相机’的卖家资料标记为在售。”

较好：

> “还在的，这台目前还没出。”

---

### 属性未知

不好：

> “请提供具体商品编号 DEMO_ITEM_001。”

较好：

> “镜头焦段这部分我这边还没有确认。”

---

### 已知包含 50mm 镜头

较好：

> “带的，这台是和 50mm 镜头一起出的。”

只能在商品数据明确记录时这样回答。

---

# 6. 第五阶段：发送前增加最后一道保护

AI 生成回复到真正发送之间可能存在时间差。

例如：

```text
AI 正在生成
↓
卖家此时人工回复了
↓
AI 旧答案生成完成
```

如果直接发送，就会出现 AI 和真人抢答。

因此发送前必须再次检查：

```text
当前是否仍允许 AI 回复？
```

---

## 6.1 发送前检查

至少确认：

```text
ai_enabled == true
human_takeover == false
conversation_role == seller_service
current conversation 没有被关闭
```

如果任何条件变化：

```text
丢弃刚生成的答案
```

---

# 7. 最终主链路

优化后的流程建议固定为：

```text
闲鱼收到消息
        ↓
[1] 解析事件
        ↓
[2] Conversation Guard
        │
        ├── 非我方卖家客服场景
        │       ↓
        │     IGNORE
        │
        └── 允许 AI 接待
                ↓
[3] Conversation Context
    找 current_item_id
                ↓
[4] 商品事实 / RAG / MCP
                ↓
[5] 判断
        │
        ├── 能回答
        │      ↓
        │   自然语言生成
        │
        ├── 商品明确但属性未知
        │      ↓
        │   澄清 / 转人工
        │
        └── 当前商品无法确定
               ↓
            自然澄清
                ↓
[6] 发送前状态复核
        │
        ├── 已人工接管 → 丢弃
        └── 仍允许 AI → 发送
```

---

# 8. 推荐实施顺序

不要同时改所有模块。

## Step 1：定位现状

只读检查：

```text
原始闲鱼消息结构
商品映射逻辑
/chat 请求参数
“请提供商品编号”的返回位置
固定回复模板
人工接管状态
```

输出当前真实链路。

---

## Step 2：实现 Conversation Guard

先解决：

> AI 到底该不该介入。

完成后单独测试。

---

## Step 3：实现 Conversation Context

先只保存：

```text
conversation_id → current_item_id
```

解决重复索要商品编号。

---

## Step 4：区分商品未知和属性未知

这是修正当前错误回复的关键。

---

## Step 5：补商品事实

只补本轮真实需要回答的字段，例如镜头信息。

---

## Step 6：调整固定模板

删除用户可见的：

```text
内部 item_id
数据库式表达
系统式表达
```

---

## Step 7：调整 LLM Prompt

让模型：

```text
短
直接
自然
不编造
承接上下文
```

---

## Step 8：增加发送前复核

防止人工接管之后旧答案继续发出去。

---

## Step 9：做完整回归测试

最后再完整测试：

```text
卖家场景
买家场景
连续三轮
属性已知
属性未知
人工接管
AI 暂停
异常 /chat
```

# 10. 本次改造的核心原则

整个改造只围绕三个问题：

```text
第一层：该不该说？
第二层：正在说哪件商品？
第三层：应该怎么说？
```

顺序不能反。

不要先花大量时间训练“像真人”，却让 AI 在错误的会话里自然地说错话。

本次完成标准不是“100% 像人工客服”，而是：

> **边界正确、上下文正确、事实正确，在此基础上让表达尽量自然。**
