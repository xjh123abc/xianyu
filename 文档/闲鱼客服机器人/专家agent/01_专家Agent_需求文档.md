# 闲鱼专家 Agent 改造需求文档

版本：V2 · 仓库结构版  
代码基线：`xjh123abc/xianyu` / `xianyu-dev` / `385ee01e8f9007ec34530c7a06ce9ec55ece6b9c`  
配套文档：[技术文档](02_专家Agent_技术文档.md)

> 本文是待实施需求，不表示专家功能已经上线。本次只提交两份文档，不修改业务代码。

## 1. 改造目标

在现有闲鱼回答链路中加入“问题规划 + 商品专家 + 价格专家 + 服务专家”，解决复合问题漏答、交易条件丢失和未知事实乱答。

外部继续使用 `POST /chat`，不新增 `/agent/chat`。闲鱼收发、商品绑定、MCP、RAG、会话锁、人工接管和企业微信通知继续使用原有模块。

## 2. 当前已经有什么

以下内容已从本次代码基线确认，不需要重新建设：

| 当前文件 | 已有能力 | 本次处理 |
|---|---|---|
| `app/api/chat.py` | `/chat` 请求、响应模型 | 保留入口，仅补充接管原因字段 |
| `app/services/chat_service.py` | 会话管理、商品解析、订单与闲鱼分流 | 在闲鱼回答分支接入专家编排层 |

当前价格代码已经能够组合“不包邮减20”和“小刀10”，仓库也已有 1470 的测试。本次是迁移、统一并补齐复合问题，不应把已有计算当作尚未实现。

当前 `clarify` 在渠道中也会转人工。本期保持这一行为，不额外开发自动澄清对话。

## 3. 专家职责

| 专家 | 处理问题 | 允许的数据来源 |
|---|---|---|
| 商品专家 `ProductAgent` | 在售、成色、功能、附件、维修史、型号使用知识 | 当前商品的 MCP 返回事实、商品介绍、匹配范围的知识资料 |
| 价格专家 `PriceAgent` | 标价、最低价、小刀、买家报价、包邮条件 | 当前商品价格政策和买家明确提出的条件；金额由程序计算 |
| 服务专家 `ServiceAgent` | 发货、快递、包装、面交、售后、普通招呼 | 当前商品服务信息、本店通用规则 |

专家只返回结果。不得直接发送闲鱼消息、通知企业微信、修改订单，或相互循环调用。简单问题不强制调用模型；需要生成时使用现有 DeepSeek 配置和调用封装。

## 4. 功能要求

### R01：一条消息中的问题必须全部处理

例如“还在吗？修过没有？不包邮最低多少？”必须形成三个任务：在售、维修记录、不包邮最低价。

同一个专家的任务合并执行；最终只生成一条买家回复。无标点长句也必须处理，不能只按问号或逗号切分。拆分保留“不包邮”“如果没修过才买”“不要镜头”等条件和否定关系。

### R02：商品事实与型号知识不能混用

“这台修过没有”只能依据这件商品的明确记录；“这个型号如何上卷”可以使用相应知识资料。

缺失、`unknown` 或存在冲突的事实不得推断成“没有问题”。“快门正常”不等于“每档速度都校验准确”，“镜头干净”不自动等于已经完成所有专项检测。商品介绍中存在明确答案时也要读取，不能只因没有专门字段就转人工。

服务规则只能来自当前商品或本店知识库，不使用演示电商知识库替卖家作承诺。

### R03：价格政策只有一套计算结果

沿用当前 `data/xianyu/items.json` 的字段，不另外维护一套平行价格数据。当前商品政策为：

| 项目 | 确认规则 |
|---|---|
| 标价 | 1500 元，当前方案包邮 |
| 小刀 | 累计最多减 10 元 |
| 买家承担运费 | 商品价减 20 元，可再叠加上述小刀 |
| 包邮最低商品价 | 1490 元 |
| 不包邮最低商品价 | 1470 元；实际运费不能编造 |

执行要求：

1. 每次从原始标价和适用政策重新计算，不能每轮继续减 10 元。
2. “最低多少”与“我出1495”分开处理：前者报底价，后者在条件满足时接受1495，不主动降到1490。
3. 同时问包邮和不包邮，分别回答1490和1470；比较方案不代表已经选择方案。
4. “1470包邮”不能改成“不包邮1470”后擅自接受。报价条件不清且影响判断时，按 R06 处理。
5. 低于授权价格、未授权的自提优惠、拆卖优惠或附带条件无法核实时，按 R06 处理。没有政策不等于可以给零优惠后直接同意附带条件。
6. 商品已售出时说明状态，不接受成交；无法解析或相互冲突的价格政策不继续报价。
7. 不承诺“已经改价”“已经发货”。本期没有新增这些执行能力。

### R04：共享已有会话，不创建专家各自的记忆

同一会话支持“那不包邮呢”“再少十块呢”等追问。不同会话、不同商品不能串用条件。

买家的条件、AI的历史回答和卖家确认的事实必须区分。历史回答可以辅助理解追问，不能成为新的价格政策或维修记录。切换商品后清除上一件商品的交易条件。

### R05：回答自然，但不能靠润色改变结论

正常答案使用简短自然中文，不出现内部商品编号、字段名、数据库、专家名称。

所有任务都有依据才回复。价格、邮费条件、商品状态不能在合并时被模型改写；同一条消息中多个任务按原始问题顺序合并，不再增加一个总控模型重新自由回答。

### R06：回答不了统一接管

任一必要任务缺少证据、存在冲突、超出授权或执行失败，整条消息买家端只回复：

> 稍等我看看

同时复用现有 S3：记录人工状态、发送企业微信通知、停止后续正常自动回复，直到卖家主动恢复。通知中保留原问题、缺失内容和已经确认的简要结果。

不得出现“需要卖家确认”“我帮你问卖家”等买家可见表达。不能用文字替换掩盖一次原本有数据可答的问题；已确认的1470报价必须正常回复。

直接调用 `/chat` 只返回决策；是否发送消息和通知由 S3 执行，不能把接口测试当作企业微信已经通知成功。

## 5. 分步交付

| 步骤 | 具体做什么 | 完成标志 |
|---|---|---|
| S1 固定基准 | 保存当前商品快照，运行现有闲鱼、API、订单测试；记录已有失败 | 新旧问题可区分，不删除失败断言掩盖问题 |
| S2 迁移价格 | 从事实响应器抽出价格计算，规范现有两条政策文本，完成单价与条件测试 | 1490、1470、1495出价、多轮不累减均正确 |
| S3 封装专家 | 商品与服务专家复用事实读取和范围化检索，增加专用生成提示词 | 每个任务返回答案或明确缺失原因 |
| S4 规划与上下文 | 扩展现有问题规划器，识别复合问题、条件与连续追问 | 任务不遗漏，条件不串商品 |
| S5 接回主链路 | 在现有闲鱼分支调用编排层，贯通接管原因，复用S3 | 一个最终决定；正常回复或一次接管 |
| S6 验收切换 | 先模拟接口与渠道，再跑固定批量问题，最后小范围真实测试 | 全部关键用例通过后才启用真实自动发送 |

## 6. 验收用例

除特别说明外，使用本仓库当前 Canon 商品资料；未知事实场景修改测试副本，不能为了测试改动真实商品。

| 编号 | 输入／场景 | 预期结果 |
|---|---|---|
| A01 | 还在吗？ | 回复在售，不调用RAG |
| A02 | 包邮最低多少？ | 1490元 |
| A03 | 不包邮最低多少？ | 1470元，不转人工 |
| A04 | 包邮最低多少？不包邮呢？ | 同条回复区分1490／1470 |
| A05 | 包邮1495可以吗？ | 接受1495，不主动报价1490 |
| A06 | 1470包邮可以吗？ | 固定等待回复并接管 |
| A07 | 还在吗有没有维修过不包邮最低多少 | 回答在售、已记录维修史、1470，不能只报价 |
| A08 | 今天能发吗？走顺丰吗？ | 按当前记录说明48小时内、中通，不承诺今天或顺丰 |
| A09 | 测光和手机对比过吗？资料无该记录 | 固定等待回复并接管，不由“功能正常”推断 |
| A10 | 复合问题中只有一个关键事实缺失 | 买家仅看到等待话术；通知说明缺哪一项 |
| A11 | 先问包邮最低价，再问“那不包邮呢？” | 使用同一会话，回答1470 |
| A12 | 不包邮1470后再要求少10元 | 不报价1460，按越权规则接管 |
| A13 | 商品A谈不包邮，切换商品B | 不继承A的优惠政策或交易条件 |
| A14 | 型号知识有证据；另一商品文档混入 | 仅用正确范围证据；没有依据则接管 |
| A15 | 模型返回卖家确认话术、空结果或错误结构 | 统一接管，通知保留原因 |
| A16 | 同一消息重复到达，或生成时卖家接管 | 不重复发送；不发送过时的正常答案 |
| A17 | 通过HTTP调用接管场景，再由模拟S3处理 | `reason` 不丢失；通知一次；状态为HUMAN |
| A18 | 原有订单与普通RAG查询 | 原路由和响应契约不被专家改造破坏 |

## 7. 实施边界

不新增多Agent框架、联网搜索、自动改价或新的对外API；不替换模型，不迁移全部JSON，不重写消息收发。业务代码按技术文档逐步实现，不能一次性复制参考项目覆盖现有服务。
