# 闲鱼 AI 客服当前问题与优化方案

## 一、本轮只解决 3 个问题

1. **关键词回复不要再带字段标签。**
2. **一句话里同时问多个问题时，只要商品资料里有答案，就应该完整回答，不能直接转人工。**
3. **带条件的议价问题不能只按某个关键词回复，要理解整句话真正想问什么。**

本轮不换模型、不训练模型、不重做 RAG，也不取消现有人工接管保护。

---

# 问题 1：关键词回复不要带“标签”

## 1.1 当前问题

现在部分关键词回复直接把内部字段名一起发给了买家，例如：

```text
运费：包邮。
维修历史：没有维修过。
成色情况：机身成色尚可，有轻微使用痕迹。
```

这类表达像数据库字段展示，不像正常客服聊天。

这里要解决的并不只是“包邮”这一句话，而是一个**统一的回复规则**：

> 只要是关键词直接回复给买家的内容，就不要把内部字段标签一起发出去，只发送自然语言答案。

例如：

```text
运费：包邮。
→ 包邮。

维修历史：没有维修过。
→ 没有维修过。

发货时间：付款后 48 小时内发出。
→ 付款后 48 小时内发出。

成色情况：机身成色尚可，有轻微使用痕迹。
→ 机身成色尚可，有轻微使用痕迹。
```

## 1.2 应该怎么改

内部数据仍然可以继续保留：

```text
shipping
repair_history
shipping_time
condition
```

或者现有 JSON 中对应的字段名。

**只修改“面向买家的回复文本”，不要删除内部字段。**

也就是说：

```text
内部：字段名 + 字段值
        ↓
回复层：只把自然语言答案发给买家
```

应该检查现有的：

- 关键词回复映射；
- 回复模板；
- formatter / reply builder；
- 如果 LLM Prompt 中也要求输出“字段名：答案”，同步去掉这种要求。

不要使用“把冒号前面的内容统一删除”这种全局字符串处理，因为有可能误删正常回答。

## 1.3 验收标准

下面这些简单问题最终应类似这样回答：

```text
买家：包邮吗？
客服：包邮。

买家：有维修过吗？
客服：没有维修过。

买家：多久发货？
客服：付款后 48 小时内发出。
```

重点不是必须一字不差，而是：

- 不再出现“运费：”“维修历史：”“发货时间：”这类内部标签；
- 不能因为去掉标签而丢失真实限制条件。

# 问题 2：一句话问多个问题，明明有答案却转人工

## 2.1 当前问题

测试消息：

```text
还在吗？有没有维修过？包邮吗？
```

这里实际上包含 3 个问题：

```text
1. 商品是否还在售
2. 是否维修过
3. 是否包邮
```

这 3 项信息在当前商品 JSON 中都有答案，但系统没有把它们组合回答，而是直接进入了卖家处理 / 转人工。

期望结果应该类似：

```text
还在，没有维修过，包邮。
```

## 2.2 需要先确认的真正原因

需要检查当前消息处理链路，确认究竟发生了哪一种情况：

```text
买家消息
  ↓
关键词规则
  ↓
是否提前返回？
  ↓
商品 JSON 是否正确读取？
  ↓
相关商品事实是否真正传给 LLM？
  ↓
LLM 是否被调用？
  ↓
为什么最后进入 handoff？
```

重点排查：

### A. 关键词规则是不是只能处理一个问题

例如消息中出现了“包邮”，程序只检查到一个关键词，但发现整句话无法处理，于是直接转人工。

如果是这样，逻辑就是错误的。

**关键词规则处理不了完整消息，不代表商品没有答案。**

### B. JSON 里虽然有数据，但 LLM 实际没有拿到

必须确认当前商品资料确实在本次调用时被读取，并作为上下文传给 LLM。

“文件里存在”与“模型已经看到”是两回事。

### C. 明确的否定值是否被错误判断成“没有数据”

例如：

```json
"repaired": false
```

如果代码写成：

```python
if not repaired:
    # 当成字段缺失
```

那么“明确没有维修过”就可能被误判成“没有维修记录数据”。

需要区分：

```text
字段不存在 / null
```

和：

```text
字段明确为 false = 没维修过
```

## 2.3 正确的处理方式

建议把现有链路调整成：

```text
买家消息
  ↓
是否属于非常简单、可以被关键词规则完整回答的单一问题？
  ├─ 是 → 关键词直接回复
  │
  └─ 否 → 交给现有 LLM
             ↓
       读取当前商品资料
             ↓
       理解整句话有几个问题
             ↓
       根据商品事实逐项回答
             ↓
       合并成一条自然回复
```

关键原则：

> **关键词回复只负责简单问题。复杂、多问题表达交给 LLM。**

不要为了处理多问题，继续无限增加关键词组合规则，例如：

```text
还在 + 维修 + 包邮
维修 + 包邮
还在 + 包邮
……
```

这样以后组合会越来越多，很难维护。

## 2.4 LLM 应该拿到什么

至少需要有：

```text
当前买家的完整原始消息
当前绑定的商品 ID
当前商品可回答的事实
适用的卖家规则
必要的最近上下文
```

例如当前商品资料内部可能是：

```json
{
  "sale_status": "listed",
  "repair_history": "没有维修过",
  "shipping": "包邮"
}
```

LLM 要做的只是：

```text
读取事实
↓
理解买家的 3 个问题
↓
组合成自然回复
```

而不是自己猜商品事实。

## 2.5 给 LLM 的回答规则需要补充

现有 Prompt / system instruction 中应明确：

```text
1. 先识别买家这一条消息中所有需要回答的问题。
2. 根据提供的商品事实逐项回答。
3. 不要只回答其中一个问题。
4. 最终合并成简短、自然的一条客服回复。
5. 不要输出“运费：”“维修历史：”等内部字段标签。
6. 商品资料没有明确的信息不能自行编造。
```

## 2.6 验收标准

至少验证：

```text
还在吗？有没有维修过？包邮吗？
```

预期：3 个问题全部回答。

还要验证没有标准标点的表达：

```text
还在吗有没有维修过包邮吗
```

以及类似换一种说法：

```text
这台还没卖吧？修过没有？邮费怎么算？
```

只要对应事实都存在，就不能因为一句话有多个问题直接转人工。

# 问题 3：“不用包邮，能便宜吗？”被错误理解

## 3.1 当前问题

买家问：

```text
不用包邮，能便宜吗？
```

系统现在回答：

```text
运费：包邮。
```

这个回答没有回答买家的真正问题。

买家的完整意思其实是：

```text
如果我自己承担运费，商品价格能不能便宜一点？
```

这里包含两个信息：

```text
条件：不要卖家包邮 / 买家承担运费
核心请求：能不能降价
```

真正要回答的是“能不能降价”，而不是重新告诉买家“现在包邮”。

## 3.2 为什么会出现这种问题

最可能需要检查的是关键词规则是否类似：

```text
消息里只要出现“包邮”
→ 直接返回“包邮”
```

如果是这种逻辑，那么：

```text
包邮吗？
```

和：

```text
不用包邮，能便宜吗？
```

虽然都出现“包邮”，意思却完全不同。

因此：

> **不能把“句子里出现某个关键词”直接等价成“买家正在问这个关键词”。**

## 3.3 正确解决方式

简单问法仍然可以走关键词：

```text
包邮吗？
→ 包邮。
```

但下面这些包含条件、比较、议价的句子应交给 LLM 理解整句：

```text
不用包邮，能便宜吗？
我自己出邮费，价格能少一点吗？
自提的话能便宜一点吗？
不要镜头，只买机身多少钱？
```

新的逻辑应该是：

```text
消息是否是简单、单一、明确的关键词问题？
  ├─ 是 → 关键词直接回答
  │
  └─ 否 → LLM 理解完整语义
```

## 3.4 议价问题还需要“卖家规则”

LLM 理解了买家的意思以后，还必须有事实依据才能回答。

例如卖家规则可能是：

```json
{
  "negotiation_policy": "不议价"
}
```

那么可以回复：

```text
不包邮也是这个价格，暂时不议价。
```

如果卖家规则明确写着：

```text
买家承担运费可以优惠 20 元
```

才可以按这个规则回复。

如果当前商品资料只写了：

```text
售价：1500 元
包邮：是
```

但是没有写“不包邮能便宜多少”，那么系统不能自己计算或承诺优惠。

这时应该进入现有的卖家确认 / 转人工流程。

## 3.5 验收标准

必须至少测试：

```text
包邮吗？
```

仍然能快速回答：

```text
包邮。
```

但：

```text
不用包邮，能便宜吗？
```

不能再只回复“包邮”。

还需要测试：

```text
我出邮费，价格能少一点吗？
自提的话能便宜吗？
```

确保系统理解的是“条件 + 议价请求”。

# 四、三个问题应该统一成什么架构

本轮不用做复杂架构重构，只把现有规则和 LLM 的职责分清楚。

建议最终链路：

```text
买家消息
  ↓
会话状态检查
  ↓
当前商品绑定
  ↓
判断是否为简单、单一、可完整回答的关键词问题
  │
  ├─ 是
  │    ↓
  │ 关键词直接回复
  │    ↓
  │ 输出自然语言，不带字段标签
  │
  └─ 否
       ↓
     读取当前商品事实 + 卖家规则
       ↓
     交给现有 LLM 理解完整消息
       ↓
     回答所有问题 / 理解条件和真实诉求
       ↓
     有明确事实 → 自动回复
     没有事实或需要卖家授权 → 现有转人工流程
```

这个设计解决的核心矛盾是：

```text
关键词规则负责“快”
LLM 负责“理解”
商品 JSON / 卖家规则负责“事实”
人工接管负责“没有授权或无法确认的情况”
```

# 五、实现顺序

## 第 1 步：修改关键词回复的展示格式

只处理“不要带字段标签”。

不要同时改路由。

完成后验证：

```text
包邮吗？
有没有维修过？
多久发货？
```

---

## 第 2 步：检查并修正关键词分流

确认现有代码是不是“只要包含关键词就立即回复”。

修改成：

```text
只有简单、单一、可以完整回答的消息
才允许关键词规则直接结束处理。
```

多问题、条件表达、议价表达不要被关键词提前截断。

---

## 第 3 步：确认当前商品事实真正进入 LLM

检查：

```text
商品 ID 是否正确
JSON 是否读取正确
需要的字段有没有被过滤掉
false / 空值是否被正确区分
最终传给 LLM 的上下文是否包含这些事实
```

重点验证：

```text
还在吗？有没有维修过？包邮吗？
```

对应事实全部存在时，LLM 必须能够看到这 3 项。

---

## 第 4 步：调整 LLM 的回答要求

要求模型：

```text
完整理解整句话
识别所有问题
保留条件和否定关系
逐项使用商品事实回答
最终合并成自然的一条消息
不带内部字段标签
不编造商品事实或优惠政策
```

---

## 第 5 步：补充议价规则边界

检查当前商品数据中有没有明确的议价政策。

如果没有，需要增加的是“卖家规则数据”，而不是让模型猜。

例如可以有类似：

```json
{
  "negotiation_policy": "不议价"
}
```

或者更具体的已授权规则。

是否新增字段、字段叫什么，应优先复用项目已有数据结构，不要重复创建第二套规则系统。

# 七、本轮完成标准

满足下面 4 点，才算这轮优化完成：

```text
1. 关键词回复不再带内部字段标签。

2. 一句话包含多个已有答案的问题时，能够完整回答，
   不因为关键词规则能力有限而直接转人工。

3. “不用包邮能便宜吗”这类表达能够理解真正的议价意图，
   不再只根据“包邮”两个字直接返回固定回复。

4. LLM 只根据当前商品事实和卖家已授权规则回答，
   没有依据的优惠、商品事实仍然不能自行编造。
```
